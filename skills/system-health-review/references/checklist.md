# 四维度排查清单

每个维度的 prompt 直接引用（或展开）本清单。清单来自 2026-09 实战审查沉淀，方向按命中率排序。

## A1 冗余与重复

排查方向：
1. **核心业务规则重复**：如涨跌停幅度、手续费、交易时段判定——最易散布（实测 5 处独立实现 + 单位不一致 0.20 vs 20.0）。grep 关键数字/前缀组合（如 "300","301","688"）定位所有实现点。
2. **交易时段/日历窗口**：grep "09:3"、"15:0"、"in_session"、"lunch"；区分「宽窗/严窗」两种语义是否被强行写成多个函数。
3. **数据补齐/批拉模式**：同构 for-range(0,n,50) 循环、hub 缓存优先→miss 直查模式；找已局部抽函数的实现点上移为共享。
4. **技术指标前后端双实现**：跨语言不强行抽共享，但查口径漂移（RSI 平滑算法、chgOf 优先级）——建议黄金样本对照测试。
5. **缓存旁路**：统一 TTL 缓存模块之外的手写 `_cache = {}` + time.time()/monotonic 模式；不进观测注册表的缓存是盲区。
6. **回测/统计口径**：绩效指标是否共享库；多个回测是「范式不同」还是「重复实现」。
7. **前端格式化**：pct/fmt/颜色映射函数多处复制；同名函数不同语义（改名著重）。
8. **常量散布**：市场前缀、指数代码、分类字典多处硬编码。

判定要点：先问「差异是语义还是巧合」——宽窗与严窗是有意口径，不属重复；单位不同绝不能盲合。

## A2 数据源/依赖残留

排查方向：
1. **硬规则违规**：治理文档规定的「唯一实现入口」之外是否有直连（grep 接口域名/字段名）；调用方用 `_pick_provider(provider, "XxxProvider")` 或 `p.name == "xxx"` 直调即绕过。
2. **已替换字段残留**：被实证不可信的字段（如 f109 字段序推断）grep 全仓确认清干净；区分「静默残留」与「有据兜底」（路由层有覆盖+审计标注的降为低优先级）。
3. **能力选择绕过注册表**：类名/源名字符串硬编码 vs 查能力注册表。
4. **硬编码 URL 散布**：http(s):// 出现在 provider 目录之外即是散落（scripts/ 留档另论——查 automation/调度器是否活跃引用）。
5. **文档-代码路由一致性**：文档写的默认链 vs config 实际构造序 vs failover 实测行为。

判定要点：每个残留标「活跃度」——被路由/调度器调用=必须清理；CLI 留档=无害；「已知例外且有审计标注」单独归类。

## A3 死代码

排查方法：
1. **双向验证**：模块名 grep import 引用（排除 __pycache__）；public 函数 token 频次 < 2（仅定义处）才候选。
2. **端点审计**：路由定义 ↔ 前端 api 库路径常量 ↔ scripts 的 http 调用 ↔ tests 引用，四方交叉。
3. **前端导出审计**：api 库大文件的导出逐个 grep（用词边界防前缀函数误命中）。
4. **配置审计**：config 键 grep 读取点；依赖清单 grep import（排除 CLI 启动的 ASGI 服务器类）。

豁免清单（不算死代码）：
- 测试引用（但「仅测试可达」单独标注）
- FastAPI 装饰器路由、Alembic 迁移、pydantic 动态字段
- `__init__.py` 再导出 + 包名路径使用
- CLI 运维脚本（查 automation 活跃调度清单）
- 制度性数据文件（登记册/种子数据，0 import 但被文档引用）

灰色地带处置：Protocol/接口类 0 引用 → 建议激活类型检查而非删除；vendor wheel 疑似传递依赖 → pipdeptree 反查后再动。

## A4 过时决策

排查方向：
1. **文档 vs 代码**：抽查复盘/计划文档里 ❌未做 项（grep 代码可能已做完）、✅已做 项（可能被后续改动破坏）；文档内部自相矛盾的条目单独列。
2. **配置化退潮**：已配置化的阈值 grep 硬编码字面量回潮（新模块复制旧模式是高发区）。
3. **收口退潮**：统一 fetch/缓存/熔断基建建成后，新模块是否绕过（自建 httpx + 手写 for attempt in range(3)）。
4. **静默吞错**：非测试文件 `except Exception`/`except:` 后 pass（违反错误计数纪律）；有 noqa+注释的豁免。
5. **时区双轨**：正确范式（beijing_now 类）与裸 datetime.now() 并存的散布度。
6. **字段建了逻辑没接**：存储字段/schema 存在但消费判定缺失（半实现——agent 最容易报成「已实现」的地方，必须亲验）。
7. **被现实推翻的设计**：文档宣布「不再需要」的端点/模块，grep 前端与调度器的实际消费。

## 报告证据规范

- 每条发现必须带 `文件:行号`；关键判定附 1 行代码摘录（用 evi 样式块）。
- 亲验过的发现标「亲验」；未复核的 agent 发现不进 P0/P1。
- 排除清单（「明确不是问题」）要写进报告——它是防止下轮审查重复误报的资产。
- **复核工具可靠性自查**：shell grep 在部分环境对交替 pattern（`\|`）甚至普通 pattern 会静默无输出（假阴性），可把「存在」误判成「不存在」——定性结论（有无某函数/某字段/某消费点）一律用可靠工具（专用 Grep 工具 / sed 读行）读到原文再下结论；这条对「验证 agent」和「被 agent 验证」双向适用（实例：告警冷却先被 agent 报「已实现」、被假阴性 grep 推翻、最终第二次复核证实 agent 正确）。
- **分项回归绿 ≠ 全量绿**：治理批次逐项 commit、逐项定向回归全绿，仍可能在全量门禁翻车——定向测试的 stub/monkeypatch 范围恰好盖住被改函数、守卫类测试（env-docs）只在全量跑到、未使用 import 只有静态检查能抓。执行计划必须把「每批 commit 后跑一次全量门禁（pytest 全量 + pyflakes + tsc + eslint + vitest）」列为固定步骤。实例（09-07）：P1-3 收口把 `_in_market_hours` 改为引用 `tc` 但模块级未导入，定向测试整体 stub 其调用链全绿；运行时 NameError 被调用方 `except Exception` 静默吞掉 → 休市标记整个失效（「吞错 + 半接线」复合形态，pyflakes 静态抓出）。
