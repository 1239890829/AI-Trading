# System Health Review（系统健康度审查）

## Overview

对任意代码库执行结构化健康度审查：盘点全貌 → 四路并行深扫 → 交叉验证 → HTML 报告 + 分级执行计划。核心价值：用并行 Explore agents 换取扫描覆盖面，用亲自复核保证结论可信度。**产出物是评估报告与执行计划，不是代码改动**——每项修复须经用户确认后另行执行（改进先提后做纪律）。

## Workflow

### Step 1 — 盘点全貌（建立基线）

并行执行结构盘点，为 agent prompt 与报告提供基线数据：

```bash
# 后端/源码模块行数分布（排除缓存与依赖目录）
find backend/app -name "*.py" -not -path "*/__pycache__/*" | xargs wc -l | sort -rn | head -40
for d in backend/app/*/; do echo "$d: $(find "$d" -name '*.py' -not -path '*/__pycache__/*' | xargs wc -l 2>/dev/null | tail -1 | awk '{print $1}')"; done
# 前端同理；prune node_modules/.next 防止扫描超时
find apps/web \( -name node_modules -o -name .next \) -prune -o \( -name "*.tsx" -o -name "*.ts" \) -print | xargs wc -l | sort -rn | head -30
# 文档清单 + 测试规模
ls docs/ && find backend/tests -name "test_*.py" | wc -l
```

### Step 2 — 四维度并行深扫（Explore agents）

对 4 个维度执行**相互独立的并行审计批次**；可使用当前环境支持的并行代理/任务能力，也可串行运行，但每个审计上下文必须自包含：项目根路径、项目背景一句话、该维度的排查方向清单（见 `references/checklist.md`）、输出格式、只读纪律。输出格式统一为：

```
## 发现清单
每条：位置（文件:行号）+ 1 行代码摘录 + 判定依据 + 建议方案 + 影响范围 + 风险
## 明确不是问题的（排查过但确认合理，简列）
## 灰色地带（不能确定，需人工判断）
```

「明确不是问题的」区块是必须的——逼 agent 记录排查过的方向，既防误报又能进报告的排除清单。总输出限 2000~2500 字，按严重程度排序。

四维度分工：
1. **A1 冗余与重复**：同类功能多模块重复实现，评估抽离统一共享能力。
2. **A2 数据源/依赖残留**：被更优源替代的旧引用、绕过统一入口的直连、硬编码 URL、注册表绕过。
3. **A3 死代码**：孤儿模块/函数/端点/导出/配置/依赖，双向引用验证 + 可安全删除依据。
4. **A4 过时决策**：文档 vs 代码现实、旧模式回潮（配置化退回硬编码、收口后退回旁路）、静默吞错、时区/阈值类隐患。

prompt 必须包含防误报豁免条款：测试引用算引用、动态挂载（FastAPI 路由装饰器/Alembic/pydantic 字符串路径）、CLI 运维脚本、外部 automation 调度、留档数据文件不算死代码；「仅测试可达」要单独标注。

### Step 3 — 交叉验证（防误判，不可跳过）

对**所有将进入 P0/P1 计划的发现**逐项亲自 grep/读码复核。实战教训：

- **agent 的定性结论必须实证**：「已实现/未实现/半实现」类判断 agent 常出错——实测中 agent 报「冷却已实现于 alert_engine.py:110」，实际引擎无冷却逻辑、只有字段落库（半实现）。凡引用具体行号的定性，sed 读原文确认。
- **grep 用词边界**：`getKline` 无边界 grep 会误命中 `getKlinePayload`（前缀函数），把活跃代码误判成孤儿。用 `\bgetEvents\b` 或读上下文排除。
- **排除 node_modules**：全仓 grep 会扫依赖目录导致 SIGTERM 超时（exit 137）。限定目录（app/components/lib/hooks）或用 find -prune。
- **命令截断即拆分**：批量验证命令被 SIGTERM 时，拆成小命令逐个跑，别重试原命令。
- **转义差异**：agent prompt 里的代码形态（如 `p.name == "eastmoney"`）与 grep pattern 转义不一致会假阴性——直接 sed 读目标行号区间最可靠。

把修正过的 agent 结论记入报告「复核记录」章节（透明度），报告里每条亲验过的发现标「亲验」标签。

### Step 4 — 输出 HTML 报告

写到 `docs/system-health-review-YYYYMMDD.html`（单文件、内联 CSS、无外部依赖）。必备章节：

1. **总评**：总体评分（/100）+ 四维度分项评级（A/B/C + 一句话依据）+ 整体判断段落。
2. **系统全貌**：行数/模块/测试/文档统计卡（来自 Step 1）。
3. **发现明细**：按四维度分组；每条一张卡片（编号、严重度标签、位置行号、代码摘录块、差异/判定、方案、影响范围、风险）。
4. **文档滞后修正表**：文档说 X 代码实际 Y，逐条对照（高价值——防后人按过时文档办事）。
5. **执行计划表**：P0（违反硬规则/影响正确性）/ P1（中成本治理）/ P2（清理与文档）；每项含事项、影响范围、风险与注意、建议批次与节奏。
6. **复核记录**：agent 结论被修正的地方。

评分口径参考：代码卫生（孤儿数量/死配置/吞错密度）、治理合规（硬规则违规数）、重复度（重复簇数量与散布度）、决策新鲜度（过时模式数 + 文档滞后数）。

### Step 5 — 收尾纪律

- **只评估不实施**：报告末尾与给用户的回复中明确「本轮不改代码，P0/P1 待确认后执行」。
- 报告文件提交 git（docs/ 入库）；技能与报告分属不同路径。
- 若用户确认执行某批次：按批次独立 commit、每批跑门禁 + 相关模块回归测试；改动核心链路（如数据源路由）须用真实数据验证后再提交。

## 何时不用

- 单点 bug 或局部重构——直接处理，无需全套流程。
- 用户只要某个具体维度的排查——把对应 checklist 方向抽出来单独跑即可，不必四路并行。
- 无代码库可读的纯咨询——本技能以代码证据为前提（能用代码回答的不问用户）。
