# 文档 × 代码 对账（设计文档失真清理）

适用于文档过时、已做误报未做、设计误报运行和收尾对账；要同时检查版本指针、消费者、守卫反例与原 stage 状态。

**为什么需要**：设计文档写于立项期，代码其后快速演进，**文档只加不改**。于是同一份文档里
「设想」与「已实现」在行文上毫无区别，读的人无法分辨。危害有两个相反方向，**必须双向都防**：

| 方向 | 失真形态 | 危害 | 现场信号 |
|---|---|---|---|
| **低估完成度** | 文档写「未做 / 需要 X 前置」，其实早已实现 | **重复造轮子**——照单开发会重建已存在的能力 | 「❌ 未做」条目仍带"补法"描述 |
| **高估完成度** | 文档把「设想」写成现有能力（档位数、字段数、角色名、端点、名单） | **误判门禁/能力已达标**，交付出"有行无内容"的界面 | 「必须 / 需要」的宾语在代码里 grep 不到 |
| **归因错误**（事实对、因果错） | 文档写「X 生产 0 处使用」——**数字是真的**，但隐含的因果是"使用者疏忽" | **修错地方**：去催/去补调用点，而真相是**根本没提供那个入口** | 「0 处 / 无人使用 / 尚未接线」类陈述 |

⚠️ **三种失真的根因相同（文档 ≠ 事实），但处置不同**：低估要**销账**；高估要**改成事实**；
归因错误要**先问"是没用，还是没法用"**。混为一谈会「去重做一件已做完的事」
「继续相信一个不存在的字段」或「给一个不存在的入口补调用点」。

> **「0 处使用」是二义的**（2026-09-12 实例）：台账写「`PanelBoundary.resetKey` 生产 0 处传」——
> 计数属实，但真相是 `Panel`（全站唯一入口）**压根没暴露这个 prop**，设计者写在组件里的
> 契约「`resetKey` 不是可选项」在集成处**无法表达**。按"使用者的疏忽"去办只会白费功夫；
> 正确动作是**先补能力、再谈哪里该接线**。
> ⇒ **判据：读到「0 处使用 / 无人调用 / 未接线」时，必须先 grep 那个入口本身存不存在**
> （prop 有没有暴露 / 参数有没有透传 / 开关有没有暴露），再判是 usage gap 还是 capability gap。

## 标准流程

### 1. 扫出候选面（优先 rg，并核退出码与扫描范围）

按「会过期的时态词」扫，比按文件名扫更准：

```
Phase\s*\d | 未来[:：] | 后续[:：] | 必须 | 需要 | 待补全 | 规划 | 计划中 | 暂不
```

- **判定扫描面也是口径**：确定不扫哪些目录（见步骤 4 的「刻意不改」），否则会把
  合法用法当成缺陷，改出伪史。
- 顺带扫**数字类**：测试数 / 端点数 / 档位数 / 文件数。这类必须**指针式**（指向权威源）或
  实测回填，**禁止写死后不管**——否则下一个读的人会当事实。

### 2. 逐项 grep 代码真身（**两向都要跑**）

对每一条候选，**先证伪自己**：

- 想写「未做」→ 先 grep 同名/近义模块名、`scripts/verify_*.py`、`tests/`。
  很可能**整模块 + 核验脚本 + 否证结论都在**（连"已研究并否决"都有）。
- 想写「已做」→ 先 grep 具体的宾语：**字段名 / 档位数 / 角色名 / 端点路径 / 常量名**。
  文档说的 12 档可能只有 7 档、说的「名单」可能根本没有这张表。
- **只认代码位置，不认文档自述**：找到定义文件 + 消费方（谁调用它）才算数。
  「有模块」≠「有接线」≠「界面看得到」——验收终点是**渲染/被调用**，不是 `return`。
- ⚠️ **找消费方要按「端点路径 / 标识符」全仓反查，不要按页面名或功能名推断**。
  实测反例（2026-09-12）：台账写「组合级 `signal-health` 尚未单独展示」——查的人只看了
  **名字相近的那个页签** `/agent?tab=strategies`（它展示的是**策略级**，是另一层），
  于是把「某页签没显示」当成了「全站没显示」；实际 `GET /api/picks/signal-health`
  早被猎场统计条（`components/hunting/stats-bar.tsx`）消费并渲染。
  ⇒ 判「某能力有没有被消费」= 拿**端点路径 / 封装函数名 / 常量名**全仓 grep（有前端
  `lib/api.ts` 这类封装层就搜封装函数名），**按功能名或页面名推断必然漏**；
  漏了下场与「低估完成度」同害——把已有能力再实现一遍。

> 下“无引用”结论前，用 rg 对精确符号、路径、封装调用和动态注册做交叉检索，核命令退出码与忽略范围；单一工具的空结果不是缺失证明。

### 3. 就地改写成**三态**，而不是改成另一个断言

设计文档正文请用三态词汇，**别用阶段号做时间锚**：

- 「**已实现**」+ 代码位置（`app/xxx.py::func`，最好带消费方）
- 「**未实现**」+ 为什么（结构性不适用？还是待排期？——**这两者要分开写**，
  「v1 结构性不适用」不是「漏做」）
- 「**设计稿，未实现**」+ 显式警告行（"下面的流水线是目标形态，落地前不得当作现有能力引用"）

**替换时保留原文可追溯**：用 `（原：…）` 或引用块说明"旧稿曾写 X，那是设计设想"，
不要删干净——下一个读者需要知道为什么会有这个说法。

### 4. 判定「刻意不改」（否则会改出伪史）

| 情形 | 处置 | 理由 |
|---|---|---|
| `archive/**`、只读历史快照 | **不改** | 它是**当时**的快照；改它 = 伪造历史 |
| 阶段账本 / 里程碑表（带日期、含 strikethrough 的完成记录） | **保留阶段编号** | 阶段号在这里是**正向索引**（防重开发），不是时态词 |
| 设计稿正文里的阶段编号 | **改** | 会过期的时态词（见下方判据） |

**可复用判据（值得单独记）**：
> **阶段编号只能出现在「账本 / 历史」语境；一旦落进设计文档正文，就变成会过期的时态词。**

同一条判据也适用于「待办清单」：只活在**没人读的文档**里的待决项 = 不存在。

### 5. 发现「文档意图 ≠ 代码实现」时，先分清是 bug 还是口径

对账会撞见两种情况，**处置完全不同**：

- **代码按自己的设计工作，只是文档吹过头了** → 改文档，**不动代码**。
  判据：看模块自己的 docstring / 常量注释是不是明确写了这个定位（自述一致 ⇒ 文档错）。
- **代码确实没做到文档承诺的功能** → 这可能是**真实缺口**，也可能是**口径选择**。
  ⚠️ 若涉及行为变更（把一个"提示"变成"硬拦截"、改阈值、改拦截链），
  **属口径变更 ⇒ 先提后做，挂账待拍板，不要顺手改行为**。

### 6. 挂账 + 出口（**这一步不能省**）

- 在原权威文档就地更正当前陈述，保留历史身份；确需记录偏差类型时进入既有知识册，不建立平行状态表。
- **待决项必须有出口**：任务状态与调度元数据只归所属 stage，写清证据、owner、选项与代价；已完成工程成果不因旧报告游标重开。模块迁移同时核导航、业务能力、组件视图、阶段账本四边界及后台承接条件。
- 模型、工具链、产品语义或治理规则改变时，按 `docs/plan-registry.md` §1.1 核总方案、专题、INDEX、stage、AGENTS/Skills/handoff，更新或写“不适用+理由”。不自动写个人 memory。

### 7. 声明若由「守卫 / 门禁」背书 → **验机制，不只验事实**

对账撞见「X 已清零 / 已有守卫禁止 Y / 门禁会拦住 Z」这类**由某个检查机制背书**的声明时，
只 grep 事实**不够**——还要问一句：**这个声明是靠哪个机制成立的？那个机制能不能被 1 行等义写法绕过？**

> **实例（2026-09-12）**：台账写「`app/` 下 `date.today()` 已清零」，守卫
> `test_no_naive_date_today_in_app` 也确实存在且**全绿**。但对账时换个扫法发现
> `app/services/akshare_ext.py` 用 `from datetime import date as date_cls` + `date_cls.today()`
> ——守卫只匹配 `Name(id="date")`，**整条绕过**。于是「已清零」是**假结论**，
> 而**测试全绿反而让它更可信**。
>
> **教训：守卫漏检比没有守卫更糟**——它让口径分裂看起来已解决，后续没人再去看。

**AST / 文本守卫必查的等义写法**（挨个注入一遍）：

| 等价形式 | 例子 |
|---|---|
| import 别名 | `from datetime import date as date_cls` → `date_cls.today()` |
| 模块限定 | `import datetime as dt` → `dt.date.today()` |
| 间接调用 | `getattr(date, "today")()` |
| 再导出别名 | `from app.core.bjtime import beijing_today as today` |

处置两条，**都要做**：

1. 守卫改为 **AST + 解 import 别名**（解析 `ImportFrom` / `Import` 收集被绑定名，
   再匹配调用点），而不是匹配字面名。
2. 把注入验证**固化成常驻自证测试**——用**合成源码字符串**断言四种写法都被识别、
   并带**反例**（文档里"不要用 X"的教学文字不得误伤）。只在本地手动注入一次是不够的：
   下一次有人改守卫，没人会再手动注入。

> **判据**：一个守卫，若能用 1 行等义写法绕过，它就不是守卫，是安慰剂。

### 8. 门禁收尾

```bash
python3 scripts/doc-health.py      # 文档体检：死链 / 未登记 / 迭代项（exit 0 才算过）
```

- 若仓库有「扫文档内容」的测试（读 `docs/*.md` 做断言），**跑一遍这几个**——
  纯 `.md` 改动不必跑全量，但要跑会读 docs 的那些。
- 版本记录 / 变更日志的**插入位置**顺手核一下（新条目要排在最新处，
  这类"顺序错"是纯手工操作的高频失误）。

## 反模式清单

| 反模式 | 后果 |
|---|---|
| 只按文件名判断"这文档归哪一层" | 漏掉散在正文里的过期时态（同一文件往往一处准确、一处过期，自相矛盾） |
| 把「已完成阶段编号」当作错误全量清除 | 会删掉阶段账本的正向索引，反而让后来者重复开发 |
| 改了文档却把新数字/新计数写死 | 制造下一轮同样的问题（**指针式 > 写死**） |
| 发现"文档写的没实现"就顺手补代码 | 越过了「口径变更先提后做」的红线 |
| 只跑 doc-health 就宣布完成 | 它只查链接/登记，不查**语义是否与代码一致**——语义一致性只能靠步骤 2 的 grep |
| 凭单一空搜索下结论 | 忽略规则、词边界、别名和动态注册可能造成假阴性 |
| 见守卫全绿就认下「已清零」 | 守卫可能只匹配字面名，`as` 别名/模块限定即可绕过 ⇒ **假绿**，且比没有守卫更误导（见步骤 7） |
| 把「清单里的数量」当事实 | 「~15 处待改」实测往往只有 1 处；清单是写方案时的印象，**先实测再引用，且注意它两个方向都会失真** |
| 见「生产 0 处使用」就去补调用点 | 计数可能属实，但**入口压根没暴露**（capability gap）⇒ 修错地方。先 grep 入口本身（prop / 参数 / 开关）存不存在 |
