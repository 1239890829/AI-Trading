# 外部工具引入评估（核验 → 对照 → 分层结论）

**核心纪律：默认答案不是「可以引入」，而是「先证明它比现状更好，且不触碰红线」。**
产出物是**分层结论 + 每层的判据与代价 + 触发条件**，不是功能介绍。

## 0. 先分辨用户给的是「参考输入」还是「规范」

用户丢来的仓库/方法论**只是示例**，不得直接替代既有体系（本仓既有纪律：参考输入 ≠ 既有体系；
示例 ≠ 规范）。评估=理解后自行判断，不是照搬。

## 1. 第零步：事实核验（跳过此步的下场 = 在错误前提上写一整篇）

| 要核验 | 怎么核 |
|---|---|
| **系统是否已经在用**？ | 全仓 grep 产品名/库名（含大小写变体）。**很多"引入评估"实际是"已在用，只是要升级"** |
| 当前用的版本与许可 | 读 `package.json` / `requirements*.txt` / `LICENSE`；Apache-2.0 与 MIT 都可能有"仅限源码、不授予数据权利"的限定 |
| 上游最新版 | 查 changelog，**重点找 breaking changes**，不要只看新功能 |
| 它的**硬前提** | 付费订阅？桌面应用？特定端口？私有 API？OS 限制？——前提不可得则后面全不必谈 |
| 它用**官方 API 还是未文档化接口** | 后者 = 随时 break + 合规风险，且通常无 SLA、无时间戳契约 |

## 2. 第二步：三条对照（任一条不过即排除，不必再算收益）

### 2.1 项目红线对照
逐条读项目自己的红线清单（本仓 = `AGENTS.md` §0）并**显式写出触碰了哪条**，例如：
- 「禁止把过期/替代数据冒充实盘」→ 该源**有无时间戳与质量档**？能否满足 `Freshness` 契约？
  拿不到时间戳的数据**无法**进推送与评分链路。
- 「禁止输出确定性买卖结论」→ 仓库是否**明令禁止**"据其数据做自动决策"？若是，接进决策面即违规。
- 「API Key 只存 .env」→ 它是否要求把凭据写进前端/文档/配置库？

### 2.2 既有体系对照
**能力重叠度**：列出它的能力类别，逐条问"本系统有没有、谁在做"。
**重叠度高而互补度低 ⇒ 引入 = 增加第二套口径**（最坏的情况：同一指标两个来源、两套语义）。
**正交而非互补**是排除的最强理由——它解决的是另一个问题。

### 2.3 量化迁移/替换成本
**不要凭印象说"改动很大"**，实测三个数：
1. **消费方文件数与行数**（`grep -rl` + `wc -l`）
2. **破坏性 API 命中数**（逐个人工点名 grep，别用模糊计数）
3. **会被重置的既有稳定性资产**——围绕旧版调出来的闪烁/性能/主题修复，
   升级后**需要重新验证**，这部分成本最容易漏算。

> ⚠️ 计数坑：管道 + `tail/head` 会让 grep 提前收到 SIGPIPE 而 exit 137，**输出被截断但不报错**。
> 计数一律单独跑、核对退出码。

## 3. 第三步：分层结论（三档，不要只给"是/否"）

| 档 | 成立条件 | 必须附带 |
|---|---|---|
| **纳入** | 补齐真实能力缺口 **且** 不碰红线 **且** 成本可承受 | 落地路径 + 验收判据 |
| **排除** | 触碰红线 / 前提不可得 / 能力正交 / 收益 < 代价 | **写清是哪一条，逐条独立成立**（任一条单独即足够） |
| **缓议** | 有价值但当前收益不对价 | **触发条件**（什么情况下重议）+ 届时的前置动作 |

**「缓议」不是「不做」**——必须写触发条件，否则下次会被当成新议题重新评估一遍。
**决策③往往才是真正的正路**：评估外部工具时，常会发现"把本系统自身能力开放出去"
（如本项目既有 P2-10/P2-13 的 MCP 工具面）比引入外部工具更贴题 ⇒ **指向既有账本条目，不另立项**。

## 4. 落笔位置（重要：不要新建文档）

本仓有明确纪律——**不为评估结论新建文档**。按四步走：

1. **精华进已有分类文档**：结构性决策 → `docs/kb/04-decisions.md`（KB-DEC 追加，含
   日期/决策/依据/代价/**重议条件**）；工程机理 → `docs/kb/03|09|10` 对应册；数据源对比 → `docs/data-source-comparison.md`
2. **未做项/缓议项进** `docs/retro-and-gaps.md` §六（唯一待办账本）
3. **登记索引**：`docs/kb/00-INDEX.md` 加一行摘要（含判据与状态列）
4. **收尾跑** `python3 scripts/doc-health.py`（B 死链 / C-KB 条目 ≤60 行 / F3 指针错册）

## 5. 自检（写结论前逐条过）

- [ ] 我核验了"系统是否已在用"，而不是假设它没在用吗？
- [ ] 我写的是**它能不能用**，还是**它比现状好在哪**？（后者才是用户问的）
- [ ] 「排除」的理由是**多条独立的**吗？还是同一条换了三种说法？
- [ ] 「缓议」写了触发条件吗？
- [ ] 引用 KB / 账本编号**grep 核验过**吗？（引用错编号比不引用更糟）
- [ ] 文中所有数字是**当轮实测**的，还是记忆中/文档里抄来的？（数字最容易失真，
      尤其"XX 项来自 YY"这种**整数分解**——加起来不等于总数就说明有漏项）

## 7. 已应用实例（回顾用，不要照抄结论）

  v4 上的闪烁与主题不重建修复）；正路 = 指向既有 MCP 工具面条目。
