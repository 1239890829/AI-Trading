# 守卫注入验证（识破假绿）

**问题**：新增守卫后测试全绿，**不能证明守卫有效**——可能只是没有测试覆盖到它。
"守卫存在且全绿" ≠ "守卫被钉住"。假绿比没有守卫更危险：它让一个未被验证的口径
看起来已经验收完毕，日后有人放心依赖，而守卫一旦被无意改坏，门禁不会响。

**解法**：**逐条注入破坏 → 确认"精确变红" → 复原**。精确 = 红的恰好是该守的测试，
其余全绿。若注入后**没红**，说明守卫不可观测 ⇒ 要么修守卫的位置，要么修测试的数据。

## 标准流程

```bash
# 0. 先确认基线全绿，并记住总量
pytest <目标文件> --basetemp=/tmp/bt     # 记下 "N passed"

# 1. 注入：把守卫改成恒真/恒假（最小改动，不要顺手重构）
#    例： if len(x) >= MIN_SAMPLES:      →  if len(x) >= 1:   # INJECTED

# 2. 跑，只看两件事：红的条数 + 红的**是不是预期那条**
pytest <目标文件> --basetemp=/tmp/bt -k "<相关关键字>"

# 3. 复原（务必用 Edit 精确改回，不要 git checkout 整文件——会连带丢掉其他改动）
```

**每轮只注入一处**。多处同时注入时，"精确变红"无法判断是哪处生效。

## 判读结果

| 结果 | 含义 | 处置 |
|---|---|---|
| 恰好预期那条红 | ✅ 守卫被钉住 | 复原，继续下一处 |
| **一条都没红** | ❌ **假绿**：守卫不可观测 / 注入打偏 | 见下方各条成因与两条「自我坑」 |
| 红了一大批 | ⚠️ 守卫被过度耦合 | 检查是否与其他机制混在一个条件里 |
| **红的恰好是同一文件的 N 条登记项** | ✅ **预期形状**（不是耦合）：文件级断言被该文件多条条目共用 | 判读看**报出的行**而不是条目数；把"N 红是预期"写进 docstring |
| 红的是别的测试 | ⚠️ 测试断言写偏了 | 断言测的不是你以为的东西 |

### 自动化自证脚本的读数纪律（把上表交给脚本时）

把上面的判读**写成脚本**自动跑时，读数是新的假绿来源——脚本会替你看输出，看错了你也不知道：

- **必须关色**：`NO_COLOR=1`（并顺手 `strip_ansi()` / `-p no:cacheprovider` 之外的 `--color=no`）。
  颜色码会插在 token **之间**，尤其**跨状态的分隔处**——真输出可能是
  `3 passed\x1b[0m, \x1b[31m2 failed`，于是 `"passed, 2 failed"` 这类**跨段模式静默不匹配**
  ⇒ 脚本报「注入后没变红」，**但其实是脚本没看见**（假阴被读成"守不住"）。
- **判据取「精确条数 + 点名」，不要取子串**：`failed >= 1` 会把"红了一大批"（过度耦合）
  也判成通过；正确形状是 **恰好 N 条** 且**逐条点名**到预期用例/预期断言行。
- **没红与没看见要分开报**：脚本输出应能区分「跑了、0 条红」与「没跑到 / 输出没解析出来」，
  否则解析失败会被读成"守卫不可观测"，然后你去改守卫（改错地方）。

### 判据分散在多个文件时：**每条注入自带它该跑的测试**

同一个口径的守卫常常落在**生产者的适配层**与**两个消费方**三个文件里
（2026-09-16 `IMP-038`：`tdx_tick.py` + `tools/market.py` + `api/routes/market_quotes.py`）。
此时脚本若写一个全局 `TESTS = ["tests/test_xxx.py"]`，**后两个文件的注入会全部漏跑**
——脚本照样打印"✅ 判红"，因为它在**另一个文件**里跑红了。这是**脚本自身制造的假绿**。

**处方**：`INJECTIONS` 的每条改成
`(标签, 相对路径, 原文, 注入后, 该跑的测试文件, 必须命中的关键字)` —— **测试跟着注入走**。
并给脚本加 `--backend-only` / `--frontend-only` 开关：前后端自证混在一个脚本里时，
要能**拆开跑**（否则与"两道全量不并发"的纪律冲突，且前端那半会拖慢整轮）。

**另一条**：注入的**锚点**要选**它自己**，不要选相邻的别的东西。
`IMP-038` 踩过两次：① 注入 `size_want = want` 会让**快路径**先红，命中的不是想验的分页用例
（且 `-x` 提前停止 ⇒ 后续用例根本没跑）；② `needle` 写成函数名，而 `-x` 让它先命中别的用例。
⇒ **`needle` 用完整用例名**，并**去掉 `-x`**（要的是"恰好这些红"，不是"第一个红就停"）。

## 九类假绿形态（成因 1~9，都是真实踩过的）＋两类「注入自身」的坑

> ⚠️ **加条目时顺手核对本行计数**：标题里的「九类」与下面「成因 N」的最大编号必须一致
> （历史踩过：条目加到 6 条、标题还写"五类"）。**计数类标题与交叉引用要一起改**。

### 成因 1：守卫被另一个条件**隐含** ⇒ 不可观测

```
ratio_line = max(p95, FLOOR)          # FLOOR = 0.02 > 0
...
hit = (dr > 0) and (dr >= ratio_line) # ← 这个 dr > 0 永远为真（被 floor 隐含）
```
删掉 `dr > 0`，测试全绿——因为 `ratio_line >= 0.02` 已经蕴含 `dr > 0`。

**修法**：把要求**上移到它真正生效的那一层**，并让它在该层可观测：
```
line = max(p95, FLOOR)
ratio_line = line if line > 0 else None   # ← 不变式放这里
hit = ratio_line is not None and dr >= ratio_line
```
顺带堵住一个暗雷：`FLOOR` 若被调成 0，原写法会 **除零崩溃**（注入时真的崩了）。
**不可观测的守卫往往同时也是错误位置上的守卫。**

### 成因 2：测试数据让两种语义**不可区分** ⇒ 测不出来

```
# 想验证"unknown 绝不当 0"，但构造的数据里正常值也是 0.0
boards = {f"板{i}": {"ratio": 0.0} for i in range(60)}
del boards["板0"]["ratio"]      # 缺值
# ⇒ "缺值"与"值为 0"算出来一样，把 unknown 当 0 也不会红
```
**修法**：把基准值**抬离触发点**，让两种语义产生不同结果：
```
boards = {f"板{i}": {"ratio": 1.0} for i in range(60)}   # base=1.0
board_0 = {"ratio": 5.0}                                  # 缺值板块取非零
# 现在"当 0"会算出 +5.0（多一条样本）⇒ 注入立刻红
```

**一句话**：**测试自身的可观测性也要验收**。断言的两个分支必须能被数据区分开。

### 成因 3：桩**缺方法**被 `except` 吞掉 ⇒ 旧实现照样全绿

改造「N 次单查 → 1 次批量」时最常见的陷阱：新实现调用 `svc.bulk(...)`，而测试桩里
**没有** `bulk` 方法 ⇒ 抛 `AttributeError`；如果调用点在
`try: ... except Exception: log.warning(...)` 里（很常见，因为它本来就在做降级兜底），
**异常被吞掉，测试全绿** —— 于是你**把实现改回旧的逐只 N+1，测试依然全绿**。

> 关键认知：**"桩里没这个方法"不构成守卫**。你以为"改回旧写法会 AttributeError 变红"，
> 实际是"改回旧写法 → 异常 → 降级分支 → 断言照样通过"。
> 这是"成因 1（被隐含/被吞掉）"的变体，但更常见、更隐蔽，且**换一个 API 就复发**。

**修法（三件套）**：

1. **桩里同时提供新旧两条路**，并给它们**装计数器**（看次数，不看行为）：
   ```python
   def get_members(self, code):      self.member_single_calls += 1; ...
   def member_symbols_bulk(self, codes): self.member_bulk_calls += 1; ...
   ```
2. 断言**"新路恰一次 + 旧路恰零次"** —— 这一条对"异常被吞"完全免疫，因为计数不会骗人：
   ```python
   assert cat.member_bulk_calls == 1, "必须走一次批量查询"
   assert cat.member_single_calls == 0, "不得逐项单查"
   ```
3. **再加一条"未走异常兜底"的断言**：若只断言次数，而兜底逻辑把异常吞掉后改成
   "另一条路径也满足次数"，次数断言同样会失效。捕获 warning 列表并断言为空：
   ```python
   assert not [w for w in warnings if "bulk failed" in w], "批量取数被异常兜底了"
   ```

### 成因 4：A/B 等价对照**覆盖不到"共用的判据本身失效"**

重构常写这类守卫：`assert bulk == {s: single(s) for s in syms}`（批量版与逐只版结果相等）。
它足够钉住"两路实现漂移"，但**钉不住两路共用的那个判据本身是错的**：

```
bulk  ─┐
       ├─→ 共用 override_still_active()   ← 把它改成恒 True，两路一起错
single ─┘                                  → bulk == single 照旧成立 ⇒ 全绿
```

> 实测：把共用判据改成恒 `True`（过期 override 也生效）后，`bulk == single` **依然通过**。
> 只有那条**单路绝对结果断言**（`assert bulk["600303"] == []`，即"过期必须不生效"）会红。

**修法**：凡"两路共用同一判据/同一常量"的重构，守卫**必须两层齐备**：
- (a) **A/B 相等** —— 钉住"两路不漂移"；
- (b) **单路绝对结果** —— 钉住"判据本身正确"。

只有 (a) 时判据坏了测不出；只有 (b) 时两路漂移测不出。

### 自我坑：**"注入"变了注释，没变行为**

给自己的守卫注入时，写下一行 `return None  # INJECTED` 却**只加了注释、没动代码**——
当然照样全绿，差点误判成"守卫覆盖不到"。

> **注入的定义是"让行为可观测地错"**。加注释、改日志、改变量名、改一个未被读取的字段，
> **都不算注入**。验收标准永远是同一句话：**精确变红（只有目标用例失败，条数对得上）**。

**一句话**：**先问"我到底改了什么行为"，再跑测试。**

### 自我坑 2：注入**打偏了**——替换串是**另一处的子串**

用脚本做注入（`text.replace(old, new, 1)`）时，若 `old` 在文件里**先于**目标位置
出现在**别的标识符内部**，替换就会落到那处 ⇒ 目标行为**根本没被改** ⇒ 跑出全绿，
你会得出"守卫无效"的**错误结论**（而守卫其实是好的）。

真实案例：想破坏 `ANCHOR_ALLOW: dict[...] = {`（J 项名单），但文件更早处有
`STALE_ANCHOR_ALLOW: dict[...] = {`——**前者是后者的子串**，`replace(...,1)` 命中了后者。
结果：J 项名单原封不动 ⇒ 测试全绿 ⇒ 一度误判"守卫无效"、甚至怀疑是沙箱写入不落盘，
**多绕了好几轮**。

**修法（两条，缺一不可）**：

1. **注入串必须带唯一上下文**——含上一行（注释/签名）或把 `old` 写成**整行含换行**；
   最稳的是直接**用 Edit 工具**（带上下文匹配，重复即报错），不要用 `replace`。
2. **注入后校验"落点"**，不是"字符串在不在"：
   ```python
   assert old in orig                       # ← 不够：子串恒成立
   text = orig.replace(old, new, 1)
   assert new in text                       # ← 也不够：新串可能出现在别处
   # ✅ 要校验**变异落在目标行**：
   assert target_line_no in [i for i, l in enumerate(text.splitlines(), 1)
                             if l.startswith(expected_prefix)]
   ```
   更省事的版本：注入后 **`sed -n '<行号>p'` 打印那一行**确认。

> 同族陷阱：`new in text` 这种子串检查会被**自身**蒙蔽（新串恰好也是别处的子串）。
> **校验要盯"位置"，不要盯"存在"。**

### 成因 5：注入**确实改了行为**，但测试的**观测范围**盖不到那条路径

第四类假绿的镜像：不是守卫不可观测，也不是注入假动作，而是**测试的比较范围天生盖不住
这个注入**。真实案例（`to_thread` 守卫的自证用例）：

```python
# 想证明"字符串里的 to_thread( 不算已包裹"
SRC = '''
x = "to_thread(fn)"      # ← 字符串在**另一行**
y = to_thread(fn)        # ← 裸调用
'''
# 守卫实现只看**同一行**前缀，判断"这行调用是否位于 to_thread( 之后"
# ⇒ 字符串在与不在，这一行照样判定为"裸调用" ⇒ **掩不掩码都通过**（等于没测到）
```

把它改成**同一行且在调用之前**（`x = "to_thread(fn)"; y = to_thread(fn)`）后，注入才真的变红。

> **排查顺序（三步，不要跳）**：
> ① 我到底改了什么行为？（最常见）
> ② **测试覆盖到这条路径了吗**——字符串/数据/代码位置的**相对关系**是否让两种情形不可区分？
> ③ 才是"守卫不可观测"。
>
> 顺序理由：①②都在你手上（改测试即可修），③往往要重设计守卫。先做便宜的排除。

**修法**：把注入做成"该断言**看得见**的形态"——改变**两者的相对位置/顺序/所在行**，
而不是只改值。验收判据 = **这样改之后仍然变红**。

### 成因 6：守卫的**判定面**被"本地有、CI 没有"的文件喂绿（本地绿 / CI 红）

守卫问的是「这个资产**在仓库里**还在不在」，而它用来回答的清点是**本地文件系统**
（`os.walk` / `glob` / `Path.rglob`）⇒ 凡是**本地有、git 不跟踪**的文件都能"救活"一个死引用。

真实案例（2026-09-12，`scripts/doc-health.py` 的 J 项）：

```
os.walk 清点 10409 个 basename   vs   git ls-files 只有 999 个
其中后缀受检、真能"伪造通过"的 7 个；实际遮盖 1 处 ⇒ 本地全绿、CI 判红
```

**为什么它会长期隐身**：遮盖者常常正是**本该消失的副本**——
本仓 tracked/独有资产的删除纪律要求进入 `artifacts/trash/`（gitignored），
于是**越守纪律，门禁越假绿**；而那条"在真实仓库上跑一遍"的守卫测试
**在本地是瞎的**（它读的也是 `os.walk`）。

**修法（结构性，不是补丁）**：
```python
def repo_basenames():
    tracked = tracked_via_git()          # git rev-parse --show-toplevel 先验 + git ls-files -z
    if tracked is not None:
        return tracked                   # ✅ 判定面 = CI 检出的内容（按定义相等）
    return walk_fallback()               # 无 git 环境才回退
```
**不要**靠往"跳过目录"表里补条目修这个问题——那是**枚举**（补了某个本地状态目录，
明天还有 `data/`、`logs/`），"跟踪清单"是**定义**。

> **通用判据**：凡守卫的判定依赖"某文件/目录存在与否"，先问一句——
> **"在 CI 的干净检出里，它还在吗？"** 不一致 ⇒ 这条守卫**必然**产生本地/CI 分歧，
> 且分歧方向永远是"本地更绿"（本地文件是 CI 的超集）。
>
> **附带一笔**：这类缺陷还会同时污染**结论行**。本轮 doc-health 的汇总行写死了
> 「（C 的日志单轮 ≤80 行属过程指标…）」，失败项是 J 时被读成"C 项待处理"，
> 排查方向直接跑偏 ⇒ **汇总行必须由实际结果派生，不得写死任何单项描述**。

## 源码级守卫（文本扫描类）的构造要点

守卫的对象若是"代码里不许出现裸调用"这类**源码文本**，用**正则扫描注释与字符串**会同时
**误报**（把解释性文字当调用）与**漏报**。三条约束缺一不可：

1. **用 `tokenize` 掩码，不要用正则**：正则处理不了 `#` 出现在字符串里、三引号跨行 docstring。
   把注释与字符串字面量替换成**等长空白**。
2. **行号必须守恒**：单行 token 原地等长替换；多行字符串的中间行只保留换行符。
   ⚠️ **两套坐标系分工**：掩码后文本**长度会变** ⇒ **行列号在掩码文本上算、
   回报时取原文那一行**。混用会让失败信息"指错行"，比不报更误导。
3. **前缀判断（"是否已被包裹"）也必须走骨架**：否则**字符串里的** `to_thread(` 会被当成
   "已包" ⇒ **漏报**（比误报危险得多——它让守卫静默失效）。
   **正向 needle 用原文**（它要证明的就是"代码里有这行"），**反向断言只在骨架上做**。

> ⚠️ **误报的失败信息也是一种缺陷**：本轮守卫假红时报的是「存在**未被 `to_thread` 包裹的调用**」，
> 而命中的是一句**解释这条守卫的 docstring**——与事实不符。后人照着这条信息做，
> **会去删掉那段正确的说明文字**。修守卫不是"改文本绕过"，是修真缺陷。

**失效条件**：源码片段的**语法不完整**时 `tokenize` 抛 `TokenError`/`IndentationError`
⇒ 退回纯文本扫描（**刻意选严，严 > 漏**），此时注释里的提及会误报。
回退路径**也要有测试**，且判据要能**证明**回退真的发生了（取"既有注释、又语法不完整"的源，
断言注释**原样保留**）——只断言返回值相等是假绿。

### 成因 7：守卫的**匹配面过宽** ⇒ **假红**（误报），会逼你去做错误的改动

与成因 1~6 方向相反：那六类是"该红不红"，这一类是"不该红却红"。**假红的危害不亚于假绿**——
它不让你漏掉缺陷，但会让你**改错地方**（把合法代码改成违例的样子）。

**两个真实形态**（2026-09-12，给"事件循环阻塞守卫"加路由层条目时连红两次）：

1. **只写方法名 ⇒ 命中同名方法**：条目写 `fn="list_events"`，而仓内另有
   `AlertRepository.list_events`（实测 0.36ms、**刻意不搬**）⇒ 另一个文件立刻假红，
   差点去包一个毫秒级调用。**修法 = 判据带接收者**（`fn="store.list_events"`）。
   💡 **可用的语法事实**：`to_thread` 传的是**函数引用**（`to_thread(store.list_events, …)`
   **不含 `(`**）⇒ 该字面量**只命中裸调用**，既不会把已包的算成未包，也不会自match。
   **收窄匹配面时先找这类"结构性事实"，比加白名单可靠。**
2. **不区分上下文 ⇒ 命中合法实现**：某同步 helper（模块级 `def`）体内有
   `repo.list_events(...)`——那**本身合法**（它不占事件循环）；真正的违规在**调用它的 async 端点**，
   是**另一层**的问题，纯文本扫描表达不了。**修法 = 让守卫能表达上下文**（如加 `async_only`：
   用 `ast` 取 async 函数体行号集合、**并减去其中嵌套的同步 def**）。
   ⚠️ 语法不完整时返回 `None` ⇒ 退回"不过滤"（严 > 漏），不要静默返回空集（那会变成假绿）。

**通判**：**"该不该守"是调用点的属性，不是被调函数的属性。** 同一个方法，在 A 处要守、
在 B 处不该守 ⇒ 守卫判据必须能表达位置/上下文。

**配套自证测试**（至少四条）：假阳性定点（合法的同步 helper 不被报）+ **正向对照**
（async 体内照抓，防"一律放过"）+ 嵌套同步 def 不算 async 上下文 + 语法不完整返回 `None`。

**失效条件**：被守对象在仓内有**多个同名方法**、或**同步实现本身就是合法的另一层**时，
纯方法名判据必然误报。此时不要靠"加白名单"消音（名单会腐烂），要收窄到**带接收者/带上下文**。

### 成因 8：守卫的**驱动形态**决定敏感度——宿主/框架的**外部取消会顺手跑掉同步清理**

判据没错、注入也真的改了行为，但**这条用例是被谁驱动结束的**决定了它能不能看见缺陷。

真实案例（2026-09-14，R24）：修的是「WS 收发两条任务的生命周期绑在一条上」
（旧实现 `await writer()`）⇒ reader 先结束（客户端断开 / 意外异常）时 writer 永久 parked、
清理函数 `hub.unsubscribe` **永不执行**。写了一条 `TestClient` 形态的
`test_client_disconnect_unsubscribes_...` 当判据，**注入旧实现后它仍然全绿**：

```python
# Starlette WebSocketTestSession.__enter__：ExitStack 按 LIFO 执行
stack.callback(fut.result)                       # 3
stack.callback(portal.call, cs.cancel)           # 2  ← 外部取消
stack.callback(self.close, 1000)                 # 1  ← 先跑
# ⇒ cs.cancel() 只"在下一个挂起点抛异常"，而 finally 里**同步**的清理语句照常执行
# ⇒ 旧实现与正确实现在这条用例上**表现完全一致**
```

**修法：两种驱动形态各司其职，缺一不可**

| 形态 | 验什么 | 能看见什么 |
|---|---|---|
| `TestClient` / 端到端 | 对外契约（协议往返、脏帧不杀连接、建连即注册） | **看不见**"是否自行收尾"——宿主会替你收 |
| **直接驱动被测协程**（`asyncio.wait_for(fn(fake), timeout=…)` + 最小替身对象） | "收尾必须**自行**发生" | 没有外部取消 ⇒ 旧实现就是**永不返回**（超时） |

同一注入下二者的期望集合**天然不同**：I4（还原 `await writer_task`）⇒ `{T_ERR_LOGGED, T_READER_END}`，
**不含** `T_DISCONNECT`。把"为什么某些用例**不在**集合里"写进注入脚本 docstring，否则后人以为漏了。

**同轮第二发现（同源）**：清理路径**含 `await`** 时，被取消的任务在首个挂起点立刻重抛
`concurrent.futures._base.CancelledError`（经 `fut.result()` 冒出来）⇒ **全部 5 条**走会话退出的
用例一起红，而清理**被整段跳过**（生产侧 = 客户端断开时订阅实际未注销，是真实脆弱点）。
固化实现：`asyncio.gather(...).add_done_callback(report)` + **同步** unsubscribe，**收尾零 await**。

**判据**：写守卫前先问一句——**「这条用例是被什么驱动结束的？宿主会替它跑掉哪部分代码？」**
**被宿主替你跑掉的那部分，就失去了被验证的资格。**

**失效条件**：被测逻辑的收尾是**异步**的（含 `await`）时，"宿主取消"与"自行收尾"在行为上更难区分，
此时更要靠直接驱动；若被测协程本身依赖宿主提供的 context（如真实的 ASGI server），
直接驱动需要替身足够完整，否则会退化成"测替身"。

### 成因 9：守卫的**候选集合为空** ⇒ 判据恒真，「没命中」被读成「通过」

2026-09-16 `GOV-015`（账本档位一致性守卫）实测。判据形如「**某个 ID 不在集合 X 中 ⇒ 通过**」：

```python
stale = [i for i in open_stage_ids if i in closed_ids]   # 未完成档里不该出现已闭环的
if stale: report(stale)                                  # 集合为空 ⇒ 永远不报
```

**当 `closed_ids` 本身为空**（F 档还一条记录都没有、或解析面失效只读到 0 条）时，
`stale` **必然为空**、守卫**恒绿**——**它看起来在工作，实际什么都没守**。
这类"空集合 ⇒ 通过"的形态**不会自己暴露**：注入（把缺陷塞回去）时若集合恰好非空，注入会红，
于是自证**通过**、你判定守卫有效；**换个时刻**集合为空，同样的注入就不再红。

**修法 = 保险丝（fail-loud），且判据与冲突分开返回**：
- 判定面为空（集合长度 0 / 关键小节缺失 / 目标文件缺失 / 档标题形态认不出）⇒ **判红并说明**，
  不许 `return []` 静默通过。**"守卫找不到判定面"比"没有守卫"更糟**——后者你知道它不存在。
- 返回值用**独立字段**（如 `(冲突列表, 保险丝说明)`）承载保险丝，**不要塞进冲突列表**——
  否则调用方无法区分「保险丝触发」与「发现冲突」，报告的修法方向会完全不同。
  ⚠️ 该元组做**中性打桩**时保险丝位必须写 `None` 而非 `""`：
  `bool("") is False` 会让「未触发」与「中性打桩」在调用方不可区分。

**注入自证的配套要求（否则自证本身也是空的）**：注入 [A] 之外，
必须再注入 **[B] 把判定面清空**（如删光 F 档记录）并确认它**红**。
只注入"A 能被抓到"证明的是**集合非空时**的空有；**集合为空时它还能不能红**才是真问题。
⚠️ **在多副本形态上注入，务必先确认「多副本已收边界」**：
本次实测第一版守卫**未在相邻小节处收扫描边界**，把紧随其后、**形态完全相同**的索引表
也当成了记录源 ⇒ 索引里每个 ID 都进了闭环集合 ⇒ **假红**（把 `RSH-026` 误判成「已闭环未销账」）。
**形态相同、相邻排布的多份副本，是"匹配面过宽"最容易发生的现场**（成因 7 的同族）。

## 三态守卫的额外检查

带 `None` / unknown 的守卫要**三向**注入，不要只注入一个方向：

- 上游缺值 → 是否被当成 0 / 被当成"通过"？
- 上游有值但为 0 → 是否被当成缺值？
- 样本不足（分位数、均值类判据）→ 是否照常启用（拿小样本装判据）？

## 归因争议：用「对照跑」定案，不要靠推理

**症状**：门禁有红，但你**说不清是不是本轮引入的**（本轮只动了别的东西 / 只加了文档 /
红的是个超时类偶发）。此时靠"看起来无关""应该是环境问题"下结论 = 推理代替观察。

**做法（一次对照跑定案）**：

```bash
# 1. 把本轮的**增量**临时移出工作区（新增文件 + 改动文件用副本替换亦可）
mv <本轮新增文件A> <本轮新增文件B> /tmp/ctrl-out/

# 2. 复跑**同一条**门禁命令（原样，不要改参数、不要放宽阈值）
<与失败时逐字相同的命令>          # 记下：失败条数 / 用例名 / 失败文本 / 耗时

# 3. 还原，并**逐字校验**还原无遗漏
mv /tmp/ctrl-out/* <原位>
shasum -a 256 <涉及文件>          # 或 git status --short 应只剩预期的未跟踪项
```

**判读**：

| 对照跑基线 | 结论 | 处置 |
|---|---|---|
| **同样红**、同一用例、同一失败形态 | **非本轮引入**（既有问题） | **不要改本轮的代码去"修"它**；把证据补进对应账本行 |
| 全绿 | **本轮引入** | 必须定位到具体改动，修完再跑 |

**配套的两条硬要求**：

- **增量必须自洽**：`新总数 − 基线总数` 要**恰好等于**本轮新增用例数
  （实测例：`597 − 592 = 5`、文件数 `66 − 65 = 1`，与新增 5 条 / 1 文件逐字相符
  ⇒ 可断言「新增的 5 条全部通过」）。对不上就说明有别的变量在动。
- **不许放宽判据 / 调阈值 / 加 skip 来求绿**——放宽只是把问题藏起来。对照跑之后还要问一句
  **「判据与它的目标是否错位」**（实测例：某用例意在抓"渲染死循环"，而同文件注释明确记录
  真死循环的表现是**挂死**而非变红 ⇒ 5s 超时**抓不到它要抓的缺陷**）。**这属于应当提给用户的
  判据改进，而不是本轮可以顺手改的东西。**


- [ ] **"没红"按三步排查**：①我到底改了什么行为（只加注释/改日志 ≠ 注入）
      ②**测试覆盖到这条路径了吗**（相对位置/顺序让两种情形不可区分）③守卫不可观测。
      跳过第 ② 步最常见的后果是——把成因 5 误判成"守卫不够狠"，然后去加严守卫（改错地方）。
- [ ] **注入后校验落点**（不是"字符串在不在"）：`sed -n '<行号>p'` 打印目标行确认改对了。
      替换串若可能是别处的**子串**（`X` ⊂ `STALE_X`），必须带唯一上下文或改用 Edit 工具
- [ ] **守卫的判定面 = CI 的干净检出**：凡依赖"文件/目录是否存在"的守卫，
      清点来源若是本地文件系统（`os.walk`/`rglob`）而 CI 只检出 git 跟踪文件，
      就必然"本地绿 / CI 红"——改用 `git ls-files`（无 git 环境才回退）
- [ ] **判定面会不会为空？**（成因 9）凡判据形如「不在集合中 ⇒ 通过」，先证集合非空；
      空集合 / 小节缺失 / 档标题形态认不出 ⇒ **判红**，并**单独**返回保险丝说明
- [ ] **同一形态的副本相邻排布时，扫描有没有显式收边界？**（成因 9 尾段）
      在相邻小节/下一张同形态表处 `break`，否则"下一份"会被算进"这一份"
- [ ] **复原后 grep 注入标记**：`grep -c "INJECTED" <改动文件>` 必须为 0
- [ ] 复原后再跑一次全绿（确认没改坏）
- [ ] 把"注入后没红"这件事**写进注释/提交信息**——它比"成功了"更有交接价值
- [ ] 若因为找不到可观测点而放弃某条守卫，明确标注它是"不可观测"，不要留着装样子
- [ ] **"收敛 N 次查询为 1 次"类重构**：桩里配上**调用计数**，断言"新路恰一次 + 旧路恰零次"
      **且未走异常兜底**（否则 `except Exception` 会让次数断言也失去意义）
- [ ] **新增守卫的测试文件本身要过项目自己的门禁**（文档/引用/命名检查会把测试里的
      合成文件名、示例路径当真实指针报红）——登记例外时要写清"这是合成名 + 谁在覆盖真实面"
- [ ] **按"文件"判的反向断言要预告预期形状**：同一文件有多条登记项时，注入一处会**同时红 N 条**。
      把它写进 docstring，否则下一轮会把它误读成"守卫过度耦合"（见判读结果表）
- [ ] **收窄匹配面之后要重跑召回**：把判据从 `fn` 收成 `recv.fn` 可能让**真裸调用**也不再命中——
      用一个"真裸调用"的正向对照确认它照旧被抓（与"正向 needle 仍在"是两件事）
- [ ] **写守卫前先问「这条用例是被什么驱动结束的」**：若收尾逻辑可能被**宿主/框架的外部取消**
      顺带跑掉（`TestClient` 会话退出、`CancelScope`、GC、`close()`），则这条用例**看不见**
      "是否自行收尾" ⇒ 必须再补一条**直接驱动被测协程**的守卫（见成因 8）
- [ ] **期望集合要写下"为什么某些用例不在里面"**：同一注入下不同驱动形态的敏感度不同，
      不写清楚，下一轮会被当成漏项去"补"（然后引入假绿）
- [ ] **自证脚本关色了吗？读数取的是精确条数还是子串？**（见上方「自动化自证脚本的读数纪律」）
      脚本报"没变红"时，先排除"脚本没解析出来"，再怀疑守卫
- [ ] **出现说不清归属的红 ⇒ 跑一次对照跑定案**（移出增量 → 同命令复跑 → 还原 + 校验），
      并核对**增量自洽**（总数差 = 新增用例数）。**禁止**用放宽判据/调阈值/skip 求绿

## 常见坑

- **别用 git checkout 复原**：目标文件常同时含本轮其他改动，整文件回滚会一起丢掉。
  用 Edit 精确改回（并 grep 确认无残留）。
- **注入要最小**：改成 `>= 1`、`and False`、删掉一个 `and` 子句即可。
  顺手重构会让"红了"归因不清。
- **相关关键字要选对**：`-k` 选太宽会跑很久且噪音多；选太窄可能漏掉该红的测试。
  拿不准就整文件跑（通常很快）。
- **新写的自证测试第一次就红 ⇒ 先怀疑「我的预期」，再怀疑代码**（2026-09-13 实测）：
  给"表格分隔行"检查器写的 `test_hr_line_is_not_a_delimiter` 首版断言 `[1]`，实测 `[1, 3]`——
  **代码是对的**（`---` 会**断开** `|` 块，第 3 行因此是新块首行、同样不成表），
  是我对判据的**块切分语义**理解不到位。
  判据是**按设计写死**的，测试是**照着脑子里的模型**写的 ⇒ 两者冲突时，先回头读判据的实现。
  处置：**不要改代码去迁就预期**；把预期拆成两条（一条测"`---` 不是分隔行"、
  一条把**块切分语义**作为规格记录下来）。
- **"扫描结果 0 处"必须先证明扫描器抓得住已知缺陷**（2026-09-13 实测）：新检查器上线前
  实测活文档面得 0，**这个 0 可能是"真的干净"，也可能是"扫描器坏了"**——两者输出完全一样。
  做法：先造一份**含已知缺陷的合成探针**（并包含若干**应当被忽略**的诱饵，如围栏内的 `|`、
  行内管道符），确认它**精确命中预期处数、且不误伤诱饵**，再去相信真实面的 0。
  与"注入验证"是同一件事的**上线前版本**：一个是证明"守得住"，一个是证明"抓得到"。
- **真实判红 > 人工注入**（2026-09-16 实测）：若某个守卫**在 CI 上抓到了真实缺陷**，
  那就**不必再造合成注入**去证明它有效——真实命中已经同时证明了「抓得到」与「守卫在生效」，
  而且不会像人工注入那样打偏或打不到判定面（成因见上方两条「自我坑」与成因 5）。
  此时把力气花在**它没抓到的那一类**上：问一句「**它这次为什么没抓到别的形态**」。
  记入账本/知识库时，**把这次真实判红直接写成该守卫的注入自证证据**（省一轮成本）。
- **报门禁前先列「改动面 → 门禁项」对应表**（2026-09-16）：别按「我改了哪门语言的代码」切，
  要按「**这个文件被哪些守卫当输入**」切。反例：只改了 `docs/` 就推定"后端门禁与我无关"，
  结果 CI 的 `backend` job 真红（那一类守卫读的是文档）。同族 [[KB-ENG-102]]。
