# 账本接续 / 项目接手

本 Skill 同时承担三件事：**新会话快速接手、恢复当前项目上下文、继续已获准任务**。不得再建立第二个“项目接手 Skill”或靠聊天长提示维护上下文。

全项目范围仍按 `docs/product/product-closure-design.md`、`docs/product/hunting-decision-design.md`、`docs/research/limit-up-dragon-research.md`（存在且相关时）、`docs/product/feature-closure-audit.md` 核大小功能及消费者。后台开放情境，普通前台简洁；局部切片不能缩小整项目目标。

## 1. 固定读取链

始终先以最新 `master` 为共享事实源，按顺序读取：

1. `AGENTS.md`：红线、角色、发布与 Jev 边界；
2. `docs/handoff.md`：当前模式、当前现场、最近重大变化；
3. `docs/INDEX.md`：权威入口与文档定位；
4. `docs/plan-registry.md`：文档权责、历史取代关系、重大决策传播契约；
5. `docs/implementation-plan.md`：当前总方案与长期取舍；
6. `docs/ai/continuous-evolution.md`：长期开放世界发现、筛选与准入前治理；
7. `docs/product/product-closure-design.md`、`docs/product/hunting-decision-design.md`、`docs/product/feature-closure-audit.md`：产品/选股/细功能目标；若 INDEX/方案/stage 指向 `docs/research/limit-up-dragon-research.md`，同轮读取该历史涨停/龙头研究蓝图；
8. `docs/ai/jev-integration.md`：Jev 当前唯一专题蓝图；
9. `docs/retro-and-gaps.md` §5.9/§6.0 → 先读取 G0–G5/GX 阶段门治理，再扫描 W00–W09 活动任务的 ID/状态/阶段门/门内序/门禁角色/优先级/依赖/效果前置/下一步；随后只深入当前门的实际候选 `docs/stages/*`；
10. 只有 handoff/stage 指向某个施工分支或 PR 时，才进一步读取该分支/提交/CI 作为实现证据。

**禁止**把最近聊天、旧下载稿、已删除或长期功能分支、旧 DESIGN_ONLY、Bridge/自动互调状态当作接手入口。

## 2. 接手摘要

首次接手或上下文不确定时，在执行前先形成一个短摘要，至少回答：

- 当前 master / 当前模式；
- 当前总方案版本与最重要的长期原则；
- 最近几轮已进入主干的重大变化；
- Jev 当前允许做什么、禁止做什么、有哪些证据门未过；
- 当前 P0/P1 的真实未完成/待条件事项；
- 是否已有网页明确派工、准确任务 ID 与验收；
- 下一候选切片是什么、为什么；若用户只是询问/审阅则只汇报候选；若用户在 Codex 端**明确调用本 Skill 并说“继续任务/继续”**，按 §3 的动态选刀规则把这句话视为“授权执行一个最高优先级可开工切片”，但不得跨第二个主切片。
- 若当前问题涉及长期替代/新技术，是否需要调用 `ashare-innovation-radar`；雷达输出不等于派工。

摘要用于本会话恢复上下文，不建立新状态表；任务状态仍只写所属 stage。

## 3. 全局阶段门选刀规则

本 Skill 不维护第二张 backlog，也不凭聊天印象重排任务；唯一算法来自 `docs/retro-and-gaps.md` §5.9。每次“继续”从最新 `master` 重新计算。

1. **先收口共享候选**：handoff 若有会改变方案/账本/Skill 的待审 PR、CI 或待合并候选，先完成该闭环；不从旧 master 抢跑业务。
2. **形成可行动集**：排除 `已完成/已退出/已合并`；`待条件` 未满足排除；`依赖` 中任一硬开工 ID 未完成则排除。`效果前置` 不阻止采样/工程开工，但阻止效果主张、策略/参数晋级和生产权重切换。
3. **确定当前主门**：在 G0–G4 中找最低的、仍存在可行动 `阻断` 任务的门。只要该门存在阻断项，默认禁止更高门成为主切片。
4. **门内排序**：先 `阻断` 后 `非阻断`；同角色按 P0 → P1 → P2 → `门内序` 升序。不得用“新任务更有趣/更近用户问题”覆盖这个顺序。
5. **GX 只伴随**：`持续治理` 任务最多作为一个不冲突伴随切片；不能因文档、雷达、CI优化而跳过业务阶段门。
6. **G5 只验收**：只有当前准确候选已完成实现/研究且到发布/验收时才进入；不能把验收任务提前当开发任务。
7. **跨门例外**：只有 handoff 明确存在 `CROSS_GATE_EXCEPTION`，且写明范围、证据、无共享依赖/污染、停止条件、恢复点和禁止效果主张时才执行。Codex 不得自己创建或扩展例外；例外结束立即回到最低未闭环主门。
8. 每轮只执行**一个主切片**；完成、阻塞或证据变化后回填并重新计算，不连续扫账本。

接手摘要必须给出：`当前主门`、该门阻断任务、首选任务、同门竞争项、硬依赖是否满足、效果前置是否仅限制主张，以及为何没有跨到更高门。若无法唯一判定，停止在选择阶段并交网页规划审核。

用户明确调用本 Skill 并说“继续任务/继续”时，仅当 handoff 允许实施、没有未收口共享候选、当前主门和首选任务唯一时，这句话才授权该**单一切片**。DESIGN_ONLY / REVIEW / BLOCKED 或门序冲突时只报告，不执行。
## 4. 执行与防漏

1. 收到“ChatGPT审核完了”只代表开始重读；先核 master、当前任务轮次、实际工作区/分支/HEAD、计划和证据。
2. 初次明确派工可实施；需修改只做限定整改；阻塞就停止。重复通知不重做，同一工作区不并行写。
3. 新提交、未推送回填、归属不明改动或版本不一致先核实；不 reset/clean，不覆盖前任成果，不丢未合分支。
4. 发现新的模型、工具链、架构、产品语义、协作或治理决策时，必须按 `docs/plan-registry.md` §1.1 做**传播核对**：列出受影响权威面已更新项和不适用项/理由。只更新专题蓝图不算完成。
5. Jev 只用于 bounded 语义判断/验证或条件能力路由；确定性金融规则、权限、撮合、风控、时间/数值计算和真实执行不得委托。human gold 未完成前不宣称 accuracy、不调生产阈值。
6. 完成后按 `ashare-task-handoff` 回填同一阶段任务、证据与 handoff 指针，提交/推送并核到远端；未推送不说已交付。
7. 本地验证、网页独立审核、准确版本 CI 和运行加载分开。额度不足不试探、不换付费 API；平台安全拒绝不绕过。

只有出现真实访问/证据/并发/权限问题才要求最小必要介入。正常接手不让用户重新搬运整套历史，也不要求功能分支长期存在。
