# 门禁红项定性分型与处置（先定性，再处置）

## 0 铁律

**禁止跳过定性直接重跑。** 「重跑即绿」是一个**结论**，不是一个**动作**——
它必须由下面的分型证据支持。先拿到「失败项名字 + 完整栈 + 首次失败时刻」，再动手。

**先跑 `date "+%Y-%m-%d %H:%M:%S %Z"`**：会话上下文给的 `current_time` 是会话起点快照，
长会话里会滞后十几个小时，会把「跨日」判错。

## 1 分型（四类，判定手段各不相同）

### A. 真回归（本分支引入）
- **判定**：`git diff <base>..HEAD -- <相关文件>` 与工作区 diff **非空**。
- **处置**：修。修法与证据按仓库既有范式和 KB 惯例走。
- ⚠️ 别忘了「改文档也可能让后端红」——门禁里常有一类**扫 `docs/` 的文档守卫**。
  所以「本轮只改了 X」**不构成**不跑全量的理由。

### B. 到期型（**单向到期**，本族最会骗人）
- **形态**：夹具日期**写死** × 被测窗口**相对运行日** ⇒ **先绿、到某一天起永久红**，
  因此被读成「偶发」。与「周期性变红」（周末/长假才红，一周 5/7 是绿的）**同源、失效形态不同**。
- **到期日可算**：`到期日 = 夹具日期 + (窗口天数 − 1)`。
- **取证（决定性）**：**只翻时钟、代码一行不改**——
  ① 真实时钟跑 ⇒ 红（或桶/集合为空）；
  ② 钉死到到期日之前的时刻（`monkeypatch.setattr(<模块>, "beijing_now", lambda: <定死时刻>)`，
     或临时伪造系统时钟）⇒ **恢复绿**。
  ⇒ 成因是**日期窗口**，不是代码。
- **处置：必须修，不许重跑**（重跑只会永久红）。
  修法范式（择一，优先①）：
  ① **同源钉死时钟**——`monkeypatch.setattr("<被测模块>", "beijing_now", lambda: <夹具那一刻>)`。
     ⚠️ 前提是被测模块**在模块级 `from ... import beijing_now`**（属性挂在模块上才打得中）；
     若被测函数已有 `now`/`asof`/`today` 注入参数，直接用参数，不要打补丁。
  ② 夹具锚到**真实存在的交易日**，并断言选它的理由。
  **不要**把夹具改成 `beijing_now().date()` 派生——那只是把「到期」换成「跨零点竞态」，治不了病根。
- **关闭时补**：把**到期日两侧**都写成契约用例（前一刻成立、后一刻失效），
  失败消息里写清「这正是 CI 跨过该时刻后翻红的点」。

### C. 真偶发
- **取证**：**隔离复跑统计失败率**（单文件/单用例，独立 basetemp），
  并记下**失败值**与**阈值**的差距。
- **两个子型，处置相反**：
  - **C1 判据有缺陷**（判别力被噪声淹没）：失败值**紧贴阈值**（例：0.480 vs 阈值 0.475）⇒
    判据的**判别窗口**与噪声同量级。**处置 = 修判据，但要「拉大两端距离」而不是「放宽阈值」**：
    把「合法结局」与「非法结局」的实测值拉开（例：残值 0.4 vs 整份 0.5 → 改成 0.4 vs 1.0），
    阈值取在中间，两侧各留 ≥2× 抖动。
    ⚠️ **余量必须写明是「哪两个量之间」的余量**——写过"留了 5× 余量"但保护的是另一个量，
    是这类缺陷的典型成因。可迁移判据：`判别窗口 / 实测抖动 ≥ 5`。
  - **C2 与噪声无关**（共享状态、SQLite 锁、端口、模块级 fixture、进程状态）⇒
    **不擅自改**，作为**观察项**登记（写明复现率、未复现的事实、下次优先怀疑的方向）。
    ⚠️ 若完整栈**没取到**，**如实标注「未归因」**，不要脑补根因。

### D. 环境型（负载/宿主）
- **形态**：**隔离复跑恒绿**，只有**全量并发**才红；同时 `uptime` 的 load 明显异常。
- **取证**：隔离复跑（含放宽预算的对照）＋ 全量复现 ＋ 记录 load。必要时用
  `pgrep -fl` 找出**别的进程/别的会话**在抢 CPU（`ps` 可能被沙箱拒）。
- **处置**：**不改断言**（改 = 放宽判据），如实标注**负载前提**后登记；
  若用户已明示"待拍板"，就**只补证据、不擅自改**。
- ⚠️ **报耗时（尤其前端数字）必须带负载前提**，否则下一位会把它当回归。

## 2 「重跑即绿」的适用边界

| 情形 | 重跑即绿成立？ |
|---|---|
| **同项**重跑变绿，且失败值可解释（贴阈值/环境） | ✅ 成立（C/D 类） |
| 重跑后**换了另一个失败项** | ❌ **不成立**——它只是暴露了第二颗炸弹（B/A 类常见） |
| 重跑**每次都红**，只是红点会换 | ❌ 不成立 |

⇒ 判据 = 「**同项**重跑是否绿」＋「失败值是否可解释」。**"换了个失败项"必须重新定性，不得套用前者。**

## 3 反模式（我实际踩过、已证伪的机械化排查）

- **全局时钟前推扫描**（`sitecustomize` 替换 `bjtime` 三函数 + `db.utcnow`，+N 天保星期不变）：
  **假阳性生成器**。钩子只覆盖 `app.*`，测试/夹具/文件时间戳仍走真实时钟
  ⇒ 造出「测试按新日期、被测按旧日期」的错配，判出一堆假红。
  验证法：**对照实验**——钩子在场但**不前推**，若原本"红"的项变绿，即证明是钩子错配所致。
- **函数名 ∩ 日期字面量的静态交叉**：`get`/`run`/`add`/`__init__` 这类通用名会把匹配面撑到几十个文件，
  纯噪声。**可靠入口是机制级判据**：只找「窗口起点取自**全局时钟** **且** 签名**无**注入参数
  （`now`/`asof`/`today`/`trade_date`）」的函数。

## 4 收尾（缺一不可）

1. **注入自证**：把缺陷形态注回去，判据必须**精确变红**；复原后 `shasum -a 256` **逐字一致**。
2. **登记**：任务账本（唯一任务清单）＋其交接索引 ＋ `docs/handoff.md` 明细条目（照模板字段）。
3. **知识点入库**：把可迁移的判据与**被证伪的排查**一起写进去（负面知识同样值钱）。
4. **门禁**：按仓库纪律跑**全量**（不是单跑受影响的文件）；数字**当轮实测回填**，
   并注明**负载前提**与**服务是否在跑**。
5. 清理：临时 basetemp、临时 worktree、临时服务；确认常驻端口仍在且健康。
6. **提交核验（2026-09-17 实测踩过，零信号丢失）**：`git add` 后 `git status --short` **必须为空**；
   `commit` 后再确认一次为空。
   - **`git add -A` 之后再编辑的文件，不会被不带 `-a` 的 `git commit` 收进提交** ⇒ 静默丢失。
   - 为什么没信号：提交成功 + 推送成功 + CI **三 job 全绿** + `doc-health` **全过** + 文档自身仍自洽。
   - **核验「我提交了什么」用 `git show --stat HEAD`（普通提交）**；
     ⚠️ **合并提交的 `--stat` 显示的是「与第一个父」的差异**（会把对方几十个文件全列出来），
     **不能用作此证据**。
   - worktree 里 `ln -s` 建的 `node_modules` **不匹配** `.gitignore` 的 `node_modules/`
     （末尾斜杠只匹配**目录**）⇒ `git add -A` 会把它当新增文件收进去；
     收尾一律用**精确路径** `git add <file>...`，或先 `git status --untracked-files=all` 逐条核对 `??`。

## 5 自检

- 我这次说「偶发」，是**测出来的**还是**感觉出来的**？（有没有失败率数字？）
- 我说「同一个项重跑绿了」——**真的是同一项**吗？
- 我改了判据——是**提升了判别力**，还是**放宽了阈值**？
- 我报的数字，**前提**写清了吗（负载 / 服务在跑 / 隔离还是全量）？
- 提交前 `git status --short` 是空的吗？我是**实际看过**，还是**以为**它为空？
