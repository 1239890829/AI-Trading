# async 上下文同步 IO 审计与搬线程

## 0 先建立正确预期

`await` **只让出控制权**；同步调用**不让出**。一个含 SQLite 全表读 / DuckDB 查询 / 文件读的同步函数
被 async 函数直接调用时，**整个事件循环**（含 1s 行情 WS 推送、其他请求）在这段时间停摆。
症状只有"卡顿"——测试全绿、类型全对、日志无异常 ⇒ **必须用源码级守卫 + 实测，不能靠读代码下结论**。

## 1 扫描：**两轮**，第一轮必然欠报

| 轮 | 判据 | 会漏什么 |
|---|---|---|
| v1 | async 函数体内对**白名单方法名**的直接调用 | ①列表推导式/嵌套表达式里的调用 ②**inline `db.execute(...)`** ③**async 端点 → 同步 helper → IO**（最常见） |
| v2 | 加**调用图传递闭包**：先标出"体内含 IO 原语的同步函数"，再回溯 async 调用点 | 噪声大（`get_session_factory()` 这类**构造**不是 IO，别算进去） |

⚠️ **v1 的欠报是真实踩过的**：v1 报 53 处，写入守卫后反向断言**当场**多报出一处
（在列表推导式里）。⇒ **扫描结果为 0 或"看起来齐了"，必须换方式复核**。
⚠️ 噪声控制：只把**真正阻塞**的调用当 IO 原语。`get_session_factory()` / `create_engine()` 是构造，
把它们算进去会让整个调用图被"传染"成 IO。

## 2 逐项实测：**标签必须与 lambda 对账**（最容易翻车的一步）

写一张 `(标签, lambda)` 表跑基准，**每个数字报出去之前，单独再测一次该对象**。

⛔ **真实事故**：标签写 `/api/alerts/events AlertRepository`，lambda 调的却是 `EventStore`
⇒ 记成 **8.5ms** 并**动手包了 `to_thread`**；复核实测只有 **0.36ms**（差 24 倍）⇒ 两处包裹被回退。
**风险面**：`X.list_events` / `Y.list_events` 这种**同名方法跨类**在仓内大量存在，肉眼极易放过。

判据：**"这个数是谁的"与"这个数是多少"同等重要**。标签错配不会报错，它会产出一个
**看起来精确的数字**，直接翻转"改不改"的结论。

## 3 定阈值：搬 or 不搬

**判据三项一起看**（只看第一项会做出错的改动）：

1. **阻塞时长**——毫秒级（<5ms）不搬：`to_thread` 的调度开销与收益同量级；
2. **触发时是否在热路径**——前端轮询 / 盘中常驻 > 管理端点 / 手动触发；
3. **搬走是否引入新风险**——见下方"绝对不要搬"。

**搬的前提（必查两件事）**：
- 被搬函数**自己新建并使用** session/连接（`with self._sf()` 这类 per-call）⇒ 不跨线程复用；
- 该函数**没有已经 `to_thread`**（worker 线程里再开线程是纯浪费）。

**绝对不要搬（会引入新风险）**：
- **读-改-写**（如"读整个 JSON → 改 → 写回"）：同步执行时读与写之间**没有 `await`**
  ⇒ 对循环而言是**一次原子操作**；丢进线程池反而**制造并发**，两条交错完成读改写 ⇒
  **后写者覆盖前写者**（丢数据），除非另加锁（那是更大的改动）。
- **构造类**（`get_session_factory()`）、**单条小查询**（毫秒级）。

⚠️ **"同步" ≠ "该搬去线程"**——这是最容易搞反的一条。

**不搬的必须逐条登记数字**（写进代码注释 + 守卫文件的"刻意不搬"段），否则下一轮会被
重新"发现"并改错。

## 4 搬的写法

```python
rows = await asyncio.to_thread(store.list_events, active_only=True, limit=30)
```

- 传**函数引用 + 关键字参数**，不要 `lambda`（保持可读、便于守卫匹配）；
- 循环里用时**先 hoist 到变量**：`_rows = await asyncio.to_thread(...)` 再 `for row in _rows:`；
- 记得在该文件 `import asyncio`（并跑 pyflakes）。

## 5 守卫扩面（判据要**带接收者**且**能表达上下文**）

- **反向断言只写方法名会误伤同名方法** ⇒ 用带接收者的字面量（`store.list_events`）。
  💡 关键语法事实：`to_thread` 传的是**函数引用**（`to_thread(store.list_events, …)` 不含 `(`）
  ⇒ 该字面量**只命中裸调用**，既不会把已包的算成未包，也不会自match。
- **同步 helper 体内的调用是合法的**（它不占循环；违规在**调用它的 async 端点**，是另一层）
  ⇒ 反向断言加 `async_only`：用 `ast` 取 async 函数体行号集合，**并减去其中嵌套的同步 def**；
  语法不完整时返回 `None` ⇒ 退回"不过滤"（严 > 漏），**不要静默返回空集**（那会变成假绿）。
- **按文件判的反向断言要预告预期形状**：同一文件多条登记项共用它 ⇒ 注入一处会**同时红 N 条**，
  写进 docstring，否则会被误读成"守卫过度耦合"。

## 6 注入验证（不可省）

- 把某处 `to_thread` 改回裸调用 ⇒ 确认**精确变红**（或按预期形状变红），再复原；
- 复原后 `grep -c "INJECTED"` 必须为 0；
- 详见 `guard-injection-verify` skill（本条对应其"成因 7：匹配面过宽 ⇒ 假红"）。

## 7 效果验证：判据是**事件循环延迟**，不是吞吐

⛔ **踩过的错**：用"4 并发重请求的墙钟 / 单发"判并行度，得出 `6.00 ⇒ 疑似串行`，
**差点误判改动无效**。错因：ORM 构造是 **CPU 密集**，GIL 下**本就无法并行**，墙钟串行是必然的、
与 `to_thread` 无关。**`to_thread` 不加速 CPU 密集工作，只把循环让出来。**

**正解——循环延迟探针 A/B**：

```python
async def lag_probe(stop, out):
    while True:
        t0 = time.perf_counter()
        await asyncio.sleep(0.005)
        out.append(max(0.0, (time.perf_counter() - t0 - 0.005) * 1000))  # 循环被占住的时长
        if stop.is_set():
            break
# A 相：直接调同步函数；B 相：await asyncio.to_thread(...)
# 两相各跑 N 次，比较 max(lag)
```

⚠️ **探针要先 `await asyncio.sleep(0.03)` 让它跑起来**再开始计时，否则 A 相（循环被占死）
会采到 **0 个样本** → `IndexError`。**采样数本身就是证据**（A 相采 6 次、B 相 36 次）。

实测样例（4 × limit=2000 的同步读）：最大循环延迟 **342.8ms → 19.1ms（-94%）**，
而墙钟 347.7 → 330.0ms 基本不变。

## 8 收尾

- **重启服务**使新代码生效（无 `--reload` 时改完不重启 = 旧代码）；
- **真实端点验收**：状态码 + **载荷契约**（HTTP 200 ≠ 契约满足，见 KB-ENG-37）；
- 全量门禁 + **自洽核对**（测试项数差额 = 新增用例数，含"零新增文件"的情形）；
- 把"实测数字 / 刻意不搬清单 / A/B 结果"写进账本与守卫文件注释。

## 环境坑

- `npx vitest run` 默认并行度下可能**被 SIGKILL（exit 137）且零输出** ⇒ 加 `--maxWorkers=1` 复跑。
  **无输出的 137 ≠ 测试失败**：环境类静默失败的特征就是"没有失败信息"。
- 查代码用 **Grep 工具**；本环境 shell `grep` 会**静默返空**（表现为"零引用"假阴性）。
