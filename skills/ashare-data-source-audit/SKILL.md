# A 股数据源实测对比与使用度审计

用户问"用哪个源"或"我们用了多少"时，答案必须来自**同一时刻、同一口径的实测**，不是印象。
这套流程的价值主要不在"怎么调接口"，而在**避免量错**——我自己就在一次审计里
连犯 3 个测量错误，其中一个差点得出完全相反的结论。

**三条路线，先判是哪条**：

| 用户问法 | 走哪条 | 产出 |
|---|---|---|
| 「用哪个源」「谁更全」「这个能力能不能拿到」 | **流程 A 选型对比** | 逐能力实测表 + 选型结论 |
| 「梳理已接入的源」「哪些没用满」「有没有更优质的替代」 | **流程 B 使用度审计** | 源清单 + 接入度 + 未用清单 + 替代建议 |
| 「换源」已获拍板 / 开始落地 | **流程 C 换源落地** | 适配层 + 降级链 + 口径标注 + 注入自证 + 测试无网开关 |

三条都遵守下面的「铁律」与「陷阱」。

## 铁律：先读文档，再调接口

同花顺官方端点文档就在仓库里：`skills/hithink-finance/docs/api/*.md`
（`capability-map.md` 是总路由，`endpoints-*.md` 是逐端点参数）。

**靠猜参数试错的代价不是慢，是得出错误结论。** 我曾因此把"端点不可用"
写进结论，实际只是参数名不对。

高频易错参数：
- 分页是 `page` / `size`（默认 50、上限 200），**不是 `limit`/`offset`**
- 龙虎榜响应是 `{stock_items, hot_money_items, count}`，**不是 `item` 列表**
- `start` / `end` 是**毫秒时间戳**；`report` 格式是 `YYYY-[1-4]`（如 `2025-4` = 2025 年报）
- `thscode` 必须带后缀（`.SH` / `.SZ` / `.BJ` / `.TI`），裸 6 位代码不接受

## 流程 A：选型对比（"用哪个源"）

### 1. 列出候选与已实现清单
先把"官方提供了什么"和"我们接了什么"摆在一起。差距本身就是结论的一部分。
（首次审计发现：59 个端点只接了 7 个方法——最大的问题不是选谁，是欠用。）

### 2. 写实测脚本，逐个能力打表
对每个能力同时打所有候选源，记录 **可用性 / 延迟 / 条数 / 字段完整度**。
异常不算失败，要如实记下异常文本。

```python
async def probe(label, coro, show=3):
    t0 = time.perf_counter()
    try:
        data = await coro
    except Exception as exc:
        ROWS.append((label, "✗", f"{(time.perf_counter()-t0)*1000:.0f}ms", "-", str(exc)[:90]))
        return None
    ...
```

### 3. 重点测"覆盖率"，不是"有没有"
条数差不多不代表能力相当。决定性差异往往在字段覆盖率：
涨停池 ths 81 只 / 东财 82 只看似持平，但**涨停原因覆盖率 100% vs 0%**——
后者直接决定题材分析能不能做。

### 4. 数据打架必须追到底，不许取一家了事
两边数字不一致时，逐条核对到具体标的，判断谁对：
- 拉出各自的原始记录
- 用第三个可验证源交叉验证（如用价格×昨收反推理论限价）
- 结论通常是"两边各有各的错"，而不是"一家对一家错"

（实例：跌停家数 ths 报 1、快照推导报 4。逐只核对后发现
ths 漏报 2 只真跌停，而快照把 1 只限价口径失配的 ST 股误算进来。）

### 5. 交叉验证"无法验证的字段"
文档里标"字段序推断、待验证"的字段（如东财板块 f109/f110 多周期涨幅），
要么找到可信源验证，要么**拒绝使用并写明理由**。
拿未验证字段当判据，等于把推断当事实。

### 6. 记录所缺能力 → 什么时候需要 → 用哪个源
用户真正想知道的是"我没有的东西，什么时候会用到、到时候找谁"。
按优先级排序，并标注硬缺口（没有任何免费源能提供，如 L2 十档）。

### 7. 联网查同类型产品怎么做
搜索关键词组合：
- `A股量化 开源项目 数据源对比 akshare tushare baostock efinance`
- `涨停板 情绪周期 打板 复盘工具 数据源`
- `A股 Level-2 逐笔成交 分钟K线 数据源 对比`

行业共识（2026 多篇横评一致）：**稳定性 > 数据完整性 > 实时性 > 性能 > 价格**。
爬虫派（akshare / efinance）的共同死因是"源站网页一变接口即失效"。

## 流程 B：使用度审计（"哪些源没被用满"）

这条路的产出是**接入度**，不是优劣。核心问题从"谁更好"变成"**已经有的东西用了多少**"。

### 1. 先划清"源"的三类边界，别只数行情源

一次完整的清单至少三类，漏一类就会被问住：

- **行情/数据外部源**（同花顺 fuyao / 腾讯 / 新浪 / 东财 / 通达信 TDX / akshare / 百度 / NOAA …）
- **本地存储**（DuckDB marketdb、Parquet 落盘、SQLite）—— 它们是**上游数据的产物**，但也是下游的"源"
- **非行情外部服务**（LLM 网关、飞书 OpenAPI）

### 2. 官方能力面 vs 已接入：把两个数并排放

官方给了多少、我们接了多少，**差距本身就是结论**。同花顺 fuyao 的官方总表在
`skills/hithink-finance/docs/api/capability-map.md`（按分类给"全部端点一览"），
按分类逐类对账，比逐个端点数快且不易漏。

⚠️ **一个源可能有多个入口**：本项目 ths 的 23 个端点分布在
`app/data_providers/ths.py`（17）+ `app/services/theme_catalog_service.py` 直连（3）
+ `scripts/sync_marketdb.py` 直连（3）。**只 grep `data_providers/` 会漏掉 6 个**。
判据：全仓 grep 该源的 base URL / 端点路径片段，不要只搜 Provider 目录。

### 3. AST 调用点计数（本流程的核心方法）

**不要用 `grep -c`**——它把 `def` 行、`import` 行、注释、子串匹配（`get_trading_days(`
会被 `trading_days(` 命中）全算进去。实测差异可达 **37 vs 52**。

```python
import ast
from collections import Counter
from pathlib import Path

def call_sites(root: Path, names: set[str]) -> dict[str, Counter]:
    """按方法名聚合 Call 节点；分 生产 app/ · 测试 tests/ · 脚本 scripts/ 三档。"""
    out = {n: Counter() for n in names}
    for py in root.rglob("*.py"):
        if ".venv" in py.parts or "__pycache__" in py.parts:
            continue
        rel = str(py.relative_to(root))
        zone = "test" if rel.startswith("tests/") else (
            "script" if rel.startswith("scripts/") else "prod")
        tree = ast.parse(py.read_text(encoding="utf-8"))
        defs = {(n.name, n.lineno) for n in ast.walk(tree)
                if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef))}
        for node in ast.walk(tree):
            if isinstance(node, ast.Call):
                f = node.func
                nm = f.attr if isinstance(f, ast.Attribute) else (
                    f.id if isinstance(f, ast.Name) else None)
                if nm in names and (nm, node.lineno) not in defs:
                    out[nm][zone] += 1
    return out
```

三档读法：**prod=0 ⇒ 死代码**；**prod=0 且 test>0 ⇒ 仅测试（守卫的观测面，不要删）**；
**prod=1 ⇒ 单点依赖（上游一抖整条能力哑，且没有第二条路径能发现它坏了）**。

### 4. 枚举外部主机，防止漏源

```python
import re
from collections import defaultdict
from pathlib import Path

hosts = defaultdict(set)
pat = re.compile(r"https?://([A-Za-z0-9._\-]+)")
for py in Path("app").rglob("*.py"):
    for m in pat.finditer(py.read_text(encoding="utf-8", errors="ignore")):
        hosts[m.group(1)].add(str(py))
```

这一步的价值：**清单上的"已知源"往往少于代码里真实出网的域名**。本轮就靠它
确认了 `www.cpc.ncep.noaa.gov`（气候）与 `finance.pae.baidu.com`（财经日历）的存在。

### 5. 第三方客户端库的能力面要 `dir()` 实测，不要凭印象

通达信走 `easy_tdx`，能力面 = 客户端类的公开方法：

```python
import easy_tdx.client as c
for cls in ("MacClient", "TdxClient", "ExTdxClient"):
    k = getattr(c, cls, None)
    if k:
        ms = [m for m in dir(k) if not m.startswith("_")]
        print(cls, len(ms), ms)
```

⚠️ **必须把"数据类方法"与"连接/文件生命周期类"分开数**：`MacClient` 30 个公开方法
= **20 数据类 + 10 生命周期**，说"用了 3/30"是错的，正确说法是 **3/20**。
⚠️ **不同客户端类可能是不同协议族**（`MacClient` 是 MAC 协议 TCP 7709，`TdxClient` 是另一族）
——"MacClient 未用数"**不等于**"该库未用能力总数"，后者要另起连接与运维面。

### 6. 未用清单必须分三类，否则建议无法落地

| 类别 | 判据 | 处置倾向 |
|---|---|---|
| **纯内部辅助 / 已被取代** | 无外部语义（`_write_atomic`、`name`） | 倾向清理 |
| **已实现未接线** | 有明确业务语义但零消费方（宏观 CPI、两融账户） | **删或接属取舍，须拍板** |
| **仅测试调用** | prod=0 但 test>0 | **是守卫的观测面，不要按"零调用"处理** |

把三类混成一堆"死代码"报出去，会诱导错误清理。

### 7. 替代建议按"确定性"排序，不按"价值"排序

排序判据（越靠前越该先做）：

1. **现役源在本机不可用**（实测"通而空"）→ 替换收益最确定
2. **官方 REST 可替爬虫**（稳定性结构性提升，且字段是显式名而非字段序推断）
3. **可作第二源消除单点**（不替换，只加冗余）
4. **可作盘后定稿口径**（不进实时链，只补留痕）
5. **无更优源** → **必须写进结论**，否则读者以为还有得换

## 六个必查的陷阱

> A–C 是**测量**错误（把量错当结论），D–E 是**工具/口径**错误，F 是**库的语义**错误。
> 六条都来自真实踩坑，每条都曾让我得出过反向结论。

### 陷阱 A：聚合时被单条样本劫持
把一个集合的样本拼成一个大字符串再做关键词匹配，
只要**任意一条**命中就给整体贴标签。

```python
# 错：41 条原因里只要有一条含"业绩"，整个题材被归成"业绩兑现"
text = " ".join(all_reasons)
for core, kws in RULES:
    if any(k in text for k in kws): return core
# 对：逐条独立归因 → 按成员投票 → 回报票型分布
```

**任意一只符合 ≠ 这个题材符合。** 聚合口径要投票，并暴露分歧。

### 陷阱 B：单边阈值把"不可能的数据"吃成正常值
```python
# 错：5% 限制的 ST 股跌了 9.57% —— 不可能发生，却被算成跌停
if pct <= -(limit - tol): limit_down += 1
# 对：双边区间（落在限价上），超出进"存疑"计数
if -(limit+tol) <= pct <= -(limit-tol): limit_down += 1
elif pct < -(limit+tol): anomaly += 1
```
静默吃下异常数据比崩溃危险得多：不报错、界面照常渲染、没人发现。

### 陷阱 C：把"我的测量错误"当成"数据源的缺陷"
下结论前先自问：这个"不可用/空数据"有没有可能是我读错了结构、传错了参数、截断了分页？
**审计结论里要单独留一节记录自己犯的错**——这些是下次最快能避开的坑。

### 陷阱 D：数字不带口径 —— 同名方法会被跨 Provider 合并计数

按**方法名**聚合调用点时，`get_quotes` 的 24 个生产点 = **6 个 Provider 合计**，
不代表某一家被调 24 次。写进文档时必须带口径句，否则下一位读者会拿它当"某源的热度"。

同族：**文本出现次数 ≠ 调用点**。`trading_days` 在 `app/` 下文本出现 **96** 次、
AST 调用点 **44** 处（prod 37 / test 5 / script 2）—— 任何中间数字都能被"合理地"报出来，
只有**写明取数方法**才能让别人复核。

### 陷阱 E：`grep` 在 macOS/BSD 上静默返空，别把"没搜到"当"不存在"

`grep "a\|b"`、`grep --include=*.py`（zsh 下 `*` 未加引号会报 `no matches found`）
在本机多次静默失败。**搜不到时先换工具（Grep 工具 / python 过滤）再下结论**，
否则会把"我的命令写错了"记成"代码里没有"。

### 陷阱 F：第三方客户端库"我拿到全量了"可能是假象 —— 先验**时间轴**，再验字段

`easy_tdx` 的 `MacClient.get_transactions`（逐笔）**签名对、字段对、数据也是真的**，
但默认用法拿到的结果**时间轴是断的**：库内自动分页（`_TRANSACTION_PAGE_SIZE = 1000`）
把「最新 1000 笔」放前面、把「更早的 1000 笔」直接 `extend` 在后面 ⇒ `count=2000` 时
`mono_inc=False`、`first=13:47:48 / last=13:47:45`（**首尾落在同一分钟**）。
⇒ 症状是「**数据看着有，但覆盖不全**」，只看 `len(df)` 或抽样前几行**完全发现不了**
（`len=2000` 看着比 `count=10` 更"完整"，实际更错）。

**必做三验**（缺一条就会把残缺当完整）：

1. `is_monotonic_increasing` + `min`/`max` —— 时间轴是否连续、首尾是否落在合理区间；
2. **首行是否随 `count` 变化**：若 `count=10` 的首行 ≠ `count=2000` 的首行，
   说明分页语义是「**以最新为原点往回取**」⇒ **调大 `count` 拿不到更早的数据**，
   必须自己按 `start` 逐页取、并把**后取的页插到前面**；
3. **与同源另一口径交叉**：本例用同库 `get_tick_chart` 的 `Σvol` 对 `get_transactions` 的 `Σvol`
   （**26,235 vs 26,243**，差 **8** = 盘后定价那 8 笔），再与 fuyao 日线 `volume` 对齐
   ⇒ **三向自洽才敢用**（单看任何一个都自洽不了）。

**同族的两条**：

- **粒度 ≠ 名字**：`get_transactions` 叫「逐笔」，实际是 **3 秒快照聚合**（600519 全天 **3867 行**，
  每行含 `trade_count` 笔真实成交，Σ = **21,729** 笔）。**换源时前端文案必须同步改**，
  否则等于把「聚合快照」当「逐笔」展示（触碰红线 2 的精神）。
- **方向编码各源相反**：TDX `bs_flag` = `0=买/1=卖/2=中性/5=盘后`，而东财 = `1=买/2=卖/4=中性`。
  **不要凭记忆映射**——用「价格变动方向 × 方向码」的交叉表实证（本例：价格上行时 `0` 占 **121/138**）。

**推论（可推广）**：**"库给了自动分页"不等于"自动分页是对的"**。凡是要"取全量"的库方法，
一律先问三句：**取数原点在哪？页与页怎么拼？拼完是否单调？**

## 流程 C：换源落地（选型通过之后）

换源不是"改一行 import"。以下 7 步每步都有过翻车实例，**顺序不要调**：

1. **先定「主源 / 备源」，判据是"单测会不会触网"——这一条比性能重要。**
   ⚠️ **实测翻车（`IMP-038`）**：原方案是「TDX 接**主源**」，实施时才发现测试环境
   `ASHARE_DATA_PROVIDER=mock`，新源排链前 ⇒ 既有用例**绕过 mock 直连真实服务器**
   （实测确实建连并返回 10 行真数据）⇒ 单测变成「有网才过、结果随行情变」。
   ⇒ **规则：直连型外部源（TCP / mock 替不掉）一律排链后做备源**；确实要排前面时，
   先确认该端点**没有任何既有用例**。**不要用"跑得快"当排前面的理由。**
2. **口径三件套逐项实测，且每项都落到断言上**：方向码（各源可**相反**）· 量纲
   （股 vs 手）· 时间戳（**真 UTC vs "伪 UTC"**）。⚠️ 后两者**不抛异常**，只静默错
   ——"伪 UTC"在 UTC+8 浏览器里把 09:30 显示成 **17:30**。
3. **降级链必须能分辨「都失败」与「都为空」**：两者渲染成同一句"暂无数据"
   = 把数据源故障说成"这只票没有数据"（红线 2 同族）。返回 `(rows, source, detail)`，
   由调用方决定报错方式（502 / 空列表 / 助手文案）。
   ⚠️ **但"可分辨"不等于消费者会分辨**——**实测翻车（`IMP-038` 收尾）**：两个消费方
   都写成 `if detail:`（`detail` 非空 ⇒ 判"取数失败"），而备源关闭时
   `detail = "chain: empty; tdx: disabled"` **同样非空** ⇒ 把"没数据"讲成"故障"，
   **方向恰好反了**。**修法 = 判据归位到生产者旁边**（`trades_failure_detail()`），
   用**白名单**过滤非故障片段，两个消费方共用一份，并加「生产者 ⇄ 分类器同步」用例。
   ⚠️ **不要用"含 Error / timeout 字样"判故障**：真实 `ProviderError` 的文本是
   `Server disconnected without sending a response.`——**一个关键字都不含**，
   按字样判会把**真故障**漏成"没数据"（比反向更危险）。
   ⚠️ **路由状态码同理**：只有真故障才 502；"没数据" ⇒ **200 + 空列表 + 原因进 `meta`**。
4. **前端格式化器的单位假设要逐字段核对**。⚠️ **实测翻车**：`fmtVolume()` 按
   「后端统一为股」÷100 转手，而逐笔 `Trade.volume` **本身就是手** ⇒ **每行都渲染成 0**，
   不报错、不告警。该缺陷此前不可见**只因端点一直 502**（换源让它第一次真的渲染出来）
   ⇒ **"新源接上后必须真的看一眼渲染结果"**（本项目走 `agent-browser` 文本通道），
   只看接口 200 等于没验。
5. **给"页序 / 方向 / 口径"各配一条注入自证**：把缺陷形态注回去（`insert(0,…)` 改
   `append`、方向表照搬另一源、时间戳改伪 UTC、降级 detail 混为一谈），确认用例
   **真的变红**；还原后 `sha256` **逐字一致**再复跑。判据取窄 = 摆设。
6. **测试必须显式关掉新源（否则是"假绿"，比假红更难发现）**。⚠️ **实测翻车（`IMP-038`）**：
   单测桩返回 `[]` 时链被判定"失败" ⇒ **降级到新源 ⇒ 真的连上服务器拿真数据**
   ⇒ 用例**过了**（断言碰巧被真数据满足）。**表现是假绿不是报错**。
   ⇒ 规则：给新源加 `settings.<xxx>_enabled` 开关（默认 `True`），**`tests/conftest.py` 置 `false`**，
   要测降级链本身时用 fixture 显式打开 + **注入假实现**（不触网）。
   ⚠️ **并且：只跑受影响的文件不够** —— 上述两条红**只有全量门禁才暴露**。
   改了后端就跑全量，别用"我只改了 X"当豁免。
7. **收尾三条**：① 新文件先 `git add` —— `doc-health` 的 **J 项**判定面取自
   `git ls-files`，**未跟踪的新文件在本地就是"不存在"**（文档里写它的路径必红）；
   ② 适配层里的同步阻塞调用要登记进 `test_event_loop_no_block.py` 的 `GUARDED`
   （本项目热路径：逐笔是前端 10s 轮询）；⚠️ 该 `GUARDED` 是**参数化**的
   ⇒ 加一条就 **+1 用例**，报门禁增量时要算进去；
   ③ **加开关就要同步根 `.env.example`**（**不在 `backend/`**）——
   `tests/test_env_docs.py::test_env_example_covers_every_setting` 扫 `config.py` 字段集
   ⇄ `.env.example` 的 `ASHARE_*` 键，漏一行立刻红（`IMP-038` 实测踩到）。

第 9 节不可省。要列出"本次没验证到的"（如非交易日返回 0 条的端点未在交易日复测、
只测了覆盖率没测正确率、延迟只采样一次）——否则读者会高估结论的适用范围。

**流程 B（使用度审计）**

```
# 全量数据源清单与使用度审计
0. 速览（几个源 / 各自接入度 / 最该做的一件替代）
1. 取数方法（可复现，禁凭印象）—— 必须写清"调用点怎么数的"
2. 全量清单总表（源 / 承载文件 / 鉴权 / 信息维度 / 使用度）
3. 逐源能力面明细（官方总数 × 已接 × 未接，按分类）
4. 零调用 / 仅测试 / 单点依赖 三张清单
5. 可改用更优质源替代（按确定性排序，含"无更优源"的诚实条目）
6. 未充分利用但具挖掘价值（按价值排序）
7. 诚实边界（不成立的假设 / 不建议接入项）
8. 本轮推翻或更正的既有结论（**逐条写明原文错在哪、为什么**）
```

第 8 节是本流程**最容易被省略、也最有价值**的一节。审计常常会发现"文档写的
和代码/实测不一致"——**必须写成"原写 X，实测 Y，成因 Z"，不要静默改掉**，
否则下一位接手者会照旧文档再做一遍。
