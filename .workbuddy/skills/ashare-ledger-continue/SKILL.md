## 施工纪律（详见 `AGENTS.md`，此处只列最容易踩的）

- **6 条红线**：禁真券商 / 禁 mock 冒充实盘 / 禁确定性买卖结论 / Key 只存 `backend/.env` /
  撮合硬拦截 / 新增页面板块需先论证。
- **改进先提后做**：想到更优方案先说清「改什么 / 为什么 / 改完什么样」，确认后再动；
  触碰红线、数据口径变更、新增付费依赖时必须问。
- **计划批准后按顺序执行到底**，不需要逐项再确认；被外部阻塞的项显式标注原因。
- **验收以实际渲染为准**：UI 不确定就用 agent-browser 文本通道（`snapshot` / `eval`）看，
  **禁止用推理代替观察**；看不出来就如实说「无法目视，需你确认」。
  ⚠️ **坑（2026-09-15 实测）**：① 该环境带**沙箱代理**，本地端口用 `curl` 探活会被代理兜底成
  **502**（看起来像「在跑但报错」）⇒ 一律加 `--noproxy '*'`，服务没起时应见 `000 / Couldn't connect`；
  ② **指针事件驱动**的交互（如助手悬浮球：`pointerdown/up` + <4px 判定点击）用 `eval` 派发
  `PointerEvent` 是**开→关切换**，连派两次等于没点 ⇒ 派发**前先读一次状态**，且
  **派发与读取必须分成两次 `eval`**（React 提交是异步的，同一次里读 DOM 读到的还是旧状态）。
- **当前时间一律 `date` 实测**（会话上下文的 `current_time` 会滞后十几小时）。
- **下结论优先用 `rg`**；shell 多分支正则显式用 `grep -E 'a|b'`，不依赖非 POSIX 的 BRE
  `\|` 扩展；返空必须换第二种工具复核后才能推导“不存在”。
- **门禁数字当轮实测回填** `AGENTS.md`，差值与新增测试数自洽，**不沿用旧数字**。
- **删除只走 `scripts/safe-trash.sh`**，禁 `rm`。
- **端口 3000 / 8000 各单实例**，任务结束必须确认两个都在跑；后端**绝不用 `--reload`**。
- 涉**时间 / 时区**的断言要 `TZ=UTC` 复跑前端测试。
- 用户给的案例 / 外部方法论只是**参考输入**，不能替代既有体系与实测；冲突时以后者为准。
- **回填文档时的三个坑（2026-09-15/16 实测，都会当场让门禁变红）**：
  ① **不要复述「已消失的路径」**——写「某路径曾存在 / 已被搬走」的句子必然含一个死锚点，
    而锚点守卫**不区分「在用资产」与「在案引述」** ⇒ 一律用**占位描述**（"旧单文件"），
    **也不要靠登记豁免绕过**（[[KB-ENG-93]] 末段）。
  ①b **同样不要写「未纳入版本控制的运行产物」的文件名**（2026-09-16 PR #13 实测）：
    在 `docs/**.md` 里写 `git status` 的 `??` 文件 ⇒ **CI `B 死链` 红、本地恒绿**（B 项判定面 =
    `git ls-files`）。只写**目录**，文件名让读者跑 `git status --short` 取。
    ⚠️ 边界：B 项**只认 `docs/` 面引用** ⇒ 写未跟踪的 docs 路径必红、非 docs 路径不红，
    所以"本地没红"证明不了什么。**推论**：**改完文档一律用干净检出复验**——
    `git worktree prune && git worktree add --detach /tmp/ci-sim HEAD`，在里面跑 doc-health。
  ② **追加 KB 条目前，先核上一条余量 ≥ 3 行**：`C-KB 条目超长` 量的是「`### KB-` 到**下一条目起点**的行距」
    ⇒ 条目间**分隔行（空行 / `---` / 空行，共 3 行）计入上一条**，而**文件末条**取 EOF ⇒ **天然少算 3 行**。
    现象是「**我没动它、它却红了**」⇒ 处置 = 给上一条做**等义压缩**，**改判据是错的**。
  ③ **写长中文表格行别用内联 heredoc**（2026-09-15 §6.46 实测 `SyntaxError: invalid syntax.
    Perhaps you forgot a comma?`）：账本 §6.5 的行动辄数千字符且**正文里含 ASCII 双引号**
    （`是"抓出上一批的静默丢失"而不是"搬完文件"`），与 Python 字符串定界符冲突。
    ⇒ 一律**用 Write 工具写成独立 `.py` 文件再执行**（`/tmp/insert-xxx.py`），
    并在脚本里加**幂等保护**（`if "| §6.46 |" in s: return`）。`commit -F <文件>` 同理，
    比 `-m "..."` 安全；⚠️ **不要为了省事写 `--no-verify=false`**（该选项不接受值，且本仓禁止跳 hooks）。
  ④ **`git add -A` 会把运行产物带进暂存区**：`backend/data/minute_decisions/scan-YYYY-MM-DD.json`
    等调度产物**无 .gitignore 规则** ⇒ 收尾先看一眼 `git status --short`，
    非本轮改动的文件用 `git restore --staged <path>` 移出（**只移出，不删除**）。

⇒ 通例：**新增文件与引用它的文档在同一轮时，先 `git add` 再跑门禁**；

⚠️ 反向情形（本地绿 / CI 红）见 [[KB-ENG-95]]；本条是**同族反向**（本地红 / CI 绿），
根因同为「**判定面 = git 跟踪清单**」，已一并记入 [[KB-ENG-102]]。
⚠️ **改完文档/判据后必须重跑**——「刚跑过一次全绿」**不能**替代「改动之后再跑一次」：
文档改动同样会红门禁（锚点 / K 表格 / C-KB），且**只有全量跑才照得出**
（2026-09-15 实测：首次全量跑在文档写入**之前**，故为绿；写完 KB 条目后全量才报红）。
⚠️ **改了 `docs/`（或 `AGENTS.md`）⇒ 后端 `pytest` 也必须跑——「后端 `.py` 零改动」不构成豁免**
（2026-09-16 `IMP-031` 轮 **CI 真红**，[[KB-ENG-102]]）。根因是**门禁的输入面 ≠ 代码面**：
后端有一类**扫 `docs/` 的文档守卫**（`test_doc_status_truthfulness.py` 等），**输入是文档**，
所以只改文档照样让 `backend` job 红；而 `doc-health` 查的是**结构与引用**，
**不查**"谈状态是否带权威指针" ⇒ **「另一条门禁绿」不等于「这条门禁跑过」**。
**通用做法（省力且更强）**：动手前先列一张「**本轮改动面 → 对应哪些门禁项**」的对应表
（写出来才会发现 `docs/` → 后端守卫 这条边）；**先按语言分「改了哪门代码」是最容易漏的切法**。
⚠️ **先按语言/目录分门禁，是最容易漏的一刀**：正确切法是**按「这个文件被哪些守卫当输入」分**。
⚠️ 前端 `vitest` 默认并行度下会连续被 SIGKILL（exit 137）且零输出，加 `--maxWorkers=1`。
⚠️ 后端耗时强依赖「8000 是否在跑」，**报耗时必须说明前提**。
