# 每日盘后复盘 SOP

> **速览（30 秒）**：本文是**人工/LLM 复盘的操作顺序**（按七阶段：定界→事实链→周期定位→六维剖析→规律提炼→KB 对照→反例自检）。
> **结论产出必须可证伪**（if-then + 量化阈值 + 验证状态）；**单案例结论一律标「待验证」**。
> 复盘产出的新规律**默认是候选假设**，须过数据验证才可进体系（`kb/04-decisions.md` KB-DEC-019）。
> **导航**：§读法 → 执行顺序 → 各阶段要点 → 与后端 Agent 的分工 → 常见误判。判断口径另见 `kb/06-review-framework.md`（七阶段框架，复盘任务先读）。
>
> 适用：A 股每交易日收盘后（15:30 之后）。执行者：workbuddy（skill `ashare-daily-review`）。
> 配套：`docs/review-agent.md`（后端 Agent 机制）· `docs/sentiment.md`（情绪双轴判据）·
> `docs/theme-prediction.md`（题材预判评分卡）· `docs/retro-and-gaps.md`（项目盘点账本）。
>
> **本文件定义「复盘该怎么做」；后端 `app/review/` 定义「自动能算出什么」。**
> 两者是互补关系：Agent 产出可复现的事实与统计，本 SOP 负责 Agent 算不出的
> 定性判断（上涨逻辑、可改进性、次日计划）。

---

## 0. 红线（每次复盘都必须遵守）

1. **只给条件，不给确定性买卖结论。** 输出"若 X 则关注 Y，失效条件 Z"，禁止"明天买 X"。
2. **缺失必须显式标注，绝不臆测。** 取不到就写"数据缺失，本项不评"，不用 0 / 空值 / 默认值冒充。
3. **过程与结果分离。** 赚钱的错误决策仍是错误决策，亏钱的正确决策仍是正确决策。
   只按结果奖惩会让策略向运气漂移。
4. **改进项必须可验证。** 禁止"下次注意""加强关注"这类无法验证的表述；
   每条必须带 `target`（改哪里）+ `proposed_change`（怎么改）。
5. **不自动改任何配置或代码。** 改进项一律人工确认后实施（见 §6）。

## 1. 前置校验（防自指与跨日污染）

**这一步不通过，后面全部停摆。** 本项目 2026-08-29 正是在这里栽过：
东财 `push2ex` 传入非交易日会**静默回退到最近交易日**，导致"昨日涨停股今日表现"
变成"涨停股查自己涨停那天的收盘价"，恒等于 +10%，情绪阶段误判为「高潮」且置信度高。

| 检查 | 判据 | 不通过怎么办 |
|---|---|---|
| 交易日锚定 | `trade_date` 与 `prev_trade_date` **严格相差一个交易日**，走权威日历，不靠 weekday 猜 | 停下，先修日历 |
| 哨兵断言 | 再涨停率 == 100% / 翻红率 == 100% / 昨涨停均值 == +10.0% | **立即中止**并在报告里标 `blocked`——正常市场不可能出现 |
| 数据新鲜度 | 快照 `received_at` 落在 `trade_date` 当日收盘后 | 标 `stale`，结论降级 |
| 限价口径 | 涨跌停必须是**双边区间**（价格落在限价上） | 单边判定会把"5% 限制的 ST 股跌 9.57%"吃成跌停，超出部分进 `limit_anomaly` |

**limit_anomaly 核实顺序（2026-09-02 固化）**：先过两类已知正常误报，剩余才逐条查——

1. **N/C 前缀新股**：上市初期无涨跌幅限制，系统 `compute_breadth` **已豁免**（不会进
   anomaly）。人工复现脚本若与系统函数结果不一致，以系统为准——09-02 复盘曾因人工
   脚本缺豁免误记"1 只 N 前缀计入异常"。
2. **ST 超 5% 档**：多为摘帽当日恢复 10% 档而数据源 name 未更新（如 09-02 的
   *ST宝馨 +10.19%）。需公告核实，**未核实前保持存疑标注**，不豁免也不定论。
3. 剩余条目逐条核对：先理解业务规则（北交所 ±30%、新股首日），再怀疑数据。

## 2. 八步复盘流程

### Step 1 · 大盘与环境定调

**数据源**：`/api/market/*`（指数、宽度）、情绪双轴矩阵（`docs/sentiment.md`）。

**看什么**：指数涨跌与成交额 → 市场宽度（涨/跌/涨停/跌停/炸板率）→ 情绪阶段。

**情绪阶段由双轴矩阵查表得出**，不是单轴阈值：热度档（涨停家数 / 最高板 / 炸板率）×
赚钱效应档（1进2 晋级率 / 昨涨停中位涨幅 / 翻红率 / 跌停家数）。
**赚钱效应可否决热度**——热度高但赚钱效应转弱 → 「分歧」，不是「高潮」。

**输出**：当前处于周期哪一段（冰点/启动/发酵/高潮/分歧/退潮）+ 该段位该做什么
（如退潮期应降仓或空仓，不新开接力仓）。

**情绪 bands 来源标注（2026-09-02 起）**：阈值档位经历史分位校准后，档位分布与旧口径
完全不同（旧口径死档 0% 命中）。输出情绪阶段时必须注明所用口径版本/校准日期——
**口径切换日的档位变化可能是"口径变化"而非"情绪突变"**，不标注会把两者混淆，
污染跨日情绪序列对比。

---

### Step 2 · 领涨板块归因

> 这是本次 SOP 新增的一步。此前 `app/review/` 的 market 维度只统计「梯队断层数」，
> **没有做领涨板块归因**——而数据在 `/api/boards` 里一直存在（2026-09-01 实测：
> 黑色金属矿采选业 +17.61%，龙头 N马矿 +290.98%）。

**数据源**：`/api/boards`（行业涨幅榜，含 `change_pct` / `leader_symbol` / `leader_name`）、
`/api/themes`（题材内核 `core.type` + `core.votes` 成员投票分布、梯队 `formation`、阶段 `stage`）。

**2.1 谁在涨**：取涨幅榜 Top 5–10，记录板块名、涨幅、龙头股、成分数、成交额。

**2.2 为什么涨（逻辑归因）**：对每个板块归到一类，并可解释依据：

| 内核类型 | 典型依据 |
|---|---|
| 政策驱动 | 部委及以上文件、规划、意见 |
| 产业趋势 | 订单/产能/技术突破、行业景气数据 |
| 业绩兑现 | 中报/年报预增、扭亏 |
| 涨价周期 | 产品提价、上游涨价传导 |
| 事件驱动 | 并购、重组、单一突发事件 |

⚠️ **聚合口径必须按成员投票，不能按"任意一只命中"。** 本项目踩过：题材内核归因拼接
全部成分股原因后取"首个命中关键词"，41 条里只要有一条含"业绩"，整个题材就被归成
"业绩兑现"。**任意一只符合 ≠ 这个题材符合**——必须回报票型分布（`core.votes`）。

**2.3 明日能否延续**：看四项证据，缺任一项都只能给"观察"不能给"重点"：

- **梯队完整度**：有 2–5 板承接（断层 = 最高板悬空，接续风险高）
- **开板率**：低开板率 = 封板牢（>70% 说明封板不牢）
- **接力溢价**：正溢价说明接力资金赚钱，负溢价说明接力即套
- **所处阶段**：启动/发酵期延续概率高；高潮/退潮期延续概率低

**输出**：次日重点关注板块 **≤3 个**，每个带：关注理由（证据）、触发条件、失效条件。

### Step 3 · 选股逐只归因（用户诉求①的核心）

**数据源**：`POST /api/picks/review/generate` → `GET /api/picks/review?date=YYYY-MM-DD`。

对每个 pick 输出"实际走势 vs 入选理由"，走坏原因由 `classify_failure()` 归到固定枚举。
**关键是区分「判断不严谨」与「外部因素」**——两者改进方向完全不同：

| 归因 | 判定依据 | 归属 | 改进方向 |
|---|---|---|---|
| `logic_failed` | 超额 ≤ −2% 且无踏空/买点/情绪解释 | **判断不严谨** | 复核打分权重与入选逻辑 |
| `sentiment_misread` | 持有期市场处于退潮/冰点 | **判断不严谨** | 环境判据未生效，应加仓位联动 |
| `entry_bad` | 按买入范围介入优于追高 >1.5pct | **执行问题** | 选股没错，买点执行要修 |
| `missed` | 全天最低价高于买入区间上沿 | **纪律正确** | 踏空非失误，不改策略 |
| `data_issue` | 市场基准缺失，超额无法计算 | **系统问题** | 补数据源，不猜测归因 |

**「选错了」与「选对了但买点不对」必须分开**（`review_entry_quality()`）：
同一只票，按买入范围介入是赚的、追高介入是亏的——前者是执行问题，后者才是选股问题。
混在一起统计会污染迭代方向。

**输出**：做错的标的清单，每条带：归因类别、属于判断不严谨还是外部因素、可改进性。

**3.x 盘前方向对照（2026-09-02 起，选股 2.0 批次 C 自动产出）**：
`POST /api/picks/review/generate` 会产出盘前方向 vs 盘后实际走势的对照
（四分类：方向对/方向错/幅度不及/未覆盖），误判再细分（数据缺失/阈值过敏/逻辑失效）。
复盘**必须消费这份数据**——系统自动产出而复盘不消费等于白产。误判分类直接决定改进指向：

| 误判类型 | 改进指向 |
|---|---|
| 数据缺失 | 补数据源（data 类改进项） |
| 阈值过敏 | 调参数（parameter 类），不动逻辑 |
| 逻辑失效 | 复核盘前判据本身（strategy 类） |

**3.y 提醒收益回看（T−1 / T−3）**：对昨日（T−1）与前日（T−3）发出的提醒/精选标的
回看其后收益——T−3 起才有足够成熟度做统计，T−1 只做方向核对。连续多日提醒后收益
系统性为负 → 提醒阈值或来源有问题，进改进项。

**⚠️ 被覆盖简报日的对照数据可信度降级**：若当日盘前简报曾被重启/盘中重生成覆盖
（generated_at 晚于 09:30 或 trigger 非预期），对照的"盘前方向"实际是盘中快照，
只能标"参考"不能当盘前判断核验。

---

### Step 4 · 执行评估（有成交时）

**数据源**：`/api/review/reports/{trade_date}` 的 `trades` 维度。

看四项：被拒单（区分「规则正确拦截」与「参数不合法」）、过度交易（超纪律上限）、
执行滑点（成交价 vs 委托价）、盈亏归因（已实现/浮动，最差持仓是否触发失效条件）。

---

### Step 5 · 系统审计（用户诉求③）

**不只是"把盘面过一遍"，要主动找系统自身的毛病。** 分四层：

1. **数据完整度**：本次复盘的 `DataGap` 清单（阻断/降级分别多少，影响哪些结论）。
2. **数据源健康**：同一字段连续多日缺失 = 源链路异常，不是偶发。
3. **数据链健康（2026-09-02 起，系统自动采集）**：复盘报告的 market 快照带
   `provider_health`（四源链熔断器状态 + 切换记录）与 ths 涨停原因哨兵快照。
   熔断 open / 哨兵 alert = 当日部分数据建立在降级口径上，system 维度会自动产出
   条目——复盘解读时据此**下调受影响结论的置信度**，而不是当成独立事件看一眼。
   哨兵 coverage < 100% 的日子，涨停原因/题材归因相关结论全部降权。
4. **简报完整性校验**：核对 `data/picks/briefs/` 当日简报存在且 `generated_at`
   落在盘前窗口（09:15–09:30）、`trigger=schedule`。被重启覆盖或盘中重生成的简报
   （2026-09-02 实测事故）意味着盘前证据链不完整，Step 3.x 的方向对照要降级解读。
5. **信号衰减**：样本量是否足够做失效判定；不足时**明确不做判定**（不编造）。
6. **选股逻辑严谨性**（`GET /api/picks/meta`）：
   - 走坏原因分布：若 `logic_failed` 占比持续偏高 → 选股逻辑本身有问题，不是运气
   - 按梯队角色的胜率：龙头/补涨/滞涨各自实际胜率与平均超额
     ——这是回答"能不能按题材抓妖"的硬证据，比任何主观判断都可靠

---

### Step 6 · 改进项合成与处置（PDCA 闭环）

每条改进项必须带：`priority`(P0/P1/P2) + `category`(parameter/strategy/data/process) +
`target`（改哪里）+ `proposed_change`（怎么改）+ `expected_impact`。

**处置四态**（`PATCH /api/review/action-items/{id}`）：

| 状态 | 含义 |
|---|---|
| `confirmed` | 认可，待实施 |
| `applied` | 已实施 |
| `rejected` | 驳回（附理由） |
| `reverted` | 已实施但回退（效果不好） |

> **为什么必须有这一步**：2026-09-01 核查发现 107 条改进项**全部 pending、采纳率 0%**，
> 根因是缺少状态变更入口——改进项只能产出、无法消费。
> 后果是 `suggest_methodology_changes` 的"采纳率<20% → 该维度产出噪音"告警
> **永远触发且毫无意义**。闭环必须从"产出"走到"处置"。

**P0 白名单**：防止噪音维度霸占注意力——只有 `data` 类与白名单内的类别可标 P0，
其余自动降为 P1。

**PATCH 操作守卫（2026-09-02 固化）**：

1. 请求字段名是 `note`（不是 `resolution_note`——Pydantic 忽略 extra 字段，
   错字段名会**静默丢 note**）；`rejected/reverted` 必填 note 否则 422。
2. 请求体必须带 `trade_date/category/title` 守卫三元组：id 是 SQLite rowid 别名且
   无 AUTOINCREMENT，复盘重跑删除重建后 id 会漂移/跨日串号（实测 111→72），
   三元组不符返回 409——**收到 409 就刷新报告重取 id，绝不重试旧 id**。
3. 处置后回读验证状态已变更（读路径会用表行覆盖 payload 快照）。

---

### Step 7 · 次日计划

输出：关注板块（≤3，来自 Step 2）+ 关注标的 + **触发条件** + **失效条件** +
仓位建议（结合 Step 1 的情绪阶段）。

**红线**：只写条件与失效条件，不写"明天买 X"。失效条件必须可观测（价格/量能/梯队事件），
不能是"感觉不对了"。

---

### Step 8 · 元复盘（方法论本身）

记录"这样复盘有没有用"，而不是"市场怎么样"：`GET /api/review/effectiveness`。

- 各维度 `effective / ineffective / unknown`
- 各 `category` 改进项的**采纳率 / 回退率**
- 样本 ≥5 且采纳率 <20% → 提示该维度疑似产出噪音；回退率 >30% → 判据不可靠

**只建议，不自动改。** 自动改会让"框架演进"变成不可归因的黑箱。

---

## 3. 输出与存档

- 报告落库 `review_reports` + 落盘 `data/review/reports/YYYYMMDD.json`
- 研究页 `/research?tab=review` 按日期查看报告、改进项与有效性统计
- 每次复盘必须能回答三个问题：**今天哪里做错了？错在哪一类（不严谨 / 外部）？明天改什么？**

## 4. 参考方法论出处

| 方法 | 用途 | 落在哪一步 |
|---|---|---|
| 交易日志（Trade Journal） | 决策留痕，事后可追溯 | Step 3 / Step 7 |
| 过程 vs 结果分离 | 防止向运气漂移 | 红线 3 |
| Brinson 归因 | 收益来源分解（配置/选股/交互） | Step 2 / Step 3 |
| 期望值框架 | 胜率 × 盈亏比，样本不足不下结论 | Step 5 |
| 情绪周期定位 | 涨停家数/连板高度/炸板率/晋级率 | Step 1 |
| TCA 交易成本分析 | 滑点、实施缺口 | Step 4 |
| PDCA | 改进项从产出到处置 | Step 6 |
