# 每日复盘执行清单

> 定位：`docs/daily-review-sop.md` 讲「每一步怎么判」，本文件讲「逐项过、逐项勾」。
> 执行者按序核对，任何一项不勾清（✅/⚠️/❌ 三态）不算复盘完成。
> 依据：用户 2026-09-04 要求——复盘不能只确认功能开发完成就搁置，要逐一检查各大板块
> 与功能当天产生的数据和操作，核验操作是否出错、决策是否正确，评估实际效果、
> 准确率与合理性，基于数据事实归因，围绕「解决问题 → 优化决策 → 提高准确率 →
> 修复漏洞 → 优化功能 → 取长补短」持续进化。

---

## 0. 使用规则（先读这个）

**执行时机**：交易日 15:35 automation「A股每日盘后复盘」自动触发，或用户说「执行复盘」。
执行速查见 skill `ashare-daily-review`；判据细节见 SOP。

**三态输出纪律**：每一项必须显式标记——
- ✅ 通过（有数据佐证）
- ⚠️ 存疑（写明疑点与待核实项，未核实前不定论）
- ❌ 异常（进改进项，带 target + proposed_change）
- **留空 = 没查，不是没问题。**「没参与」≠「净额为 0」，「未查」≠「正常」。

**归因三问（防过度揣测，写入报告前逐条过）**：
1. 有当日数据/日志支撑吗？（引用端点、文件、记录）
2. 换一个解释能被数据排除吗？（排除不了就并列写两个假设，别选边）
3. 是单日现象还是跨日趋势？（单日不下策略级结论）
三问不过 → 写「暂无法归因」，按 data_issue 处理，**绝不编一个听起来合理的解释**。

**硬停线（不过就停，来自 08-29 事故）**：交易日锚定失败 / 再涨停率或翻红率 100% /
简报缺失且无法定位时点 → 中止复盘并标 blocked，先修地基再复盘。

## 1. 地基层：数据可信度核验（后续一切结论的前提）

| # | 核验项 | 判据 | 数据源 | 依据 |
|---|---|---|---|---|
| 1.1 | 交易日锚定 | trade_date 与 prev_trade_date 严格相差一个交易日（走日历不靠 weekday） | `backend/data/trade_calendar.json`（days 是数组） | 08-29 push2ex 静默回退，昨日涨停查自己 |
| 1.2 | 哨兵断言 | 再涨停率/翻红率 ≠ 100%，昨涨停均值 ≠ +10.0% | 情绪序列 | 正常市场不可能出现，出现=日期串了 |
| 1.3 | 数据链健康 | 熔断器无 open；ths 涨停原因哨兵 coverage=100%；有降级 → 受影响结论全部降权 | 复盘报告 market 快照 `provider_health`；`/api/system/providers` | 09-02 四类静默失败：不核链路，data_issue 永远是盲区 |
| 1.4 | 简报完整性 | 当日简报存在、generated_at ∈ 09:15–09:30、trigger=schedule | `data/picks/briefs/` | 09-02 简报被重启覆盖，盘前方向实为盘中快照 |
| 1.5 | 快照新鲜度 | received_at 落在当日收盘后；limit_anomaly 按「N/C 豁免 → ST 摘帽存疑 → 逐条」核实 | Parquet 快照（项目根 data/parquet/snapshots/） | 单边限价判定把 ST 跌 9.57% 吃成跌停 |

⚠️ 任何一项异常：相关维度的结论降权或标「数据缺失本项不评」，**不用 0/空值冒充没有**。

## 2. 板块核验层：逐一检查每个功能「今天产出了什么、对不对」

> 这是本清单的核心新增。功能上线 ≠ 功能在干活；每个模块每天都要回答三问：
> **该产出的产出了吗？产出得对吗？它驱动的决策/操作对吗？**

### 2A 行情与数据链
| 核验点 | 判据 | 数据源 |
|---|---|---|
| QuoteHub 秒级更新 | health: consecutive_failures=0、is_stale=false、last_success_refresh 在 1~2s 内 | `/api/health` |
| 四源链状态 | 当前主源、当日切换次数与时段（盘前切换要单独标注） | `/api/system/providers` |
| 涨速/竞价/快照采样 | speed_sampler 有采样、竞价快照 stage 到位（13:00 后） | `/api/speed-rank`、竞价快照 |

### 2B 盘前链路（简报 → 卡片 → 执行闸门）
| 核验点 | 判据 | 数据源 |
|---|---|---|
| 盘前简报 | 见 1.4；方向性表述带触发/失效条件 | `data/picks/briefs/YYYY-MM-DD.json` |
| 09:26 飞书卡片 | 已发出、fields 齐全（名称/分数/止损加粗、逻辑/失效/止损分行）、执行状态行有值（挂了=降级标注，不是空白） | lark-cli 发送记录 + `docs/push-templates/*.card.json` |
| 执行闸门 | 有当日产出、data_status=ready/final；blocked/observe/normal 判定与实际竞价 gap 抽查 ≥2 只对得上 | `/api/picks/execution-gate` |
| 抽查口径 | 拿 1 只 blocked 股人工复核竞价 gap ≥9.5% 判定是否成立 | ths 竞价快照 |

### 2C 每日精选与影子持仓
| 核验点 | 判据 | 数据源 |
|---|---|---|
| 当日组合产出 | 有组合或「空仓闸门日」标注（闸门触发=纪律生效，不是数据缺失） | `/api/picks/today` |
| 稳定性约束 | 当日换股 ≤2 只；carryover 成员有被重评的痕迹 | `/api/picks/today` 对照昨日 |
| 评分合理性抽查 | Top1 的入选理由与当日盘面对得上（梯队/阶段系数方向正确）；退潮期仍给情绪高分的=阶段系数失灵 | `/api/picks/today` + Step 1 情绪 |
| 影子持仓晨窗执行 | 09:26–09:45 有执行日志；先卖后买；等权整手；**闸门 blocked 日影子必须空仓**（这是 gate 正确性的独立验证） | `data/picks/shadow/YYYY-MM-DD.json`、`/api/picks/shadow` |
| 幂等 | 无重复订单（同日二次 buy） | 影子日志 + paper 订单（scope=shadow） |

### 2D 盘中链路（跟踪 / 预警 / 情绪监控）
| 核验点 | 判据 | 数据源 |
|---|---|---|
| 盘中方向产出 | opportunities 有产出或显式空（退潮日 0 只候选=宁缺毋滥生效） | `/api/picks/intraday-top` |
| 方向对照消费 | 报告里四分类（方向对/错/幅度不及/未覆盖）+ 误判细分已呈现，**不许系统产了复盘不消费** | `/api/picks/review?date=` |
| 预警触发审计 | 当日触发列表逐条回看：该触发没触发（漏）？不该触发触发了（误）？对照盘面手工核 1~2 例 | `/api/alerts/*` + 盘面数据 |
| 预警送达 | in_app/feishu 通道送达记录；失败通道有显式 warning | `/api/alerts/channels` |
| 盘中情绪监控 | 三类事件（高度板炸板/炸板率连拍破 40%/指数急杀）当日有无触发；与实际盘面对照有无误报漏报 | `/api/system/providers` 快照 + 复盘 market 维度 |

### 2E 交易与复盘系统自身
| 核验点 | 判据 | 数据源 |
|---|---|---|
| 模拟交易操作审计 | 当日每笔委托：拒单是规则正确拦截还是参数问题（两种分开计）；滑点=成交价 vs 委托价；无绕过 T+1/涨跌停/整手硬拦截的成交 | 复盘报告 trades 维度 |
| 新闻/公告摘要 | requested vs actual provider；actual=rules 而 expected=llm → 降级要显式标注并查原因；**抽查 1~2 条摘要的事实准确性**（对照公告原文） | `/api/news/digest/{symbol}` |
| 复盘报告本身 | 维度齐全、DataGap 清单如实、meta_insights 非空 | `data/review/reports/YYYYMMDD.json` |
| 数据底座 | 当日 Parquet 快照落盘且无损坏读警告；交易日历未被测试污染（跑过 pytest 后必查）；marketdb 增量同步成功 | `data/parquet/snapshots/`、`trade_calendar.json` |

## 3. 决策与操作审计层：当天「做过的事」逐一回看

> 板块核验看「产出」，本层看「动作」。系统当天做过的每个自动动作、人确认过的每个
> 决策，都要能回答：**该做而没做？不该做而做了？做了生效了吗？**

3.1 **自动动作清单**：列出当日全部自动动作（简报生成、卡片推送×2、影子买卖、
预警触发、监控事件、digest 刷新），逐条标注三态。
- 依据：09-02 简报覆盖事故的根因之一是「自动动作发生后无人回看」。

3.2 **人工/agent 操作回读**：当日所有 PATCH（改进项处置、配置改动、代码部署），
事后回读验证真的生效（读路径会用表行覆盖快照——**PATCH 成功 ≠ 回读正确**，
复盘 action_items 教训）。

3.3 **决策对照**（这是「决策是否正确」的直接证据）：
- 盘前方向 vs 盘后实际：四分类 + 误判细分，误判类型直接决定改进项 category
  （数据缺失→补源 / 阈值过敏→调参 / 逻辑失效→复核判据），**不要凭主观再归因一遍**。
- 仓位建议 vs 实际情绪阶段：昨日建议「退潮空仓」而今日实际高潮 → 判据问题进改进项。
- 昨日改进项的执行核对：昨天说要改的，今天改了吗？（接 §6 回访机制）

3.4 **过程与结果分离红线**：赚钱的错误决策仍是错误决策；踏空（missed）是纪律正确
不是失误。只按盈亏奖惩会让策略向运气漂移。

## 4. 准确率台账层：跨日累计指标（单日样本不足的，在这里攒）

> 单日数据下不了结论 ≠ 不看。所有「需要 ≥5 样本才能判定」的指标统一记台账，
> 复盘时更新并对照阈值；**破线才进改进项，不破线不动策略**——防止被单日噪音牵着改。

| 指标 | 判据（破线动作） | 更新频率 | 数据源 |
|---|---|---|---|
| 精选准确率 = 达成/(达成+失误) | 连续 5 日 <40% → 复核六维权重（踏空/data_issue 不摊薄） | 每日 | `/api/picks/review` |
| 方向对照「方向对」占比 | ≥5 样本且 <50% → 按误判细分定位（源/参数/逻辑） | 每日 | `/api/picks/review` |
| 提醒收益 T−3 | 连续多日系统性为负 → 提醒阈值或来源有问题 | 每日 | `/api/picks/review` |
| classify_failure 分布 | logic_failed 持续偏高 → 选股逻辑本身问题，不是运气 | 每日 | `/api/picks/meta` |
| 按梯队角色胜率 | 龙头/补涨/滞涨实际胜率与超额——「能不能按题材抓妖」的硬证据 | 每日 | `/api/picks/meta` |
| 影子 vs 空仓 A/B | 影子累计收益显著差于空仓且闸门日一致 → gate 判据要修；显著好于空仓 → gate 过保守 | 有影子日 | `/api/picks/shadow` |
| 预警命中率/误报率 | 误报 >50% → 收紧触发条件；漏报关键事件 → 补规则 | 每周汇总 | 预警记录 |
| 摘要抽查通过率 | 抽查事实错误率 >20% → 摘要降级为 rules 或修 prompt | 每日抽查 | digest |
| 改进项采纳率 / 回退率 | 采纳率 <20% → 该维度产出噪音；回退率 >30% → 判据不可靠 | 每周 | `/api/review/effectiveness` |
| 情绪阶段判定后验 | 昨日判定的阶段 vs 今日实际晋级率/炸板率方向一致吗？连续错 3 日 → 双轴判据复核 | 每日 | 情绪序列 |

## 5. 归因纪律层：基于数据与事实，不过度揣测

**五类归属表**（判断/执行/系统/纪律/外部必须分开，混计会污染迭代方向）：

| 归因 | 归属 | 改进方向 |
|---|---|---|
| logic_failed | 判断不严谨 | 复核打分权重 |
| sentiment_misread | 判断不严谨 | 环境判据加仓位联动 |
| entry_bad | 执行问题 | 修买点执行，不动选股 |
| missed | 纪律正确 | 不改策略 |
| data_issue | 系统问题 | 补数据源，不猜测归因 |

**禁止清单**（每条都有前科）：
- ❌ 用单日样本推翻或确立策略（期望值框架：样本不足明确「不下结论」）。
- ❌ 把数据问题归因为策略问题（先过 §1 地基，data_issue 优先排除）。
- ❌ 把「任意一只成分股符合」说成「题材符合」（归因按成员投票票型）。
- ❌ 把口径变化当成情绪/策略变化（bands 口径、复权口径、连板两口径各归各用）。
- ❌ 用 0 / 空值 / 默认值冒充「没有」；把「没参与」当「净额为 0」。
- ❌ 无依据的对立归因（「主力出货」「情绪崩了」这类没有数据支撑的叙事不写进报告）。

## 6. 改进项闭环层：从产出到处置到回访

| # | 动作 | 判据/依据 |
|---|---|---|
| 6.1 | 每条改进项带 priority + category + target + proposed_change + expected_impact | 「下次注意」类不可验证表述禁止 |
| 6.2 | 当日逐条处置四态（confirmed/applied/rejected/reverted），请求体带 `note` + 守卫三元组，处置后回读验证 | 107 条全 pending 采纳率 0% 的教训；不处置 = 没复盘 |
| 6.3 | 重复项合并处置：今日条 confirmed 承接 + 历史重复条 rejected（注明承接谁） | 重复项稀释采纳率统计 |
| 6.4 | **applied 回访（新增）**：已实施项 T+3 回访——问题解决了吗？没解决标 reverted 或升级；**「改完即完」是修复漏洞主线的断点** | 用户主线「修复漏洞」要求验证效果；reverted 没人主动打，是因为没人回访 |
| 6.5 | P0 白名单维持：仅 data 类与白名单类别可标 P0，其余自动降 P1 | 防噪音维度霸占注意力 |
| 6.6 | 小改动直接实施（用户 09-02 授权），大改动先给方案；跑完 pytest 还原 trade_calendar.json | 既定工作模式 |

## 7. 取长补短层（每周五随当日复盘执行，非每日）

1. **外部口径交叉验证**（抽 1~2 项）：涨停池/晋级率对照 seal_nextday 自证、
   板块多日涨幅对照官方 K 线——**自己算的指标要定期和独立口径对表**，
   防止口径漂移无人察觉（B3 关闭就是因为交叉验证发现推断值方向都反）。
2. **方法论对表**：过一遍 `docs/github-stars-trading-analysis.md` 与 freqtrade 出场纪律，
   检查「别人已验证有效的做法」还有没有没落地的（冲高≥3% 止盈就是从这里来的）。
3. **失败模式对照**：本周 classify_failure 的主要类别，找外部同类系统的处理方式
   （如情绪误判 → TradingAgents 的多角色辩论思想），只借鉴可规则化的部分。
4. 产出写进当日报告 meta_insights，可落地的进改进项（照常走 §6）。

---

## 8. 收束层：次日计划 + 元复盘 + 交付

**次日计划**（引用 SOP Step 7）：关注板块 ≤3 + 触发条件 + 失效条件 + 仓位建议；
失效条件必须可观测（价格/量能/梯队事件），禁止「感觉不对了」。

**元复盘**：`/api/review/effectiveness` 各维度 effective/ineffective、采纳率/回退率；
样本 ≥5 才判定；只建议不自动改。

**交付四块（缺一不可）**：
今天哪里做错了 → 错在哪一类（判断不严谨/外部/执行/系统）→ 明天改什么 → 改进项处置结果。
