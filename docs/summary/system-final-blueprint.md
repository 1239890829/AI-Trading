# AShare AI Trader 最终技术方案（任务四后基线）

> 基线：2026-09-15；适用范围：A 股实时行情、投研、猎场、模拟交易、事件选股与交易智能体。
> 本文是**目标架构与验收口径**，不另建任务清单；所有施工项只进入
> `docs/retro-and-gaps.md` §6.0，并以其中状态、优先级和 ID 为准。
> 系统输出仅用于研究和模拟交易，**不构成买卖建议**。

## 0. 结论先行

系统方向正确：数据质量三态、题材到个股的分层筛选、交易权限与可参与性硬门、模拟交易硬约束、
盘后复盘和内部调度器都已形成可靠地基。当前瓶颈不是再堆技术指标，而是把“候选为何产生、为何被挡、
为何排第一、提醒后结果如何”保存成同一条可回放证据链，并用样本外结果持续校准。

本轮直接修复三项现行缺口：

1. 猎场两个并发端点改为同键**单航班**构建，并对请求级风险字段使用深拷贝，消除冷缓存时两份瞬时快照
   互相覆盖、共享缓存对象被原地污染造成的 `1 ↔ 8` 数量抖动。
2. 通知中心只消费 `__picks_buy_point__` 的 `buy_point` 个股机会；板块异动、新闻、日选摘要仍留在分析面，
   不再进入通知列表。买点仍须通过精选置信档、红线否决、跟踪闸门、买入区间、涨停区、真实行情等门槛。
3. 内置 `evolution-agenda` 继续由进程内 `SchedulerRegistry` 在交易日 15:45 触发；受限自治默认开启，
   C 类改代码仍由独立开关控制且只生成 patch 与隔离分支，禁止自动合并、推送或真实下单。

## 1. 目标架构

```text
数据源 → Freshness/Quality 三态 → 场景识别 → 候选生成（高召回）
                                      ↓
结果标签 ← 模拟成交/盘后回放 ← 通知闸门 ← 个股精排 ← 可交易硬门
   ↓                                  ↑
因子/策略评估 → Champion/Challenger → 参数实验 → 交易智能体控制面
   ↑                                                   ↓
场景化 KB 检索 ← 复盘归因 ← 异常/漏洞探针 ← 审计、预算、回滚、停机
```

必须保持两层分权：

- **数据与决策平面**：确定性代码完成行情、因子、候选、硬门、排序、模拟成交和结果标签；LLM 不进入
  涨跌停、T+1、权限、费用、停牌、数据新鲜度等硬判据。
- **智能体控制平面**：LLM 负责异常解释、假设生成、KB 检索、实验设计、复盘摘要和改进排序；只能在
  可审计权限内调整参数/文档，代码只能提议。这样智能体有实际作用，但不会成为不可复现的黑箱评分器。

## 2. 猎场数量异常：根因、修法与验收

猎场页面同时请求 `/intraday-opportunities` 与 `/intraday-top`，两者以相同参数装配机会树。旧路径执行
“先读缓存、未命中各自构建、最后写缓存”，冷缓存并发时会启动两次全量构建；上游快照正好变化时，
一份可得到 1 只，另一份得到 8 只，最后完成者覆盖缓存。其后风险字段又直接写入缓存 dict，形成第二层
跨请求污染。刷新只是改变竞态顺序，所以表现为来回变化，而不是稳定的数据口径差异。

修复后的不变量：

- `(trade_date, top_themes, stocks_per_theme)` 相同的并发请求只允许一个装配工厂运行；
- 缓存只保存不带请求级实时风险字段的基线，响应先深拷贝再叠加当前快照；
- 两个端点共享同一份候选集合，允许展示切片不同，不允许总数因竞态不同；
- 回源失败不缓存，下一次仍可重试，不能用旧值冒充实盘。

验收以并发回归为主：同时发起两次构建，工厂调用数必须为 1；各响应候选数一致；修改任一响应不得
改变缓存或另一响应。真实盘中再以冷缓存连续刷新做端到端确认（账本等窗项）。

## 3. 通知策略：只提醒真正的个股机会

板块是候选上下文，不是通知对象。通知链固定为：

1. **板块先有效**：题材强度、持续性、资金/涨停梯队、事件传导与数据新鲜度成立；未知必须显式降级。
2. **个股再筛选**：只取账户有权限、当前可参与、非停牌、非封死涨停、非红线否决的标的。
3. **多维精排**：题材核心度/角色、量价、资金、筹码、形态、历史辨识度和风险收益共同决定排名；
   高相关指标只保留一个代表或零权重登记，不能用同类指标重复投票制造“伪共振”。
4. **买点触发**：精选置信档至少可执行、跟踪闸门通过、现价进入买入区间、未进入追高区、行情真实。
5. **提醒治理**：只发最优个股，按“交易日 + 标的 + 机会版本”去重；设置冷却、每日预算和失效通知。

通知卡必须展示标的、所属机会板块、核心依据、关键风险、失效条件、数据时间和“仅供研究/不构成买卖建议”。
板块异动、新闻摘要、日选列表继续在相应页面留痕，但不占用人的即时注意力。

## 4. 选股与因子：从加指标转向可证伪的精排

现有“题材 → 个股 → 闸门 → 风控”的方向应保留。需要调整的是研究方法：

- 将流水线明确拆为**候选生成器**（追求召回）、**资格硬门**（只回答能否参与）、**精排器**（追求
  Precision@K 与净期望）和**通知闸门**（追求注意力效率）。一个总分不应同时承担四种语义。
- 新因子先过结构新颖性检查：与已上线因子的截面相关、IC 序列相关、排序重合和条件贡献；高度同源则
  保留研究成果但不计权。优先研究方向无关的趋势强度、资金/筹码结构、题材扩散位置、可成交性和时效，
  暂缓 RSI/WILLR/STOCHRSI 等明显同族的批量扩张。
- 所有训练和回放必须是 point-in-time：按当时可见数据、复权版本、成分历史和披露时间重建；采用
  purged walk-forward/embargo，纳入手续费、滑点、整手、T+1、涨跌停买不到与停牌，防止未来函数、
  幸存者偏差和“收盘价可成交幻觉”。
- 不以单一胜率优化。主指标为 Precision@K、提醒后可成交净期望、相对基准超额、最大回撤、Profit Factor、
  Brier/可靠性曲线、覆盖率与周转成本；同时报告样本数、置信区间和分市场状态表现。
- 只有 Challenger 在多个滚动样本外窗口、成本后结果和风险约束上稳定优于 Champion，才允许小流量晋级；
  劣化自动回退。单日命中、单票案例或全样本调参结果只能生成假设，不能转正。

现阶段不能宣称系统已有可泛化的“高胜率”。已有回放、因子 IC 和案例证据证明部分机制可用，也多次
否证了流行策略，但主题策略触发样本仍有 0–7 次的小样本区间，且完整 walk-forward/成本闭环尚未统一。
提升准确率的正确路径是提高标签与验证质量，而不是调高页面上的一个分数。

## 5. 知识库：保留成果，升级为场景化证据路由

知识库已经实际参与进化议程、复盘对照和工程决策，代码也引用多条 KB 纪律；但当前选股运行时没有
“按场景检索指定 KB → 记录所用条目 → 量化其增益”的完整闭环。因此它**有用但尚未证明能提高选股结果**。

目标路由：

| 场景 | 可调用知识 | 用途 | 禁止事项 |
|---|---|---|---|
| 盘前/事件映射 | `KB-STOCK`、已验证的 `KB-TRADE` | 生成产业链与扩散候选、反例清单 | 示例条目不得当硬规则 |
| 盘中候选/买点 | 已落地或试验中的交易纪律 | 补充解释、风险与失效条件 | 不得越过数据/交易硬门 |
| 盘后复盘 | `KB-STOCK`、`KB-TRADE`、复盘框架 | 归因、发现反例、提出假设 | 不得用事后信息改写当时决策 |
| 系统进化 | `KB-DEC`、`KB-ENG`、治理册 | 防重复踩坑、约束实验和改码 | 不进入个股收益打分 |

每次决策快照记录 `scenario`、`kb_ids`、引用状态、支持/冲突依据、特征版本和 `as_of`。用有/无 KB 的
影子消融比较候选召回、Precision@K 与净期望；没有稳定增益时，KB 只保留解释/治理作用，不强行入模。

## 6. 自主运行、迭代与主动找漏洞

系统不依赖外部应用定时任务：后端进程的 `SchedulerRegistry` 负责常驻循环、死亡检测和状态查询，
`evolution-agenda` 每个交易日内部触发。自治闭环应按以下状态机运行：

```text
观察 → 异常检测 → 证据归档 → 假设 → 离线/影子实验 → 审核门 → 小流量晋级 → 监控/回滚
  └──────────── 证据不足或未通过 ────────────→ 保留研究，不改生产
```

主动漏洞发现至少覆盖：调度器死亡、缓存同键多回源、API 契约漂移、过期/未知数据被消费、规则零触发或
异常暴增、候选数跨端点不一致、提醒重复/漏记、结果标签缺失、因子分布/IC 漂移、文档与账本指针失效。
探针必须由独立事实面验证，不能由被测函数自己宣布健康。

权限边界：

- A 类参数实验：证据门槛、值域、预算、审计、自动回滚齐全后可自治；
- B 类 KB/文档：可写但必须有来源、状态与冲突记录；
- C 类代码：即使独立开关开启也只生成脱敏 patch + `evolution/*` 隔离提交，禁止修改测试、配置、迁移、
  凭据和治理文件，禁止合并/推送；落地走 `codex/*` PR、完整 CI 和人工/网页版审查；
- 永久禁止真实下单、删库、绕过交易硬门、伪造数据、输出确定性买卖结论；自治停机开关必须随时有效。

智能体目前已经在证据汇总、议程、告警判读和复盘中起作用，但还没有证明能带来稳定的策略增益。
它的近期成功标准不是“生成了多少建议”，而是建议的采纳率、实验通过率、缺陷提前发现数、误报率、
回滚率，以及经样本外验证的净增益。

## 7. 功能取舍与模块边界

- **保留但分权**：日选负责盘前计划，猎场负责盘中候选，买点负责即时提醒，模拟交易负责可成交验证，
  复盘负责结果标签；可以共用卡片和证据结构，不应把它们合成一个含义模糊的列表。
- **降噪**：watcher 中间态、板块异动、新闻和日选摘要保留为分析/审计数据，不再进入通知中心。
- **避免重复评分**：题材强度、个股确定性、可参与性、权限和风险分别输出，不压成一个无法解释的总分。
- **继续切片**：`theme_service.py`、`evolution.py`、`stock-detail.tsx` 仍偏厚；仅在行为契约和渲染回归齐备时
  按业务域拆分，不为“文件更小”改变接口。
- **补齐关键缺口**：决策快照/离线重放、统一结果标签、场景化 KB 路由、Champion/Challenger、
  消费影响视图、主动漏洞探针和真实盘中冷缓存验收。具体施工顺序只看账本 §6.0。

## 8. 分阶段交付与验收

| 阶段 | 目标 | 退出条件 |
|---|---|---|
| S0 稳定与降噪 | 数量一致、通知只发个股机会、受限自治真实启用 | 并发回归全绿；真实盘中冷缓存不抖；板块通知为 0；调度器可观测 |
| S1 可回放闭环 | 每个候选/过滤/排名/提醒都有 point-in-time 快照和结果标签 | 任一提醒可离线重放；未知/过期不可伪装；标签覆盖率可量化 |
| S2 研究升级 | 新颖性门、walk-forward、成本、校准、Challenger 影子运行 | 无泄漏守卫；分状态/分年度报告；晋级和回退可复现 |
| S3 KB 与自治 | 场景化检索、消融、主动漏洞探针、受控参数实验 | KB 增益可证或明确仅解释；异常可自动建议/回滚；代码仍不自动落地 |
| S4 体验收敛 | 一个注意力入口、少而准、原因与失效条件可见 | 通知预算/重复率/点击与处置反馈达标；页面不新增重复信息架构 |

建议长期 SLO：同键候选一致率 100%；过期数据冒充实时 0；板块通知 0；重复个股提醒率 <1%；
调度器死亡发现 <2 个心跳；所有生产策略 100% 有版本、样本外报告和失效条件。Precision@K、净期望和
最大回撤的目标值应由累计样本分布确定，不能在样本不足时拍脑袋写死。

## 9. 完成所需条件与主要风险

需要稳定运行的后端进程、可靠交易日历、带时间戳的数据源、足够长的逐时点快照、模拟成交结果、
可重复的评估算力和人工审阅 C 类 patch 的流程。若服务进程停止，内部调度也会停止；这不是“外部定时任务”，
但部署层仍需进程守护与健康告警。

最大风险依次是：数据泄漏造成虚假胜率、封板样本造成不可成交幻觉、小样本调参、同族指标重复投票、
LLM 解释被误当事实、自治权限漂移、提醒过载和用户只看胜率忽略盈亏比。上述风险均应通过硬门、版本化、
样本外验证、预算、审计和回滚控制，而不是依赖提示词自律。
