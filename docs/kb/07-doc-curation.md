# 文档整理方法论（Doc Curation Framework v1.1）

> **定位**：本项目 docs/ 与 .workbuddy/memory 的**文档治理规则**——回答"新文档放哪、什么算精华、怎么建索引、同类要不要合并、什么时候淘汰"。
> **与 06 的关系**：06-review-framework 管"知识怎么产出"（复盘 SOP）；本框架管"产出后怎么归档、串联、淘汰"。
> **性质**：流程规范，非交易知识——**无需市场有效性验证**，但按"先验证可行再迭代"原则，仍需**试运行后迭代**（见 §9）。
> **建库**：2026-09-10（用户指令：文档增多易散落，需分类/归纳/索引/整合/淘汰的成文规则）。

> **速览（30 秒版）**：新文档先按「归属三问」定层（§2）→ 沉淀必答「精华五要素」（§3）→ 新建必登记、互引须双向（§4）→ 同类 ≥3 份评估合并（§5）→ 三级淘汰、archive 只读不删（§6）→ 长度**按层配额** + **摘要前置**（§7）。
> **章节导航**：§1 分层模型 ｜ §2 分类与命名 ｜ §3 提炼与沉淀 ｜ §4 索引与串联 ｜ §5 整合 ｜ §6 淘汰 ｜ §7 长度与颗粒度 ｜ §8 参考 SOP ｜ §9 试运行与迭代 ｜ §10 附录 A 现状体检 ｜ §11 附录 B 整理候选 ｜ §12 版本记录

## 1. 分层模型：按"作用"而非"来源"分层

| 层 | 位置 | 放什么 | 权威性 | 典型示例 |
|---|---|---|---|---|
| **L0 权威知识** | `docs/kb/01~04` | 经复盘/实测验证的知识点（KB-STOCK/TRADE/ENG/DEC） | ⭐ 唯一权威 | KB-STOCK-24 缩量语义 |
| **L1 框架与规范** | `docs/kb/05~07` | 流程规则：仓库台账、复盘框架、本文档 | 流程权威 | 06-review-framework |
| **L2 总纲与设计** | `docs/` 根（无日期） | 系统总纲、架构、数据字典、现役设计 | 设计基线 | PROJECT-MASTER、architecture、api.md |
| **L3 专题报告** | `docs/` 根（**带日期**） | 单次调研/审计/复盘的分析结论 | 一次性证据 | board-fund-page-audit-20260910 |
| **L4 过程存档** | `daily-review/`、`evolution/`、`repo-watch/` | 逐日记录、进化日志、仓库发现轮 | 时间序列 | daily-review/2026-09-09.md |
| **L5 只读历史** | `docs/archive/` | 被取代的决策、已执行完的计划 | 只读（不删） | github-repo-audit-*.md |
| **L6 参考输入** | `docs/` 根 | 外部方法论/他人材料，**头部须标非权威** | 参考（不替代 L0）；**09-10 起同主题参考输入一律并入对应 KB 附录**（如五层提问框架 → `kb/06` 附录 A） |

**判定口诀**：先问"这是标准、设计、某次分析、过程记录、历史、还是外部参考"，六选一即可定层，不按作者或文件字数归类。

**与控制台「知识库」面板的对照（2026-09-12）**：上表是**治理口径**（7 层，用于归档决策）；
控制台面板呈现时聚合成 **4 桶**（`/api/agent/kb/tree` 的 `tier` 字段），因为界面只有
"默认展开 / 折起"两态，7 层平铺等于没分层：

| 面板桶 | 覆盖治理层 | 位置 | 界面行为 |
|---|---|---|---|
| `canonical` | L0 + L1（按目录聚合） | `docs/kb/` | 置顶，标「唯一权威」 |
| `current` | L2 + L3 + L6 | `docs/` 根、`docs/summary/` | 默认展开，按目录分组 |
| `history` | L5 | `docs/archive/` | 折进「历史与日志」 |
| `timeline` | L4 | `daily-review/`、`evolution/`、`repo-watch/`、`push-templates/` | 同上 |

⚠️ **`kb/05~07` 属 L1 框架，面板上归 `canonical` 桶**（与 L0 同目录、同权威档位呈现）——
桶是**呈现粒度**，不是权威性重排；引用时仍以 §1 的层为准。
未登记的顶层目录落 `current`（**故意选"多显示"方向**：新增目录宁可多占版面，也不静默藏入折叠区）。
对照逻辑与守卫：`backend/app/api/routes/agent.py::_DOC_TIER_DIRS` +
`backend/tests/test_agent_kb_tree.py`。

## 2. 分类与命名规则

### 2.1 归属三问（新文档落位）

1. 它回答"判断标准"吗？→ L0/L1（进 kb/，按 KB-ID 体系）
2. 它回答"系统长什么样/怎么建"吗？→ L2（docs 根，**不带日期**）
3. 它回答"某天发生了什么/某次调研结论"吗？→ L3（docs 根，**文件名带日期** `YYYYMMDD`）

### 2.2 命名规范（强制）

- **类型前缀统一**：`*-plan`（计划）、`*-audit`/`*-review`（审计/复盘）、`*-design`（设计）、`*-methodology`/`*-framework`（方法论/框架）、`*-research`（调研）
- **主文档不带日期**（会持续更新）；**报告类必带日期**（一次性结论，不可变）
- 日期格式统一 `YYYY-MM-DD` 或 `YYYYMMDD`，同一目录内保持一致

## 3. 提炼与沉淀规则（核心：不留整篇）

### 3.1 精华五要素（任何沉淀必须回答）

| 要素 | 说明 |
|---|---|
| **结论** | 一句话说清"学到了什么/决定了什么" |
| **依据** | 可验证的证据（数据/案例/来源日），禁"感觉" |
| **适用范围与反例** | 什么情况下成立、什么情况下不成立（防过度泛化） |
| **取代关系** | 它取代了谁 / 被谁取代（双向标注） |
| **遗留项** | 哪些没做完、被什么阻塞 |

### 3.2 开发完成后的文档处置（**v2.0 · 2026-09-10 用户确立，取代 v1「压缩归档」**）

> **用户原话**：「每完成一个功能点对应的方案后，请及时沉淀成果、提炼精华（**而非新增文档**），随后**可删除原始计划文档**……将以上流程确立为后续长期遵循的规范：功能完成后统一按此方式处理文档，**避免盲目新增文档**，而非沿用最初为开发实施计划而创建文档的做法。」

**核心原则：不为开发计划新建文档；方案落地即提炼、原件即删。**

四步（功能点完成**当轮**执行，不排队）：

```
① 沉淀  → 成果精华写进「已有的分类文档」：现役 L2 文档 / L0 KB 条目 / docs/summary/
          ⛔ 禁止新建文档承载成果
② 登记  → 没做完的部分写进 docs/retro-and-gaps.md §六（唯一待办总账）
          每条带「关键设计要点」（阈值/口径/挂载点），避免删件后信息丢失
③ 解引用 → 全仓 grep 原件名 → 同步更新代码注释 / 文档指针（零断链）
④ 删除  → scripts/safe-trash.sh（可 --restore 找回）
          docs/INDEX.md 与 plan-registry.md 标「已删除 + 精华去向」
```

**与 v1 的关键差异**：

| | v1（旧） | **v2（现行）** |
|---|---|---|
| 有未执行批次时 | 保留原件在 L2 标「进行中」 | **废止**——未做项提炼进总账，**原件照删**（防多份文档各写一半） |
| 归档方式 | 压成一页「精华页」入 archive | 精华直接进分类文档；原件直接删（git 历史 + 回收站双保险） |
| 触发条件 | 功能全落地 + 无未执行批次 | **策略更宽**：已落地部分可提炼 + 未做部分可入总账 → 即可删 |

**保留例外（仅两类）**：① 用户明确要求保留（如 `live-trading-guosen-plan.md` 未来蓝图）；② 属**现役基线/数据**而非方案（如 `picks-replay-baseline.md` 方法论基线）。

**⑤ 账本自身的瘦身（2026-09-12 补）**——上面四步管「方案文档」，本条管**账本自己**：

`retro-and-gaps.md` 是**待办总账**，不是功勋簿。「已完成条目」的逐条实施细节**不属于账本**——
它已在 `.workbuddy/memory/` 逐日日志与 git 历史里。判据就一句：**同一件事是否在两处记账**
（是 ⇒ 账本侧只留「里程碑一行 + 指针」，明细归逐日日志）。

- ⚠️ **下沉前必须先做「遗留承接」**：删完成记账时逐条检查该节是否夹带开放项
  （实例：旧 §二 #3「盘口 L2」、旧 §一「仅余 LLM 增强层（待凭据）」「只余通道接入」）——
  **开放项必须先迁进 §六、再删原文**，否则「整理」就变成「丢待办」（[[KB-ENG-36]] 同族）
- **编号只动非引用面**：全仓按 `§六` / `§6.2` / `§6.10` 引用的编号**一律不变**；
  被合并掉的编号（2026-09-12 的 §二/§三/§五）在文首写明「已取消」，不留悬空指引
- 落点：`retro-and-gaps.md` 511 → 453 行（54 行已完成明细下沉，2 项待决项补出口）

## 4. 索引与串联规则（防"躺在角落"）

### 4.1 双索引分工

- `docs/INDEX.md`：管**文档**——按"我要查 X → 去 Y"的问题导向组织（现役部分在 §0 使用地图）
- `docs/kb/00-INDEX.md`：管**知识点**——按 KB-ID + 状态（✅🔶⏳❌）组织

### 4.2 文档头元信息块（所有新文档强制）

```markdown
> 定位：一句话（这是什么、给谁用）
> 上游：[[被谁引用/依赖]]    下游：[[谁应该读它]]
> 状态：现役 / 参考（非权威） / 已归档（被 X 取代）
```

### 4.3 串联三纪律

1. **新建必登记**：任何新文档 → docs/INDEX.md 加一行（摘要写清"能回答什么问题"）
2. **互引必双向**：A 引用 B → B 头部"下游"补 A；被取代 → 新旧互相标注
3. **月度孤岛扫描**：站在任何文档都能沿索引找到它的上游/下游；无人引用且不索引的文件 = 孤岛，须处置

## 5. 整合规则（同类合并 / 必要时拆分）

### 5.1 合并三条件（同时满足才合并）

1. **同主题**（如全部是 GitHub 仓库审计）
2. **同产出模式**（同样是"评估某个对象并给结论"）
3. **同受众与用途**（都是给选型决策用）

→ 合并为一份**主文档 + 附录表**，原文档各压成一节或归档。

### 5.2 拆分三条件（满足其一即拆分，但必须有共同索引页）

1. 单文档**超过所在层阈值**（§7 分层配额）且主题可分离
2. 服务于**不同时点**的决策（不能对话的活文档 vs 一次性报告）
3. 更新频率差异大（活的规则 vs 冻结的结论）

**注意（用户明确）**：同一类型**不是**只能保留一份——按"分类维度"可多份（如按时间/按子系统），但**必须有一个共同索引页**串联，否则退回散落状态。

## 6. 淘汰规则（三级处置 + 安全护栏）

| 处置 | 适用 | 动作 |
|---|---|---|
| **保留** | 现役规则/总纲/时间序列/基线数据 | 留在原层，保持登记 |
| **提炼后删除**（现行主线） | 已落地的计划/方案——**含仍有未做项者** | 按 §3.2 v2：精华进分类文档 + 未做项进总账 → **删原件**（可 `--restore`） |
| **归档**（历史留痕） | 被取代但仍需追溯的决策文档 | 移入 `archive/`（只读，不删） |

### 6.1 删除判据（**分两类，A 类已降门槛**）

**A. 计划 / 方案类（常规动作，落地后即删）** —— 满足 ①②③ 即可：

1. 成果精华已进分类文档（`summary/` / 现役 L2 / L0 KB）
2. 未做项已进 `retro-and-gaps.md` §六（含关键设计要点）
3. `grep` 全仓**无活引用**（INDEX / plan-registry / retro 处置表里的**记录性引用可保留**）

**B. 其他文档（保守，四条件全满足才删）**：

1. 关键结论已进 L0/L1（可检索到）
2. 无独有信息（数据、参数、历史决策理由均已转录）
3. `grep` 全仓无引用（含 docs/、代码注释、memory）
4. 超出时效窗口（报告类 > 1 年、审计类 > 半年）

### 6.2 安全护栏（不可越）

- **删除一律走项目回收站，禁止 `rm`**（2026-09-10 用户纪律）：`scripts/safe-trash.sh <路径> --reason "..."` → 移入 `.workbuddy/trash/YYYY-MM-DD/`（保留原相对路径 + MANIFEST 留痕），`--list` 查看、`--restore` 找回。
  - **为何不用系统 `trash` 命令**：⚠️ **09-10 当天已更正**——并非"假进废纸篓"，文件确实进了 `~/.Trash`（用户从 Finder 实见）；真相是本进程受 **macOS TCC 限制读不到 `~/.Trash`**（`ls` 报 `Operation not permitted` 并静默返回空），当时把"读不到"误判成"没进去"。**教训：受限导致的假阴性不能当事实**（同 shell grep 假阴性）。项目内回收站的真正价值：可验证、可 grep 追溯、不依赖 TCC 授权，且 MANIFEST 留删除原因。
  - **archive/ 只读不删**（历史决策防回退，参考 KB「永不删除条目」原则）
- 删除前**逐个 grep 复核引用**（项目既有纪律）
- 批量删除/移动**须用户确认**，不擅自执行
- 淘汰动作留痕：在今日 memory 日志记一行（删了什么、为什么、结论去哪了）

## 7. 长度与颗粒度规则（v1.1：按层配额，非一刀切）

**原则**：行数不是目的，"可被完整消费 + 30 秒可判断相关性"才是。三类文档的"长"性质不同，**用三种不同维度约束**，不用统一上限。

| 层 | 约束维度 | 阈值 | 超标动作 |
|---|---|---|---|
| **L0 KB 分类文件** | **条目级**（总行数不限） | 单条 KB 条目 ≤ **60 行** | 条目超长 → 拆知识点；文件 > 800 行 → 评估按子类拆文件 |
| **L1/L2 框架·总纲·方法论** | 文件级软上限 | **500 行** | 拆"索引页 + 分册" |
| **L3 专题报告** | 文件级软上限 | **600 行** | 长表外移后仍超 → 拆分册 |
| **L4 日志（append-only）** | **单轮新增**（不设总行数） | 单轮新增 ≤ **80 行** | 超量说明未精炼；30 天前内容按维护规则蒸馏进 MEMORY |
| **表格** | 单表行数 | **30 行** | 转附录或 `data/` CSV，md 只留结论表 |
| **L5 archive** | 不设限（冻结） | — | — |

**为什么按层而非一刀切（v1.0→v1.1 的修订依据，2026-09-10 实测）**：

1. **300 行的真实含义**是"可被完整消费"阈值（≈4–6k tokens，人/模型都能一次读完不跳读）——它适合规则型文档，不适合所有类型。
2. **累积型文档行数 ≠ 质量**：KB 分类文件靠 `grep docs/kb/` 一次搜全，按行数拆会破坏该价值 → 改管"单条目长度"。
3. **时间序列不该管总行数**：日志长 = 那天工作量大（实测最长 1072 行），拿行数管只会逼人删证据 → 改管"单轮新增精炼度"。
4. **该防的是"长而无结构"**：实测最长的两份（883/441 行）问题都是**长表塞 md**，而非行数 → 靠"长表外移 + 摘要前置"解决。
5. **拆分有成本**（断引用、散检索）：阈值过低导致频繁重组，维护负担反升 → 文件级阈值定为 500/600。

**摘要前置（比行数更有效的硬约束）**：
- 凡 **L1 框架 / L2 总纲·设计 / L3 报告** 中 **>150 行**的文档，**前 40 行必须是**：
  结论摘要 + 适用范围 + 目录/章节导航
- 目的：跳读者先看首屏即能判断相关性；检索命中后不读全文也能定位
- **适用范围与例外（2026-09-10 澄清，原文"凡 >150 行"与 §7 表的「按层配额」自相矛盾）**：
  | 对象 | 是否适用摘要前置 | 依据 |
  |---|---|---|
  | L1/L2/L3（框架·总纲·报告） | ✅ 适用 | 它们要被"跳读定位" |
  | **L0 KB 分类文件** | ❌ 不适用（改用文件头「速览与导航」+ 条目级 ≤60 行） | §7 表：KB 层约束维度是**条目级**，管文件级摘要会与它冲突 |
  | **L4 时间序列**（daily-review / evolution / repo-watch） | ❌ 不适用 | 按时间顺序消费，逐日"摘要"无意义；且 append-only 不改历史 |
  | L5 archive | ❌ 不适用 | 冻结只读 |
- **检查方式**：`python3 scripts/doc-health.py` 的 D 项（已把上表例外编码进去），不再靠人工抽样。
  首跑实测（2026-09-10）：修复前 9 份缺失 → 按例外重算后仅 3 份真缺，已补齐 → 现 0 份。

**颗粒度通则**（不变）：
- 一篇一主题；一节一结论（节首句即结论，后接证据）
- 30 秒判断标准：靠头部定位块（§4.2）+ 摘要前置

## 8. 参考 SOP（**参考模板，可按实际裁剪；非摆设要求见 §9**）

### 8.1 单文档整理（约 15 分钟）

1. 读头部定位块 → 判定层次（§1）
2. 抽精华五要素（§3.1）→ 写入 L0/L1 对应位置
3. 更新引用（§4.3 双向）
4. 原文档按处置表（§6）保留/压缩/申请删除

### 8.2 文档体检（**已脚本化**：`python3 scripts/doc-health.py`，收尾必跑）

> 2026-09-10 起本节由**人工 30 分钟**降为**一条命令**（`scripts/doc-health.py`）。动机：规则只是文字时，

- **「机械迁移」往往不机械**：把挂载取数迁到 `usePollingFetch` 时发现该钩子**只在 `intervalMs` 变化时重跑**——参数会变的取数（如按 `code`）迁过去会**静默漏刷新**。→ 给钩子补第三个 `key` 参数，并在 docstring 写明"参数会变必须传 key"。**教训：复用既有抽象前先读它的依赖语义，别把"看起来一样"当"行为一样"。**
- **同一 lint 规则下的现场是多种模式**：`set-state-in-effect` 的 20 处里，有挂载取数、有派生状态、有 SSR 安全的外部读取、有加载态重置——**必须逐处分类**（对应的修法完全不同），一刀切会改坏行为。
- **验收必须落到真实渲染**：UI 改动完成后用 agent-browser 实测了 4 个页面 + 深链 + 抽屉开合（含"徽标 60 → 空"这类可观察断言），而不是只看 lint 变绿。

**本轮暴露的方法论自身缺陷（已就地修正）**：
1. **规则与规则冲突**：§7「摘要前置＝凡 >150 行」与同节「按层配额（KB 用条目级）」**自相矛盾**——按前者，

3. **"排除记录性引用"会过度排除**：archive/逐日日志内部的引用天然指向"当时存在的文件"，

- **文档治理必须有机制承载**：规则写在 md 里不等于会被执行；**能脚本化的检查一律脚本化**

  两者混用是"示例被当方法论"的**技术成因**（比主观误读更常见）。
