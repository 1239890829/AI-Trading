# 验证层陷阱（KB-ENG）· 测试 / 门禁 / CI / 环境

> 定位：**你用来「验证」的东西本身会骗你**——测试跑绿不等于接上了线、门禁跑绿不等于覆盖到了路径、
> CI 跑绿不等于测了真实环境。含「防线（守卫 / 上界）到底有没有在生效」的判据。
> 与 `08-tooling-pitfalls.md` 的分工：那边是**怎么用工具**（操作速查，每条 3~5 行）；
> 这里是**验证结论可不可信**（系统性教训，每条 10~35 行）。
> 共同索引页：`00-INDEX.md`（KB-ENG 全序列唯一登记处，按 tag 检索，**不分文件**）。

### KB-ENG-19 测试不得写真实仓库路径：_EVOLUTION_DIR 锚定仓库根，必须注入隔离
- **事故**（2026-09-09）：`tests/test_evolution.py` 的 B 类夹具（"watcher 阈值偏松"/"沉淀今日结论"）
  经 `_execute_b` 写入 `_EVOLUTION_DIR`（= 真实 `docs/evolution/`），**每次 pytest 全量都向真实
  `docs/evolution/当天.md` 追加**——单日累计 84 行垃圾（09-08 也 85 行），进化日报不可读。
- **根因**：`PROJECT_ROOT = Path(__file__).parents[3]` 锚定真实仓库根；测试 patch 了 DB 会话
  却没 patch 文件路径 → "DB 隔离了、文件没隔离"。
- **修复**：sf fixture `monkeypatch.setattr(evo, "_EVOLUTION_DIR", tmp_path/"evolution")` +
  回归测试 `test_b_class_never_touches_real_evolution_dir`。
- **通用教训**：凡是"模块常量指向真实仓库路径"的写入口，测试 fixture 必须一并隔离；
  只隔离 DB 不隔离文件 = 半吊子隔离。清理时保留 evidence 非空的条目（垃圾特征：`依据：{}`）。
- **延伸**：[[KB-ENG-63]]——本条是"自己的测试写自己"，那条是**别的测试间接触发**打断链路
  （扫荡式 openapi 冒烟 → 端点 → 缓存落盘），隔离位置也随之上移到 **conftest 单点**。

### KB-ENG-42 模块有测试 ≠ 接线有测试：完成度看「消费方」，不看「库」
- **背景（2026-09-11，P1-24 分钟决策库）**：`app/market/minute_decisions.py` **库本体完整**
  （触发即记录 / 30 分钟窗口结算 / leave-one-out 错误归因 / 4 态 outcome），**6 项单测早已全绿**，
  表也建好；但全仓 grep 后，除自身外**零生产调用方** ⇒ 库内仅 **1 行**（08-31 手工跑出、
  从未被触发）。任务台账写「已完成」，实际只是「库写完」。
- **判据（一句话）**：**一个模块的完成度 = 它的消费方（谁调用、何时调用、结果给谁看），
  不等于它的实现与单测。** 库级测试证明「算得对」，接线测试才证明「真的会算」。
- **自检命令**：grep 该模块名在 `backend/app` 下的**导入点**——命中数为 0、
  或只有「它自己 + 本次新加的入口」，即说明尚未接线（**入口数就是完成度的直接证据**）。
- **接线时才暴露、且模块测试永远抓不到的三类缺陷**（本轮实测，都不是测试写错）：
  1. **导入路径写错**（`beijing_today` 实际在 `app.sentiment.metric_history`，接线处写成
     `app.market.trading_status`）——模块测试直接构造入参，**根本不走这个导入**；
  2. **模块边界的类型契约无测试**（引擎已把结果 `model_dump()` 成 dict，接线方仍调
     `.model_dump()` → 整条链 `AttributeError`）——**返回类型是调用方的假设，不是模块的承诺**；
  3. **响应层同款假设**（端点把 `out["signals"]` 当模型列表）——同一错误在两个调用点各犯一次。
- **正解（写进「新模块」的验收清单）**：
  ① 模块测试之外**必须有一条真实调用链**（触发源 → 模块 → 出口），并在测试里覆盖**调用方**
  （哪怕只是契约断言：返回类型、字段齐备、三态值域）；
  ② 接线缺陷**不能只靠「手工点一次页面」**发现——本轮 3 个缺陷全部由**新写的接线测试**逼出；
  若只点页面，`AttributeError` 会拖到盘后才炸，且被调度处的 try/except 吞成一行 warning。
- **关联**：[[KB-ENG-41]]（枚举里存在 ≠ 已实现；同族：「写完了」≠「接上了」）[[KB-ENG-37]]

### KB-ENG-46 被 `except` 吞掉的"守卫"是死代码：必须用测试钉住它**真的在跑**
- **背景（2026-09-11，同上补跑撞出）**：`_calendar_days_ms()` 负责给增量同步算滞后
  交易日数，实现里写 `days = trading_days()`，而真实签名是
  **`async def trading_days(provider, lookback_days=120)`**——**缺 provider 且未 `await`**，
  必然抛 `TypeError`，被外层 `except` 接住后只 `print` 一行 warn 并返回 `[]`。
  调用方看到空列表就**跳过**「滞后 >7 交易日则拒绝增量、强制 `--full`」的门槛
  ⇒ **这道保护从写下那天起就没生效过**。
- **这类缺陷的杀伤力在于"运行日志看起来完全正常"**：它每天照打一行 warn，
  既不报错也不影响功能，**只有在真的需要它拦一次的时候才会发现是空的**。
  ⇒ 与 [[KB-ENG-33]] 的「跳过原因必须具名」是同一族，但更进一步：
  **不是"没说清为什么跳过"，而是"根本跳过了、还留了个像模像样的理由"**。
- **三条防线（本轮全用上）**：
  1. **测试直接调那个函数**，断言它返回**非空且语义正确**——
     而不是只断言"不抛异常"（抛异常被吞掉正是原状）。再补一条**过期日历补足**用例，
     钉住兜底分支真的走工作日填充。
     > ⚠️ **2026-09-12 订正**：本条原先写的是「末元素**等于今天**」，这句本身就是错的
     > ——本函数产出的是**交易日**序列，今天非交易日（周末/节假日）时不追加，
     > `out[-1]` 恒为「≤ 今天的最后一个工作日」。照原话写出来的断言在**每个周末必挂**
     > （参见 [[KB-ENG-56]]：错误处方会被后来人一字不差地抄进测试）。
     > 正确断言：`out[-1] == ms(≤ 今天的最后一个工作日)` **且** `out[-1] <= ms(今天)`（上界防"补到今天之后"）。
  2. **反漂移断言**：把源码读出来断言不再出现旧的错误调用形态
     （`assert "days = trading_days()" not in src`）+ 断言正确的新写法在
     （`assert "_load_persisted()" in src`）。廉价，但能挡住"下次重构又改回去"。
  3. **端到端可见性**：修完后真实跑一次同步，确认日志里**真的打印了**
     跳过的那个量（本轮 `[freshness_lag_days] 1`）——**"门在跑"必须有外部可观测证据**，
     否则等于换了个安静的失败方式。
- **修复选型上的一个纪律**：CLI 脚本没有事件循环也没有 provider，不要为了迁就错误
  签名去**造一个 provider**（引入网络依赖与不确定性）；应当改用**同源但同步的**入口
  （`trade_calendar._load_persisted()`，与 `marketdb_freshness.trading_day_lag` 同源
  ⇒ 口径单点收口，见 [[KB-ENG-44]]），并在日历落后时用**工作日兜底**（宁可多报滞后）。
- **可迁移判据**：凡「守卫 / 校验 / 门槛」类代码，问一句
  **「它失败时会怎样？」**——如果答案是"被 except 吞掉后静默放行"，那它就是死代码。
- **关联**：[[KB-ENG-44]] [[KB-ENG-33]] [[KB-ENG-45]] [[KB-ENG-06]]

### KB-ENG-47 门禁工具本身也会**假阴性**：先怀疑工具，再怀疑被测对象
- **背景（2026-09-11 门禁取证，两个现象都不是代码问题）**：全量 pytest 跑完 `exit=0`，
  但日志里**找不到 "N passed" 统计行**，差点被判成"没跑完"；同一时刻
  `.pytest_cache/v/cache/lastfailed` 里躺着 **2 条失败记录**，又差点被判成"其实有失败"。
  两个现象**都源自工具链**：
  1. **静默档位叠加**：`backend/pyproject.toml` 已经设了 `addopts = ["-q"]`，
     命令行**再加一个 `-q`** ⇒ 实际生效的是 `-qq` ⇒ **统计行（含 "N passed"）被整体抑制**。
     ⇒ 要数字就**不要在命令行重复 `-q`**（本项目配置已含一个）。
  2. **缓存跨轮累积**：`lastfailed` / `nodeids` 由 `_pytest.cacheprovider` 维护，
     **通过的用例会被移出 `lastfailed`，但已删除/改名的 nodeid 永远不会被清理**
     （`nodeids` 更只是 `union`，从不删除）⇒ 缓存条目**不能当作"本次运行的结果"**。
     本次两条记录经 grep 确认：测试名在代码里**早已不存在**（模块还在，用例已改名）。
- **处置纪律（两条都要做，缺一即误判）**：
  - 判「有没有失败」只认**退出码 + 进度字符**（出现 `F` / `E` 即为失败），**不要读缓存文件**；
  - 判「某个 nodeid 是否存在」必须 **grep 源码**，**不能问缓存**。
- **可迁移判据**：**受限/陈旧造成的假阴性不能当事实**——与 shell `grep` 假阴性、
  读不到 `~/.Trash` 就当"没进废纸篓"是同一族错误。
  当一个结论只能由某个"看起来权威"的工具产物推出时，先问三句：
  **它是什么时候生成的？以什么口径生成的？它会不会保留陈旧内容？**
- **关联**：[[KB-ENG-46]] [[KB-ENG-37]]

### KB-ENG-52 三条"看着无关"的静默陷阱：注释提前闭合 / 测试依赖共享状态 / pyflakes 不认 noqa
- **① JSDoc 里写 `**43/83/87/88**/92` 会提前闭合块注释**——`**/` 里含有 `*/`。
  症状极具误导性：**报在打包器 transform 阶段**（`vite:oxc` 提示 "Try inserting a semicolon here"），
  测试统计显示 `Tests no tests`（整个文件没被解析，看起来像"测试全丢了"）。
  ⇒ 注释里描述代码段清单时**别用 `**` 加粗包裹含斜杠的列表**（用空格分隔即可）。
- **② 测试不许依赖「表恰好还没建」这类副作用**——否则**通过与否取决于执行顺序**。
  实例：新用例把 `_sf` 设成真实可用 sessionmaker，只 patch `core_db.get_session_factory` ⇒
  **只拦到真实持仓那一路**，模拟持仓那路照常成功。单跑（表未建，两路都抛 `no such table`）出 2 条、
  全量跑（前序用例已 `create_all`）只出 1 条。
  ⇒ **「单跑绿、全量红」第一件事是查测试对共享状态的隐式依赖**，而不是怀疑被测代码；
  修法是让每条路径**显式注入失败**，与顺序无关（本项目还为顺序无关性补了混序复跑验证）。
- **③ pyflakes 不认 `# noqa: F401`**（那是 flake8 的语法）⇒ 为"导入即副作用"写的 noqa
  会被直接报 `imported but unused`，门禁红。改法：**顺手断言该名字**，既用掉名字也把
  「导入是刻意的」写进测试（如 `assert RealTrade.__tablename__ == "real_trade"`），
  比 `__all__` 或 `_ = X` 更有信息量。
- **关联**：[[KB-ENG-47]] [[KB-ENG-50]]

### KB-ENG-53 测试与前端环境的六条「静默失败」——都无报错、都只在特定条件下现形
- **① pytest 必须显式 `--basetemp`**：不带时默认目录 `/private/var/.../pytest-of-unknown` 被沙箱 shim 拒绝 ⇒ `PermissionError: EEXIST ... mkdir`，表现为**几十个 E 而不是 F**，极易误判成"刚才的改动把后端弄挂了"。纪律：**E 成簇出现在开头 → 先怀疑环境，不要先怀疑代码**；本项目统一 `pytest --basetemp=/tmp/pytest-basetemp`。
- **② SQLite 的 datetime 过滤必须传 datetime 对象**：库里存的是空格分隔格式（`2026-09-11 09:30:00`），与 ISO 字符串 `2026-09-11T00:00:00` 字面比较**恒 False** ⇒ 过滤条件形同不存在、防线静默失效（预算防线曾因此长期不生效）。统一走 `evolution._utc_cutoff_today()` 这类单点入口，不要各写各的字符串拼接。
- **③ 滚动加载哨兵必须挂在滚动容器内部**：放在容器外时它不随列表滚动，`getBoundingClientRect` 恒定落在视口内 ⇒ **首帧补载一页后再不触发、静默卡在第 2 页**（无报错、无告警，最难查的一类）。`<ul>` 内嵌入时需外包 `<li>` 保持嵌套合法。
- **④ 列表项 memo 化的两个前提缺一即全失效**：回调必须 `useCallback` 固定、数据必须 `useMemo` 稳引用（反例：heatmap 1540 格 hover 全量重渲染，根因就是引用每次都是新的）。
- **⑤ 复用既有抽象前先读它的依赖语义**（不读就复用的代价是静默漏刷新）：`usePollingFetch` 只在 `intervalMs` 变化时重跑 ⇒ **参数会变的取数必须传第三参 key**。
- **⑥ 扫「跨文件未引用导出」默认要排除测试文件** ⇒ 直接照单删会删掉只被测试引用的导出（如 `navUrlForAlias`）；**必须把测试纳入扫描再逐项 grep 复核**，并区分「真死代码」与「只是 export 暴露过宽（本文件内部在用）」。
- **判据**：这六条的共同形态是**「没有错误、没有告警、结果看起来正常」**（甚至"数量对不上"也被解释成"本来就该这么多"）⇒ 凡"改完没变化"或"数量对不上"，先按本表逐条排除环境与复用前提，再去怀疑被测代码。
- **关联**：[[KB-ENG-01]] [[KB-ENG-04]] [[KB-ENG-47]] [[KB-ENG-51]] [[KB-ENG-52]]
- **延伸**：[[KB-ENG-62]]——本条是「测试与前端环境」的静默失败，那条是**部署型自动化**
  （launchd/cron）的静默失败：「装了」不等于「在跑」，且判据在**运行次数与退出码**上，不在文件是否存在。

### KB-ENG-54 加了一层「守卫 / 上界」之后，真正的风险是**没覆盖到的那些路径**（S1-4 / S2-3）
- **形态**：保护逻辑只挂在**其中一条**执行路径上，其余路径静默绕过——守卫"看起来在跑"。
- **实例①（S1-4 涨跌停守卫，触红线 5）**：`place_order` 与 `match_pending` 是两条独立成交路径，历史上只有前者做了拦截 ⇒ 挂单在股价冲上涨停后**仍按现价成交**（等于在涨停板买入）。修法：判据抽成唯一函数（`limit_block_reason`），两条路径都调。**同族写法**：`if quote.limit_up_price and ...` 在限价 `None`/`0` 时整体短路——**缺值被当成"不需要校验"**；限价来自单源补价、曾真实被中断，所以"缺失"是**会发生的状态**而非异常路径 ⇒ 必须取保守侧（判不了就不放行）并配可见的拒单原因。
- **实例②（S2-3 请求预算）**：给 `_call_serial` / `_call_hedged` 加 `deadline` 参数时**顺手给了默认值 `None`**，4 处调用点漏改 1 处 ⇒ 那条路径整条绕过预算（实时对冲回落的串行段静默跑满 30s，**只有测试抓到**）。**修法不是补这一处，而是把参数改成必填**——让漏传在开发期 `TypeError`，而不是静默降级。
- **实例③（2026-09-11 事件循环阻塞）**：同一个 async 调度循环里**相邻两个 `if` 分支**各调一个同步重 IO 函数，只给其中一个包了 `asyncio.to_thread` ⇒ 另一个把事件循环卡住（连累 QuoteHub 的 1s 行情节奏）；同批另查出 `async def` 里直调同步函数（内部链到 `duckdb.connect` + 多路 SQLite 全表读）。**修法不是"记着下次包"**：新建 `tests/test_event_loop_no_block.py`，把调用点做成**一张表**（新增点只加一行，不再逐个写测试文件），断言分**正向**（`to_thread(<fn>)` 必须存在）+ **反向**（不得另有未包裹的 `<fn>(`，按行前缀判定以排除 `def` 定义行）——**只做正向时，在别处再抄一行裸调用依然全绿**；两道都注入幽灵值实测过（正向只抓"去掉 to_thread"，反向才抓"另加一处裸调用"）。⚠️ **反向还要防自己的实现漏洞**：首版用 `prefix.strip().startswith("def ")`，`strip()` 把 "def " 的尾空格也吃掉 ⇒ 所有函数定义行被误报为裸调用；改用**整行** `line.strip()` 判定。
- **纪律**：任何"加了保护"的改动，收尾必答三问——① `grep` 出**全部**调用点，确认都经过它；② 用测试钉住**最常走的那条**（不是只测新写的那条）；③ 保护被触发时必须有**可见出口**（拒单原因 / 结构化字段 / 哨兵 issue），否则等于没有。
- **判据**：「**判不了**」必须与「**不需要判**」在代码里分开表达——前者取保守侧并报出来，后者才放行。
- **关联**：[[KB-ENG-46]] [[KB-ENG-42]] [[KB-ENG-44]]

### KB-ENG-56 断言若由**真实运行日**驱动，就只在特定日历日变红——「一周 5/7 是绿的」等于没写守卫

- **背景（2026-09-12 00:15 全量 2 failed，根因同源）**：①`assert out[-1] >= 今天`（实测 09-11 vs 09-12）；
  ②`assert real_days[-1] >= 今天`。**当天是周六**——交易日历只装交易日，末元素必为周五
  ⇒ 两条断言在**每个周末与每个长假**都挂，一周里 5 天是绿的。
- **归属判定**：**产品口径正确，断言写宽**。`_calendar_days_ms` 与 `marketdb_freshness.trading_day_lag`
  同源约定「非交易日不追加、周内工作日兜底、宁可多报滞后」；调度器拒绝在周六生成议程**也是对的**。
- **两类错误前提（可迁移）**：
  - **①把"日历覆盖交易日"写成"日历覆盖今天"**：日历的语义是交易日集合，"覆盖"只能按**交易日**判。
  - **②把"运行日"当成"测试夹具"**：`test_scheduler_*` 的主题是「时钟跨过 15:45 是否触发」，
    与"今天是否交易日"**正交**；用真实今天当时钟起点，就把两件正交的事绑死了。
- **修法（均不碰产品逻辑）**：
  1. **基准日做成可注入参数**：`_calendar_days_ms(limit=400, *, today=None)`，`None` 才取 `now()`。
     **范式照抄既有的 `trading_day_lag(latest, asof)` / `freshness(asof=)`，别另发明**。
     附带修掉跨零点竞态：此前**测试与实现各取一次 `now()`**，跨零点会落在不同日期。
  2. **夹具锚到「日历里真实存在的交易日」**：`probe_day = real_days[-1]`，并断言
     `last_trade_date(real_days, asof=probe_day) == probe_day`（把选它的理由写进断言）⇒ 与运行日解耦且不丢真实口径。
- **必配定点回归**（否则修完仍是"只有周末才有效"）：周六→周五；**周日→同样周五**；
  **工作日节假日（如 2026-10-01 周四）会被刻意补上**（该取舍若改，必须连 `freshness` 一起改，不能只改一处）；
  **补负向用例**——原有覆盖只测"交易日必须触发"，**"非交易日必须不触发"无人守**，本次暴露的恰是这一侧。

### KB-ENG-60 门禁的「扫描面」也是口径：写窄的 glob 会让新对象**根本不进检查**，症状是全绿

**发现（2026-09-12，KB 分册时）**：`doc-health.py` 两道 KB 检查都用 `glob("0[1-9]*.md")` 选文件
⇒ **只覆盖 `01`~`09`**。本次要新建 `10-…md`，实测该文件**不会被任何检查看到**（条目超长不查、
>800 行提示也不出）。**这不是「检查失败」而是「根本没进检查」，所以输出与通过完全一样——全绿。**

**同族的三个已修项**（都是「扫描面被写窄」）：`check_dead_links` 只扫 `*.md` ⇒ 漏代码注释指针（故补 **F**）；
F 只认 `docs/xxx.md` ⇒ 漏裸名（故补 **F2**）；本项漏 `10+` ⇒ 补覆盖守卫。

**正确做法三条**：①扫描面**收成一个入口函数**（`kb_classified_files()`），多处共用，
避免各写各的 glob 而只改到一处；②配**覆盖守卫**——枚举全部应扫对象，凡「没被任何检查覆盖」
即 FAIL（`kb_file_coverage_gap`），使「新增即自动纳入」**不依赖有人记得改 glob**；
③**门禁触发要量假阳性再定档**：F3 的宽版（同行出现即比对）实测 **23 命中 / 0 真阳性**
（全是逐日日志的记录性引用与长句巧合）⇒ 会变成「永远红的门禁」（[[KB-ENG-58]]），
故只留窄触发（实测 1 命中 / 0 误报）。

**判据**：写「全覆盖」类检查时先自问——**「新增一个对象，它会自动被扫到吗」**；
答不上来就必须配覆盖守卫。**「没进检查」与「检查通过」在输出上不可区分**，这是本类缺陷的全部危险性。

**配套（结构重排的自检法）**：拆分/搬家类改动**不要靠肉眼或脚本自证**——把原件副本留一份，
拆后**逐条目取哈希比对**（本例 44 条全部逐字节一致、零丢失零重复、编号无缺号），
比「看起来搬对了」可靠得多；且「只搬位置不重写」本身就让核对变得可执行。

### KB-ENG-62 安装型自动化（launchd / cron）的「装了 ≠ 在跑」：验活必须读**运行次数 + 退出码**

- **事故**（2026-09-12）：`com.ashare.review`（16:30 独立盘后复盘，`claude -p` headless）
  自 09-09 装进 `~/Library/LaunchAgents/` 后**已加载、已触发 4 次、全部失败**，
  **从未产出过任何复盘**——而 plist 注释与账本一直把它写作「已落地」的自动化。
  旁证：`docs/daily-review/` 里最后一个 agent 版复盘正是 `2026-09-09-agent.md`，此后再无。
- **根因**：项目位于 `~/Desktop`（macOS **TCC 保护目录**，`ls -ld@` 显示 `drwx------+`），
  launchd 启动的进程**没有该目录的访问授权** ⇒ `/bin/bash: <脚本路径>: Operation not permitted`
  ⇒ **exit code 126**。
- **三条「看起来能跑」的伪证据**（本轮逐条被证伪）：① 脚本有可执行位（`-rwxr-xr-x`）；
  ② plist 位于 `~/Library/LaunchAgents/`（安装位正确）；③ `run.log` 里有「复盘完成」字样
  ——那是**手动**跑的那次留下的，与定时是否成功无关。
- **验活三问**（缺一即「不知道它在不在跑」）：
  1. `launchctl print gui/$UID/<label>` 读 **`runs`** 与 **`last exit code`**；
     `state = not running` 只说明「此刻不在跑」，**不能**推出「跑过并成功」。
  2. ⚠️ **不要用 `launchctl list | grep <label>` 判「未加载」**——本轮据此得出的「未加载」
     是**误判**（job 其实已加载），精确查询 `launchctl print` 才作数。
  3. 读**产出目录**最新文件的日期，与「理论上应该在跑」的日期对齐（本项 = `docs/daily-review/`）。
- **判据**：「装了」「有执行位」「日志里有成功字样」都**不构成本在跑的证据**；
  只有 **`runs` 递增 + `last exit code = 0` + 产出目录有新文件** 三者同时成立才算。
- **退出码字典（省一轮排查）**：`126` = **找到了但不可执行**（TCC 拒绝 / 无执行位）；
  `127` = 命令找不到（PATH 缺，launchd 的 PATH 极简）；`78` = 配置错误（`EX_CONFIG`）。
  ⚠️ **EPERM 与 EACCES 要分开认**：报 `Operation not permitted`（EPERM）指向**沙箱/TCC**，
  报 `Permission denied`（EACCES）才指向文件权限位——两者修法完全不同。
- **零成本直证法**（本轮实践）：`launchctl kickstart -k gui/$UID/<label>` 主动触发一次，
  再比对 **`runs` / `last exit code` / 产出日志的 mtime**。三项联读可**区分两种失败**：
  退出码变化但产出日志 mtime 不变 ⇒ **脚本零执行**（在打开文件时就被拒，权限问题）；
  产出日志有新增 ⇒ 脚本跑起来了，失败在更深处。选**非交易日**触发最安全
  （脚本会被自己的交易日判定拦下，不产生真实副作用）。
- **同类面**：凡「脱离主程序独立运行」的机制（launchd / cron / 系统计划任务 / 第三方调度）
  都要走这套验活。**主程序内的调度另有权威入口**——本项目的 `SchedulerRegistry`
  提供 `GET /api/system/schedulers`（逐任务状态 + 死亡进哨兵，[[KB-DEC-021]]）；
  **能进主程序调度就不要另起独立机制**，后者天然缺少状态出口。
- **关联**：[[KB-ENG-53]] [[KB-ENG-57]] [[KB-ENG-47]] [[KB-DEC-021]]

  **子串存在性断言对「值的方向对不对」完全不敏感**，桩数据 + 单测全绿。
- **为什么被抓到**：**真实数据跑一遍看见了**（「验收以实际渲染为准、禁推理代替观察」的又一次应验）。
  ⇒ **桩数据能证明「跑得通」，不能证明「读得对」**；凡新增面向人的数值输出，至少跑一次真实数据。
- **修法（两层）**：①格式化按量的语义分档——**有方向的量**（区间收益 / 超额 / 年化 / 样本内外）
  带符号；**无方向或天然负极的量**（最大回撤 / 波动率 / 胜率 / 盈亏比）**不带**；浮点一律定小数位。
  ②给每档配**方向性断言**：`assert "最大回撤 +" not in out`，而不只是 `"最大回撤" in out`。
- **通用判据**：**写任何数值呈现之前先问一句「这个量有方向吗」**——答案不同就必须走不同格式函数。
  **存在性断言 ≠ 正确性断言**：凡涉及符号、单位、量纲、口径的呈现，都要有一条**能被注入验证打红**的断言。
- **关联**：[[KB-ENG-58]]（口径类改动三步：先量影响面）· [[KB-ENG-47]]（门禁取证只认退出码 + 统计行）·
  [[KB-ENG-19]]（同族：防线自己会错，只有注入验证能发现）


### KB-ENG-65 三种「假绿守卫」形态：桩缺方法 / A-B 对照盲区 / 注入只改注释
- **事故群**（2026-09-12 评审批次 3，同一轮里连踩三例，**都在"守卫看起来在守"时发生**）：
  ① **桩缺方法不是守卫**：把 `picks_pipeline` 的题材成分取数从逐题材 `get_members(code)`
  改成批量 `member_symbols_bulk` 后，测试桩 `_Catalog` 里**没有**该方法——
  但 `AttributeError` 被 `candidate_pool` 与批预取处的 `except Exception: log.warning(...)`
  吞掉，于是**把实现改回旧的逐只 N+1，测试照样全绿**。（与批次 1 的
  `_Store.directions_of` 是同一个坑，隔天以变体形态复现 ⇒ 这是**模式**，不是偶发。）
  ② **A/B 等价对照钉不住"共用判据本身失效"**：批量版与逐只版共用 `override_still_active`
  判「override 是否在有效期」。把该判据改成**恒 True**（过期也生效）后，
  `assert bulk == single` **照旧成立**——两路一起错，对照关系不敏感。
  ③ **"注入"只改注释不改行为**：给新探针注入时写了 `# INJECTED: return None` 却
  **没动代码**，自然全绿，差点误判成"守卫覆盖不到"。
- **通用判据（三条，互相独立）**：
  1. **看次数，不看行为**——凡"把 N 次查询收敛为 1 次"的重构，守卫要把**调用计数**
     放进桩（范式：`test_board_fund_api.py` 的 `member_calls` / `bulk_calls`），
     断言「批量恰一次 + 单查恰零次」；并且**必须另有一条断言"未走异常兜底"**，
     否则计数断言会被 `except` 吞掉而失去意义。
  2. **A/B 必须配"单路绝对结果"**——凡两路共用同一判据/同一常量的重构，
     守卫要同时有 (a) 两路 A/B 相等 与 (b) 单路绝对结果断言；只有 (a) 时**判据坏了也测不出**。
  3. **注入的定义是"让行为可观测地错"**——加注释、改日志、改未使用变量都不算；
     验收标准是「**精确变红**：只有目标用例失败，用例数对得上」，且复原后
     `grep -c INJECTED` 必须为 0。
- **失效条件（什么时候这几条不适用）**：
  · 第 1 条要求被测函数**有可注入的桩边界**；若取数是模块级直接调用（无桩位），
    应先补注入点，而不是退回"读码确认"；
  · 第 2 条只适用于**存在两条等价实现**的重构；单路实现无 A/B 可言，用绝对结果断言即可；
  · 若目标用例与守卫在同一次运行里**共享可变状态**（同类桩被多段复用），
    注入结果可能出现"多红"，此时先修隔离（如给桩加 `prefix`），再判精确性。
- **关联**：[[KB-ENG-46]]（被 `except` 吞掉的守卫是死代码——本条是它的**三例实证 + 处置范式**）·
  [[KB-ENG-19]]（防线自己会错，只有注入验证能发现）· [[KB-ENG-47]]（门禁取证）·
  [[KB-ENG-42]]（模块有测试 ≠ 接线有测试）


### KB-ENG-66 源码级守卫必须区分「调用」与「提到调用的文字」；「注入了却没变红」多半是没覆盖到那条路径

**事故（2026-09-12 评审批次 5 / G-2）**：给 `test_event_loop_no_block` 新增 pipeline 条目时，
守卫**当场假红**——命中的是**我写在 docstring 里解释这条守卫的那句话**
（「同一条 `store.list_events(active_only=True, limit=30)` 跑了三遍」）。
纯文本扫描把"提及"当成了"调用"；更糟的是失败信息断言「存在**未被 `to_thread` 包裹的调用**」，
**与事实不符**。误报的失败信息比不报更糟：它会引导后人去**删掉那段正确的说明文字**。

**修法（三个约束，缺一不可）**：
1. **用 `tokenize` 而不是正则**把注释与字符串字面量换成等长空白——正则处理不了
   `#` 出现在字符串里、以及三引号跨行的 docstring；
2. **行号必须守恒**：单行 token 原地等长替换；多行字符串的中间行只保留换行符。
   失败信息要指得准，否则"指错行"会再次误导（本项目实测踩过"offset 混用导致行号串"——
   掩码后文本**长度会变**，所以**行号/列号在掩码文本上算、回报时取原文那一行**，两套坐标分工）；
3. **"是否已包"的前缀判断也要在骨架上看**：否则字符串里的 `to_thread(` 会被当成"已包"⇒
   **漏报**（比误报更危险）。反向断言（找裸调用）与正向 needle 各用各的坐标系：
   正向 needle 用原文（它要证明的就是"代码里有这行"），反向只在骨架上做。

**第四条假绿形态（补 [[KB-ENG-65]]）**：本次新增的
`test_to_thread_inside_a_string_does_not_count_as_wrapping` 首版把那个字符串放在**另一行**，
而前缀比较只看**同行**前缀 ⇒ **掩不掩码都通过**（等于没测到）。把字符串与该调用移到
**同一行且在调用之前**之后，重做注入该条确实变红。
⇒ **"注入了却没变红"的排查顺序：先怀疑测试没覆盖到那条路径，再怀疑守卫不够狠**；
验收判据 = 把注入做成"该断言**看得见**的形态"后仍然变红。

**失效条件**：语法不完整的片段（本仓不会出现）会自动退回纯文本 ⇒ 此时注释里的提及会误报，
这是**刻意选严**（严 > 漏）；被守卫对象若无可用的 tokenizer（YAML/脚本片段），退回正则 +
行首对齐，并接受该类误报。

**关联**：[[KB-ENG-65]]（假绿三形态，本条为第四形态）· [[KB-ENG-19]]（防线自己会错）·
[[KB-ENG-60]]（扫描面也是口径）· [[KB-ENG-59]]（区分注释与运行期字符串的同族教训）

### KB-ENG-69 「兜底分支必须无条件推进」：解析/分派循环里两个**各自正确**的分支会组合出「零消费死循环」；渲染期死循环单测与类型检查都照不出，只能端到端打开页面

**现象（2026-09-12，用户报「进入交易智能体的知识库会整个卡住动不了」）**：
知识库面板一打开就整页冻结——不是慢、不是白屏，是**主线程被占死**（连点击都无响应）。
后端无异常（`/api/agent/kb/file` 实测 200 / 54ms / 46KB），文件也不大（24K 字符 / 227 行）。

**根因：兜底分支「一行都不消费」**。自研 Markdown 渲染器的块级循环按序分派：
围栏代码块 → 表格 → 标题 → 列表 → 引用 → 分隔线 → 空行 → **普通段落（兜底）**。
其中**表格分支**要求「当前行以 `|` 开头 **且下一行是分隔行**」（GFM 语义：无分隔行不成表）；
**兜底分支**的延续条件里带着 `!lines[i].trim().startsWith("|")`。
两者单独看都对，**组合起来**就出现一个空档：**以 `|` 开头却不构成表格的行**
（缺分隔行 / 恰为末行）会被表格分支放行、又被兜底分支**在首轮**否掉 ⇒ `buf` 为空、
`i` 不推进 ⇒ 外层 `while (i < lines.length)` 永不退出。**这不是"慢"，是同步死循环。**

**为什么没被任何门禁挡住**：单测全绿、`tsc` 全绿、eslint 全绿——因为没有任何一条测试
喂过"不成表的 `|` 行"；类型系统更看不见运行期的循环不变量。**唯一能照出它的是端到端
打开页面**（本项目「验收以实际渲染为准」的又一例：桩数据证明"跑得通"，不证明"跑得完"）。

**判据与通例（可迁移）**：
1. **兜底分支必须无条件先消费一行**（`do...while`，或进入分支时先 `i += 1`）。
   「本轮一定能推进」应当是**结构上显然**的，而不是"推导一下就会发现条件其实不冲突"。
2. 排查形态：**分派条件与分支体条件互为否定式**时，去查「被分派条件排除、又被体条件拒绝」的
   空档集合；该集合只要非空就是一个死循环入口。审查时两个分支各自看都是对的。
3. 「解析不了」的正确降级是**退化为普通文本**，绝不能是**不推进**。
4. **写"检测死循环"的脚本时，脚本自己的循环也必须能退出**——本轮验证脚本第一版
   检测到"未推进"却忘了 `break`，把自身的扫描循环也挂死了（`SIGTERM/137`），
   与它要抓的缺陷**形态完全相同**。检测器要先证明自己会终止。

**触发面是全仓系统性的，不只是这个面板**：`docs/` 下实测 **4 份文档 / 共 49 行**
（`kb/00-INDEX.md` · `retro-and-gaps.md` · `api.md` · `external-data-source-survey-*.md`）
用**空行给同一张表分组**——这在**任何严格 GFM 渲染器**（GitHub / 编辑器预览）下同样会把表打碎。
而 `kb/00-INDEX.md` 恰是面板**默认打开**的文档 ⇒ 一进面板必中。**修法两条缺一不可**：
①文档改为合法 GFM 表格（源码与其意图一致，修复面覆盖所有渲染器）；
②渲染器兜底分支改 `do...while`（防御纵深：此后**任何**输入都不可能不推进）。

**失效条件 / 边界**：②只保证"不死循环"，不保证"渲染得漂亮"——孤立表格行会退化为
带管道符的普通文本（这是 GFM 的正确答案，不是缺陷）；若希望它们仍渲染为表，必须改
**文档**而不是放宽渲染器（放宽会与「表头+分隔行」型表格分派冲突，把相邻两张表吞成一张）。
注入验证的已知形态限制：把 `do...while` 改回 `while` 后，回归测试是**挂死**而不是变红
（死循环在同步渲染期，测试超时机制无法打断）——刻意接受：「挂死」比「静默通过」安全得多。

**关联**：[[KB-ENG-38]]（「滚不动」先查结构归属：同为**渲染层**缺陷、同属"看起来是性能/卡顿，
实为结构问题"）· [[KB-ENG-53]]（静默失败族：共同形态 = 无报错、结果看着正常）·
[[KB-ENG-60]]（扫描面也是口径：没有测试喂过这类输入 = 该路径根本没进检查）·
[[KB-ENG-65]]（假绿守卫）· [[KB-DEC-018]]（示例 ≠ 规范：单测绿 ≠ 真实页面绿）

### KB-ENG-71 性能实测的**标签**必须与**被测对象**逐行对账：错配的标签会驱动一次错误的改动

2026-09-12「async 端点同步 IO 扫面」轮。用一张 `(标签, lambda)` 表跑基准，其中一行写
`("/api/alerts/events  repo.list_events(50)", lambda: store.list_events(...))` —— 标签说的是
**AlertRepository**，lambda 调的却是 **EventStore**。据此把 `/api/alerts/events` 记成 **8.5ms**
并**动手包了 `to_thread`**；后来为写注释复核数字，直接测 `AlertRepository.list_events(50)`
只有 **0.36ms**（差 24 倍）⇒ 两处已写好的包裹被**回退**。

**为什么危险**：错配的标签不会报错，它会**产出一个看起来精确的数字**，而这个数字直接决定
"改不改代码"。本仓的判据是「搬线程的收益是否超过调度开销」，0.36ms 与 8.5ms 恰好落在阈值两侧
⇒ **标签错配直接翻转结论**。同类风险面：`X.list_events` / `Y.list_events` 这种**同名方法跨类**
在仓内大量存在（`store.` / `repo.` / `svc.`），肉眼扫一眼"都是 list_events"极易放过。

**处方**：
1. 基准表的**标签由 lambda 派生**（或紧邻书写），不要分开写；表格按对象分组而不是按端点分组；
2. 报出的每个数字，**写进注释/文档之前再单独测一次该对象**（本轮正是这一步抓到的）；
3. 发现标签错配 ⇒ **就地回退**基于它做的改动，并把这次错配写进注释（防后人重新"发现"同一件事）；
4. 阈值两侧的样本（本例 0.36 vs 8.5）要**各留一条对照行**，差值一眼可见。

**判据**：数字本身精确 ≠ 结论正确——**"这个数是谁的"和"这个数是多少"同等重要**。
与 [[KB-ENG-55]]（口径比判据本身更要命）同族：那条错在**取数口径**，本条错在**取数对象**。

**关联**：[[KB-ENG-55]] · [[KB-ENG-67]]（搬不搬的三项判据）· [[KB-ENG-47]]（门禁工具也会假阴性）

### KB-ENG-72 源码级守卫的**匹配面**：只写方法名会误伤同名方法，不区分 async 上下文会误伤同步 helper

同一轮给 `test_event_loop_no_block.py` 加「路由 / 事件层」条目时，反向断言（"不得存在未包
`to_thread` 的 `<fn>(` 调用"）**连红两次**，两次都不是代码的错：

1. **同名方法误伤**：条目写 `fn="list_events"`，而仓内另有 `AlertRepository.list_events`
   （实测 0.36ms，**刻意不搬**）⇒ `app/assistant/tools/events.py`（当时该模块还是单文件）立刻假红，差点逼我去包一个
   毫秒级调用。修法 = **判据带接收者**：`fn="store.list_events"`。关键性质：`to_thread` 传的是
   **函数引用**（`to_thread(store.list_events, …)`，不含 `(`）⇒ 该字面量**只命中裸调用**，
   天然不会自match，也天然不会把已包的算成未包。
2. **同步 helper 误伤**：`notifications._alert_items` 是**模块级同步函数**、体内有
   `repo.list_events(...)`——那本身合法（它不占事件循环）；真正的违规在**调用它的 async 端点**
   （另一层，文本扫描表达不了）。修法 = 反向断言加 `async_only=True`：用 `ast` 收集
   **async 函数体的行号集合**，并**减去其中嵌套的同步 def**（否则 `async def` 里定义个小工具
   就会被误判），只报落在该集合内的裸调用；语法不完整时返回 `None` ⇒ 退回"不过滤"（严 > 漏）。

**两条通用判据**：
- **守卫的匹配面越具体，假阳性越少**——但每收窄一次都要回答「收窄后还能抓住原目标吗」；
  本例靠"传函数引用不产生 `(`"这一**语法事实**同时满足了两边。
- **"该不该包"是调用点的属性，不是函数的属性**：同一个 `list_events`，在 async 端点里要包、
  在同步 helper 里不该包 ⇒ 守卫必须能表达**上下文**，纯文本方法名做不到。

**配套（已固化为常驻测试）**：`test_async_only_ignores_module_level_sync_helper`（假阳性定点）、
`test_async_only_still_flags_async_body_calls`（正向对照，防"一律放过"）、
`test_async_context_excludes_sync_def_nested_inside_async`、`test_async_context_returns_none_on_unparsable_source`。

⚠️ **注入验证的预期形状要写明**：反向断言按**文件**判，`events.py` 有 5 条登记项共用它 ⇒
在该文件注入一处裸调用会**同时红 5 条**（不是守卫失灵，而是"5 条描述同一个文件"的必然结果）。
判读时看**报出的行**而不是条目数。注入实测：`events.py` 一处 ⇒ 5 红；`notifications.py` 一处 ⇒

### KB-ENG-74 守卫的「驱动形态」决定敏感度：**外部取消会顺手跑掉同步清理，从而掩盖"必须自行收尾"的缺陷**

**事故**（2026-09-14 R24，注入验证 `EXIT=1` 三处不吻合）：R24 修的是「WS 收发两条任务的生命周期绑在**一条**上」
（旧实现 `await writer()`）⇒ reader 先结束（客户端断开 / 意外异常）时无人察觉，writer 永久 parked、
`hub.unsubscribe` 永不执行，订阅成孤儿。我写了 `test_client_disconnect_unsubscribes_even_when_hub_never_pushes`
（`TestClient` 形态）当判据，**注入旧实现后它仍然全绿**。

**成因**：Starlette `WebSocketTestSession.__enter__` 把三个回调压入 `ExitStack`，会话退出时按 LIFO 依次执行
`close(1000)` → `portal.call(cs.cancel)` → `fut.result()`。其中 **`cs.cancel()` 是外部取消**，而取消只是"在下一个
挂起点抛异常"——`finally` 里**同步的**清理语句照常执行 ⇒ 旧实现在这条用例下表现与正确实现**无法区分**。

**修法（两种驱动形态各司其职，缺一不可）**：
1. `TestClient` 形态验**端到端契约**（ping/pong、脏帧不杀连接、建连即注册）；
2. **直接驱动路由协程**形态（`asyncio.wait_for(quotes_ws(fake_ws), timeout=2)` + 最小 `_FakeWS`）才能钉
   「收尾必须**自行**发生」——没有外部取消，旧实现就是**永不返回**。同一注入下二者的期望集合**天然不同**：
   I4（还原 `await writer_task`）⇒ `{T_ERR_LOGGED, T_READER_END}`，**不含** `T_DISCONNECT`。

**同轮第二发现（同源）**：收尾路径含 `await` 时，**全部 5 条**走会话退出的用例都抛
`concurrent.futures._base.CancelledError`（来自 `fut.result()`）——因为被取消后首个 await 点立刻重抛，
**其后的清理被整段跳过**（生产侧 = 客户端断开时订阅实际未注销，是真实脆弱点）。固化实现：
`asyncio.gather(...).add_done_callback(_report_task_failures)` + 同步 `unsubscribe`，**收尾零 await**。

**教训**：
1. **写守卫前先问「这条用例是被什么驱动结束的」**——测试框架/宿主的收尾动作（cancel、close、GC）
   会替你跑掉一部分代码，**被替你跑掉的那部分就失去了被验证的资格**；
2. **同一缺陷可以有多条用例，但敏感度不同**：把「注入后精确变红的集合」写进脚本 docstring，
   并注明**为什么某些用例**不在集合里——否则后人会以为漏了；
3. **"守卫存在" ≠ "缺陷被守住"**（[[KB-ENG-65]] 同族）：判据要挑**唯一能区分新旧实现**的那种驱动形态。

### KB-ENG-75 门禁必须**整仓**跑：局部 `eslint <file>` 通过 ≠ 门禁通过；`react-hooks/refs` 禁止渲染期写 ref

**事故**（2026-09-14 R19）：修完手填价的竞态后只跑了单文件相关测试与类型检查，**没跑整仓 eslint**；
收尾时 `npx eslint .` 报出 1 个 **error**：

```
components/trade-form.tsx:83  error  Cannot access refs during render
  sigRef.current = orderSig;   // ⚠️ Cannot update ref during render
```

**成因**：`eslint-plugin-react-hooks` v6 的 `react-hooks/refs` 规则按 React 官方要求
（**渲染必须是纯的**）禁止在渲染期读写 `ref.current`。我原先的写法是为了让 ref 与 state「同步更新」。

**修法（语义不变，且更严谨）**：把写入移到**发出请求的那个 effect 的体内首行**：

```tsx
useEffect(() => {
  sigRef.current = orderSig;          // 首行同步登记"当前订单"
  if (pv <= 0 || qv <= 0) return;
  const t = setTimeout(() => { /* 发请求，回包按 sigRef 过滤 */ }, 300);
  return () => clearTimeout(t);
}, [orderSig, pv, qv, symbol, side]);
```

**为什么没有窗口**：该 effect 的依赖含 `orderSig`，草稿一改即重跑；而它发出的请求最少要等
**300ms 去抖 + 一个网络往返**，**任何回包都晚于本次 effect 的同步段** ⇒ ref 必已更新到最新。
（对照：若改用 `useEffect` 之外的位置如渲染期或 lazy init，前者被 lint 判错，后者根本不更新。）

**教训**：
1. **门禁的"扫描面"包括文件面**：`eslint` 只查你点名的文件时，"0 error" 只是**那个文件**的 0；
   改完前端组件后必须 `npx eslint .` 整仓复跑（与 KB-ENG-60「写窄的 glob 会让新对象根本不进检查」同源）；
2. **lint 报错是设计信号，不是障碍**：`react-hooks/refs` 在说"渲染不纯"——正确的回应是
   **把写入挪到 effect，并论证时序仍成立**，而不是 `eslint-disable`；
3. 挪位置后**必须复跑该模块的注入验证**（本轮 R19 注入 `4/4` 仍精确变红，守卫未被削弱）。

[[KB-ENG-74]]（守卫的驱动形态）

### KB-ENG-77 注入验证的三条硬约束：**等宽注入 / `compile()` 前置校验 / 崩溃安全**

**事故**（2026-09-14 R17）：注入验证脚本被 SIGTERM 打断，**`evaluate.py` 被留在注入态**
（`hold_days = max(horizon - 1, 1)`，守卫被摘掉）。`try/finally` 没能挽救——**SIGTERM 的默认
处置不执行 `finally`**。发现方式不是"感觉不对"，而是**复原后按锚点 grep 逐个复验**：脚本自己
打印的"复原后复测"那一步根本没跑到。若只看脚本输出的最后一行，会把注入态当成品提交。

**三条约束（缺一即假验证）**：

1. **注入面必须与语义面等宽**（承接 [[KB-ENG-72]]）：注入要打在**真正被断言的那条路径**上。
   R17 的 I2 首版只改 `qs[5] - qs[1]` → `qs[5]`，却留下 `if 1 in qs and 5 in qs` 的前置过滤 ⇒
   「缺 Q1 的年不得产出」那条用例**照样绿** ⇒ 预测集与实测集不等。等宽 = 连**前置条件**一起注入。
2. **注入必须先过 `compile()`**：正则/字符串替换可能留下空 `try:`、孤立 `else:` ⇒ 整模块
   `SyntaxError` ⇒ **红是假的**（所有用例都红，看起来"守卫极强"）。本仓做法：替换后
   `compile(mutated, path, "exec")`，失败即判该注入无效并跳过。
3. **崩溃安全三层**：①启动**自愈**——发现残留备份先把源文件还原（上一轮异常退出的痕迹）
   ②注册 `SIGTERM`/`SIGINT`/`atexit` 还原；③**备份文件本身即真相源**，人工也能一键还原。
   并**每次注入跑完立刻还原**，把暴露窗口压到最短。
4. **注入面若被下游共用，波及面 ≥ 直接断言它的用例**——预测集要按**共用关系**推导，不能按「哪个测试名像」。
   实例（2026-09-14 R15/R16 · J3）：摘除 `p{h}`（未成熟计数列）时首版只预测 4 条，实测 9 条。
   多出的 5 条不是无关失败——注入面是 `_agg()` 的 SELECT 列清单，而**该清单与 `_agg_cols()` 同源**，
   `stats()` / `summarize_row()` / `render()` 都按同一列集取数 ⇒ 摘任何一列，**所有消费该列集的用例**
   （漏斗计数、市场中性 ×2、渲染表头、单条件独立）都会红。同批 I1 同理（多红 1 条：全截面排名让 NULL
   也获得名次 ⇒「全未成熟日 ic 为 NULL」同样变红）。
   ⚠️ **判据不得因此放宽为「实测 ⊇ 预测」**——那等于放弃可证伪性（多红永远"合理"）。

### KB-ENG-79 `ntile()` 没有 tie-break ⇒ 分层归属与准入门槛**不可复现**（连跑 3 次给 3 个结论）

**事故**（2026-09-14 R17 注入验证时**顺带照出**）：写重算追溯的守卫时，同一份合成仓、同一份代码，
**连跑 3 次 `run_full_eval` 得到 3 个不同结论**（基线 `dc2cc35` 上复现）：

```
imax20  ['PASS', 'CONDITIONAL', 'PASS']      # 3 次跑出 2 种结论
sump20  ['CONDITIONAL', 'PASS', 'PASS']
```

**定位方法（可迁移）**：不要停在"它不稳定"，要**逐层二分到具体字段**——
`ic_mean` 三次**逐字相同**（−0.8672）、`consistency` 相同，但 `q_avg_daily` 每次不同：

```
run1: {'1': 0.032839, '2': 0.031396, '3': -0.006985, ...}
run2: {'1': 0.031756, '2': 0.03187,  '3': -0.006225, ...}
```
⇒ 差异**只在分位组归属**，不在 IC 计算。根因 = `ntile(5) OVER (PARTITION BY date_ms ORDER BY f)`
**排序键不唯一**：因子值存在大量并列时（`imax20` 是整数索引 0~19、`cntp20` 是计数），
分位切点落在并列值中间 ⇒ **谁进哪一组由执行顺序决定** ⇒ `monotonic_pairs` 与多空差抖动 ⇒
门槛 `≥3/4 单调对` 随之抖动。

**为什么长期没被发现**：①每次跑都"全绿"（评估是离线批任务，没有"两次结果必须相同"的守卫）
②`report.py` 只消费 `ic_mean/icir`，这两个量恰好是稳的 ⇒ **运行期消费方看不见抖动**
③只有"同一输入重跑必须同结论"这条**元级判据**才能照出它。

**第二个实例：噪声会污染「口径变更」的验收归因**（2026-09-14 R17 验收对账，同一坑第二次咬人）。
R17 的年化口径修正要求「重算后与旧报告逐因子对比」，而 `recheck` 清单里唯一的翻转
`imax20`（PASS → CONDITIONAL）**不能归因于 R17**，三条实测证据：

1. 触发翻转的判据是 `monotonic_pairs`（2/4 < 3/4），而该量**与年化公式无关**（R17 只改缩放与年度差分）；
2. 三方对照（**同一份数据**、只换代码）：基线 `dc2cc35` 代码 → `monotonic=3`；工作区代码 → `monotonic=2`；
3. 若沿用基线那次归属（3/4），新口径下 `imax20` 仍判 **PASS**（|多空 9.66%| ≥ 3.0% ✓ 且 3/4 ≥ 3/4 ✓）。

⇒ **结论：该"翻转"是归属抖动的观测，不是口径修正的因果结果。**

**由此升格为纪律**：凡**以「结论发生变化」为验收判据**的改动，其底层指标必须先**可复现**——
否则验收报告里的"翻转"是**不可解释的观测**（既可能来自改动，也可能来自抖动，两者不可区分）。
故修 tie-break 不是"顺带优化"，而是**让这一类验收成立的前提**。

**修法**：给排序键补**唯一 tie-break**（`ORDER BY f, thscode`）——并列值怎么分本是任意的，
但**必须确定**。**判据：凡"分层/分位/分桶"类SQL，先问「排序键唯一吗」**；验收 = **同一输入连跑 ≥3 次，
逐因子结论逐字相等**（把它写成一条守卫，而不是靠人记得）。

**状态**：本项**已定性、待拍板**（改 tie-break 会改变并列值大户的历史分位归属 ⇒ 与 R17 同属
"会改变既有产物结论"的口径变更，按纪律先提后做）。见 `docs/retro-and-gaps.md` §六。

### KB-ENG-80 验证判据**自身的失真**会制造假缺口：「归一化过宽」与「一次性脚本不可复核」

**与 [[KB-ENG-04]] 同族，但更隐蔽一层**：KB-ENG-04 是「工具搜不到 ≠ 不存在」（判据是通用工具，
至少有别人踩过）；本条是「**判据自己制造了"不存在"**」——判据是**为这一次结论专门写的一次性脚本**，
天然缺少他者复核，且写它的人和下结论的人是同一个。**⇒ 自造判据 = 自造的假阴性。**

**实例（2026-09-14 报告交付收尾，已全量撤回）**：为核验 `md → html` 是否无损，写了一次性比对脚本，
得出「**HTML 丢失 2 处内容**、md 里 **10 处裸 `<`** 会被当成标签起始吞掉后续文字」，
并已准备去"修"渲染器。

**复核结论：撤回。渲染器无此缺陷。** `.workbuddy/tools/md-report-html.py::_inline()` **首行即**
`html.escape(text, quote=False)` ⇒ 裸 `<` 渲染为 `&lt;`，本就安全。逐条目对账实测 **1191/1191 全绿**。

**根因（缺陷在判据，不在被测物）**：比对脚本在 **md 侧**用了 HTML 去标签 `strip('<[^>]*>')`——
但 **md 是纯文本，其中的 `<` 是内容而非标签起始**。对 `均 < 24h 且数据为多日聚合` 这类片段，
一次 strip 会一直吃到**下一个 `>`** 为止的大段正文 ⇒ **md 侧凭空变短** ⇒ 差异呈现为「html 缺失」。
方向被彻底读反：**变短的是我自己造的那一侧**。

**第二形态：归一化「顺手多删一点」**。修正首版后仍报 **16 处**假缺口，逐条查全是**字面量被当标记删掉**：
`*`（`NEXT_PUBLIC_*` / `tests/*.py` / `12 * 3600` / `is_*` / `--noproxy '*'`）、
`|`（`grep "\|"` / `_is_trading_day|_trade_day_state`）、`\`（`"\|err\|"`）。
html 侧经 `unescape` 后这些字符**原样存在**，md 侧被删 ⇒ 又是单向假缺口。

**三条判据（可迁移）**：
1. **被比对象是什么格式，就用该格式的解析器**——md 侧**不得**做 HTML 去标签；html 侧必须
   **先 `unescape` 再比**。跨格式比对时，「把这一侧也当另一侧解析」是最常见的隐性错误。
2. **归一化只去真正的标记**（成对 `**`、反引号、行首列表/标题/引用标记、链接语法），
   **字面量一律原样保留**。宁可多留噪声，不可多删内容——删多了会**伪造**另一边没有的东西。
3. **判据必须能变红**（[[KB-ENG-65]]）：注入删除一个片段 ⇒ 必须**精确**报出该处、断裂点吻合；
   否则判据等于没写。本轮的教训更硬一层：**判据还会反过来制造 bug**（若不复核，就会去改正确代码）。

**修法（已落地）**：固化为 `.workbuddy/tools/md-html-parity.py`（零依赖，三项判据：
逐条目文本命中 / 结构计数相等 / 时间戳新鲜；失败打印**第一个断裂点**即保留前缀 + 断裂片段 + md 原文，
`exit 1`）。**三组注入验证**：A 删掉 `&lt; 24h 且数据为多日聚合` ⇒ 精确报 **L574** 一处、断裂点吻合；
B 破坏 table 计数 ⇒ `37=35` 判红；C 时间戳倒挂 ⇒ 判红。**真实报告实测 1191/1191 无损**。
⇒ 它也**取代**了原先文档里「数 `<li>`/`<table>` 个数」的口径（那个只测结构、测不到单元格内的内容）。
一次性脚本从此不再作为验收依据——**验证手段必须是可复用、可被他人重跑的登记工具**。

### KB-ENG-81 复核一个函数 ≠ 复核一个模块；**同一条错误判据用在两侧 = 双向自洽的假绿**

**（[[KB-ENG-80]] 的续篇，2026-09-14 同日；因单条 ≤60 行（§7 L0）而独立成条。）**

上面的撤回**只对 `_inline()` 成立**。复核了一个函数就宣布"渲染器无此缺陷"，是把**局部结论
推广成整体结论**——这正是 [[KB-ENG-04]] 的形态，只不过这次是我自己犯的，且**受害者是我自己
刚写的结论**。同一份报告的全量对账（`md-html-parity.py`）随后报出 **371/373、2 处未命中**，
这次是**真阳性**。

**真缺陷位置**：`.workbuddy/tools/md-report-html.py::_split_row()` —— 表格切分用裸
`line.strip().strip("|").split("|")`，**不识别转义竖线** `\|`（md 表格里 `\|` 是"字面竖线"）。
后果不是"少一格"这么轻，而是三件事**同时**发生：

1. 该行比表头**多出 `<td>`**（实测 4 个 `<td>` vs 表头 3 个 `<th>`）；
2. `<code>` **未闭合**（切分把反引号劈开两半）；
3. **反引号原样泄露**到页面文字里。

读者看到的是 `boolean \| null` 而不是 `boolean | null`，且表格右移错列。

**GFM 口径（两轮才对）**：第一版修法"保护行内代码段、只还原代码段外的 `\|`"是**错的**。
GFM 的表格解析**在行内解析之前**就把 `\|` 还原为 `|`，因此单元格内 `` `boolean \| null` ``
在 GitHub 上渲染为 `` boolean | null ``。正确口径是两分：

| 语境 | `\|` 处理 | 理由 |
|---|---|---|
| **表格单元格**（含行内代码 span 内） | **一律还原**为 `|` | GFM 在行内解析前先做转义还原 |
| **非表格正文** | 仅还原**代码段之外**的 | CommonMark 下代码 span 内的 `\|` 是字面量（本仓 `` `grep "\|"` ``） |

⇒ 落地为 `_cell_inline()`（表格用）+ `_inline()`（正文用），parity 侧用 `_split_cells()`
对齐同一条口径。**两边口径必须逐字一致**，否则会制造"凭空多出一格"的新假缺口。

**更硬的一条：这个缺陷差点又被判据的盲区漏掉。** parity 的「结构计数」只数 `<table>` 个数，
**不校验列数一致** ⇒ 切分错位只能伪装成"文本未命中"被间接发现；而若 md 与 html 用**同一条
错误判据**切分，第 1 项判据还会**双向自洽地通过**（错得一样就查不出错，[[KB-ENG-65]] 形态）。
**已补第 3 项判据**：每个 `<table>` 的数据行 `<td>` 数必须等于表头 `<th>` 数（md 侧同查），
单独报"表#N：表头 3 列 vs 数据行 4 列"。

**注入验证（两轮，均精确判红）**：回退 `_split_row` ⇒ 旧版报 `371/372` + 定位 L125；
**新增列数判据后** ⇒ ② 独立判红并直指「html 表#7：表头 3 列 vs 数据行 4 列」。
复原后两个工具 **sha256 逐字节一致**、`INJECTED` = 0、`372/372` 全绿。

**可迁移判据（三条）**：
1. **复核一个函数 ≠ 复核一个模块**：说"X 无此缺陷"前，先枚举 X 的**所有**同类入口
   （本例渲染器有两个文本入口：`_inline` 与 `_split_row`）。
2. **同一条错误判据用在两侧 ⇒ 双向自洽的假绿**：判据必须有一条**独立于"内容逐字比对"**
   的**结构一致性**检查（列数 / 行数 / 配对数），否则"两边一起错"永远查不出。
3. **修复要按被仿对象的真实规范**（GFM/CommonMark），不要凭直觉设计"更安全的"中间口径；
   我第一版的"保护代码段"直觉就是错的，靠实测 GitHub 行为才纠正。

### KB-ENG-84 「时间新鲜」≠「结论可用」：**口径版本是与时间正交的第二维度**；复核清单 ⊋ 翻转清单

**事故**（2026-09-14，GOV-001 落地时**实测**照出，非推理）：磁盘上的因子评估报告
`backend/data/factors/eval_report.json` 产出于 **`2026-09-07T17:00:46`**、**连 `algo_version`
字段都没有**（该字段 09-14 才引入），而代码口径已是 `2026-09-14.ic-maturity-v3`。实测：

```
freshness() → {"stale": false, "age_days": 7, "max_age_days": 40}     # 7 < 40 ⇒ 判"新鲜"
ic_evidence() → {"available": true, "stale": false, ...}               # 旧口径结论照常送进进化议程
```

即：**一份用旧口径算出来的因子结论，以「不陈旧」的身份继续被当调参依据**——
报告 F5 要防的「旧报告继续被当调参依据」，就是这个形态。

**根因**：新鲜度只有**一个维度（时间）**，而「这份结论还能不能用」是**两个正交维度**：

| 维度 | 问的是 | 失效方式 |
|---|---|---|
| 时间 | 数据/产物多久没更新 | 数据旧 ⇒ 结论不代表当下 |
| **口径** | 它是用**哪一版算法**算的 | 算法改 ⇒ 结论的数值前提已变，**即使它昨天才跑** |

只看时间 ⇒ 「口径一改，所有旧结论都要复核」这件事**没有任何机制承载**：
`stale=False` 会被读成「结论仍然成立」，而它只证明了「跑得不久」。

**三条纪律（本项落地）**：

1. **两个维度必须是两个字段，不许合成一个布尔**。`algo_current` 与 `stale` 并列且正交；
   把口径并进 `stale` 会让既有消费方（调度器的「该重跑了」判定）被口径变更**误触发**。
2. **口径维度要三态**：`True`（同源）/ `False`（已变更）/ **`None`（旧产物未声明口径 ⇒ 未判定）**。
   `None` **不得**塌缩成 `False`，也**不得**被当成"没问题"放过——**不可知恰恰更需要人看一眼**
   （实测那份 09-07 报告正是 `None`；若按"未声明 = 未变更"处理，它就永远复核不到）。
3. **复核清单 ⊋ 翻转清单**。只列"结论翻转了的"是错的——**未翻转 ≠ 不受影响**：
   旧结论是旧口径算的数，换口径就该复核，**哪怕三态恰好停在原档**。
   翻转清单（`recheck`）服务于"改动是否静默把通过改失败"，复核清单（`review_required`）
   服务于"哪些历史结论要重看"，**两者职责不重叠，不能互相替代**。

**同族第二次咬人：文档承诺 ≠ 实际覆盖**（[[KB-ENG-72]]）。制度文档
`factor-lifecycle-governance.md` §7.2 早就写着「报告按 generated_at **版本化留存**」，
而落盘路径长期是**单文件原地覆盖** ⇒ 历史结论只剩上一次的 `verdict_prev`，更早的**不可枚举**
——**没有归档，"列出需复核的历史结论"连数据面都不存在**。
⇒ **凡"版本化/留存/归档"类承诺，必须有一条守卫钉住它真的产生了文件**，不能只写在文档里。

**可迁移判据**：判断某产物能否继续用之前，先问一句 **「它是由哪一版口径产出的？」**——
凡是"算出来的结论"（因子 IC、评估报告、回测基线、门槛校准），都与产生它的算法版本绑定；
版本对不上，时间再新也只是"新的旧结论"。

### KB-ENG-86 注入验证必须**改序**：秩 / 分位类度量对**仿射单调变换不变**，只改值的注入是静默空操作

**事故**（2026-09-14 `RSH-001`）：为自证「新增因子的附加性守卫**能变红**」，向因子值注入扰动——**两次注入都被判据原样放行（全绿）**，而守卫本身完好。差点据此宣布「守卫已验证」。

| 注入 | 为什么无效 |
|---|---|
| `c20 × 1.01` | `f = close/c20 − 1` 变成 `(f − 0.01)/1.01` —— **纯仿射变换**（缩放 + 平移） |
| `c20 × (1 + 0.5·(rn % 2))` | 夹具里老股**同日上市**、行号与交易日一致 ⇒ `rn % 2` 在**同一交易日内跨股票取同值** ⇒ 退化成**又一层全局缩放** |

**根因**：**IC 走 `percent_rank`（秩相关）** ⇒ 对输入的**任何仿射单调变换**（等比例放大、平移、按同一常数分段缩放）**逐点不变**。两次注入都只改了「值」，未改「序」。

**修复**：改 `c20 × (1 + 0.5·(hash(thscode) % 2))`——`hash(thscode)` 在同日**跨股票不同** ⇒ 真正**打乱截面次序** ⇒ 判据立刻变红。

**四条纪律**：
1. **先问「度量对什么不变」**。秩 / 分位 / 相关系数类（IC、RankIC、Spearman、AUC、各类 pct-rank）对**单调变换不变**，对「值的绝对大小」不敏感 ⇒ **注入必须落在它的不变量之外**；与之相反，均值 / 方差 / 阈值类度量对**值的量级**敏感——**同一个注入对两类度量有效性相反**。
2. **"注入后仍全绿"的第一嫌疑是「注入无效」，不是「判据可靠」**。⚠️ 两种情形观测**完全相同**：**判据正确 + 注入无效** = 全绿；**判据失效 + 注入有效** = 全绿。⇒ 全绿**不能**作为判据已验证的证据，必须**再补一次能预期变红的注入**（[[KB-ENG-65]] 的反面：判据「能变红」既要有注入，也要注入**真的改变了被判定的那个量**）。
3. **注入要与被判定的维度正交**。要改的是「截面序」，就要保证扰动**同日跨股票不同**；若扰动与别的维度同构（随行号、随日期、随整日恒定），会被该维度**吸收**掉。
4. **强度不是关键，「是否触及不变量」才是**。只改值哪怕 ±50% 也可能完全无效；改序哪怕 ±微小也立即生效。

**顺带纠正一条登记错误（同一轮，属「文档承诺」类）**：账本把 `RANK20` 登记为「qlib **截面排名**，需展开 `LAG(1..19)` 列」，**两处都错**——`ops.py::Rank` 主路径是 `rolling(d).rank(pct=True)`（**滚动窗口内**百分位），DuckDB 窗口 `list() + list_filter` lambda **闭式即可**。⚠️ **该错误改变了「要不要做」的判断**：截面排名在 RankIC 下与原始值**单调等价 ⇒ 零信息增量**，若照登记实现，本项**本无必要做**（即本条纪律 1 的同一个道理的另一种表现）。⇒ **施工前必须回源码核实口径，不能照登记的实现路径提示写**。

**关联**：[[KB-ENG-65]]（判据必须能变红）· [[KB-ENG-72]]（清单覆盖 ≠ 真实覆盖）· [[KB-ENG-84]]（口径版本是与时间正交的第二维度）

### KB-ENG-87 「换个参数再跑一遍」不能靠改写表达式层实现：参数扫描必须**参数化 base 链**，否则**阶段错位**

**事故**（2026-09-14 `RSH-002` 窗口敏感性扫描）：为回答「生产因子的 PASS 是对窗口稳健、还是恰好落在 20 日窗」，首版把因子表达式**窗口化后塞进 `scored` 层**（生产管线的过滤/打分阶段）⇒ **21/21 算子在生产窗 w=20 处与生产对不上**，差异只在第 3~4 位小数。当时**两种解释都成立**——「我改错了」与「生产本身不可复现」——必须靠实测区分。

**三层归因（全部实测，非推测）**：

1. **先量「自身抖动」，再定容差**。同一条生产 SQL 连跑 2 次：**8590 处不同**，`ic3 = −0.08903252911303587` vs `−0.08903252911303591`（Δ ≈ **4e-17**）。⇒ 根因是**并行浮点累加顺序不固定**（[[KB-ENG-79]] 的「结论抖动」在**浮点层**的表现），量级 **~1e-16**。⇒ 用 `1e-12` 严格判等**必然全数误报**；容差须**先实测自身噪声量级**再取余量（本轮取 `1e-9`，留 7 个数量级）。
2. **主因是阶段错位**。生产列在 `lvl3`/`lvl4` 计算，而守卫 `WHERE cnt >= {min_bars}` 在**之后的 `scored` 层** ⇒ 窗口函数是在**过滤前的全行集**上求值的。首版把窗口化表达式写在 `scored`（过滤**之后**）⇒ **窗口函数的输入行集不同**，frame 覆盖的样本整体后移 ⇒ **同一个算式在不同计划阶段不等价**。
3. ⇒ 两条叠加：「数值对不上」既**不可能**靠严格判等暴露（噪声淹没），也**不可能**靠调容差修好（差异是结构性的）。

**正解：改「产生该列的那一层」，不改「消费它的那一层」**。参数化生产 `_base_cte` 本身——把 frame 长度与守卫谓词**定点替换**（`>= 20`→`>= {w}`、`ROWS BETWEEN 19 PRECEDING`→`{w-1} PRECEDING`）。**列名保持不变**（`amt20_cur` / `vola20_w` 里的 `20` 只是历史命名）⇒ 21 条生产 `FactorDef.expr` **逐字复用、零改写**，且过滤阶段与生产完全一致。

⚠️ **替换必须用「唯一占位符两步法」**：先把 `>= 20` / `>= 14` / `19 PRECEDING` / `13 PRECEDING` 各自换成 `__GW__` / `__GAW__` / `__W1__` / `__AW1__`，**再**统一求值——否则后一次替换会命中前一次产出的数字（先替 `20`→`w`，再替 `19`→`w-1` 时就会串味）。

**自证形态的优先级：结构臂 > 数值臂**（本轮两臂齐备，21/21 + 3/3）：

| 臂 | 做法 | 为什么优先 |
|---|---|---|
| **结构** | 生成 SQL 与生产 `_base_sql` 尾段**逐字比对** | **相同即等价，无需容差**，不受自身抖动干扰 |
| **数值** | 抽样实跑比对（`|Δ|≤1e-9`） | 只作补充；必须先完成「自身抖动」标定 |
| **模块级** | `assert _base_cte_param(prod_w, prod_aw) == _RAW` | 把「参数化没写坏」变成 **import 期**就报的硬约束 |

**四条可迁移纪律**：

1. **凡「换个参数重跑生产逻辑」的任务，先问「要改的是哪一层」**——改表达式层 = 换了执行阶段；改 base 层 = 只换参数。判断依据是**该列在哪一层产生**，不是哪一层看起来更好改。
2. **对不上时先量噪声**（同输入连跑 ≥2 次）**再定判据**；**容差不来自直觉，来自实测噪声量级**（[[KB-ENG-65]]：定不出量级的容差不是判据，是橡皮）。
3. **能结构比对就别数值比对**：逐字相同是**判等**，数值接近是**估判**；前者不受浮点抖动影响，也不需要「差多少算一致」的约定。
4. **旁证性扫描不得改判定口径**：本轮 `ALGO_VERSION` **不 bump**、既有因子评定一个不动（扫描是**旁证**、非重评）；脚本须带**范围声明**（不含五分位分层 ⇒ 「至少 CONDITIONAL」只是**上界**）。

**关联**：[[KB-ENG-79]]（结论不可复现：`ntile` 无 tie-break）· [[KB-ENG-65]]（判据必须能变红）· [[KB-ENG-60]]（扫描面写窄 = 全绿）· [[KB-ENG-84]]（口径版本是与时间正交的第二维度——「生产窗」亦然）

### KB-ENG-90 「恢复态」功能的判据必须含「恢复之后再操作」；双写底稿（state + ref）少写一份 = 一操作就抹掉历史

**事故（2026-09-15，`IMP-004` 助手会话持久化）**：落盘恢复时只写了**两份状态里的
一份** —— `setMessages(cur.messages)` 更新了 React state，却没写 `msgsRef.current`
（本组件后续**所有**变更的底稿，`syncRef()` 以它为源）。于是「刷新 → 会话恢复」看起来
完全正常（只读判据**全绿**），而**恢复后第一次提问，历史被整段覆盖**：界面只剩这一问一答，
**再刷新一下历史又全回来了** ⇒ 症状是「一提问历史就没了、刷新又有了」，
用户无法把它与「持久化根本没生效」区分开。

**为什么单读判据照不出来**：断言「刷新后能看到历史」在**缺陷代码上同样通过** ——
恢复那一步两份状态是**一致**的，分歧只在**下一次变更**时才暴露。⇒ **恢复类功能的判据
必须包含「恢复后继续操作一次」**（本轮用例即为此：恢复后发问，断言渲染出的
`data-msg-id` 集合 = 恢复的 2 条 + 新增的 2 条且互不重复）。⚠️ 另外：**React 19 在本仓的
jsdom 里对"重复 key"不发 `console.error`**（实测捕获为空）⇒ 想钉「id 不得重复」就**直接读渲染出的 id**，
不要依赖框架告警文案。

**四条可迁移纪律**：

1. **凡「恢复」都走与「正常变更」同一个写入口**（把恢复当成一次普通变更），否则必然"只写了一半"。
   本仓双份状态不是个案：`useState` 与 `useRef` 底稿、内存缓存与持久层、任何 latest-ref 形态都会重演。
2. **恢复类功能的判据清单（缺一不可）**：①刷新不丢 ②**恢复后继续操作** ③上界裁剪（条数/长度）
   ④脏数据容错（坏元素丢弃、不整份丢）⑤**出口可达**。⑤ 本轮实测形态：删掉**最后一条**会话后
   历史入口按钮随之隐藏，而列表视图仍开着 ⇒ 界面**无处可退**（修法 = 删空即自动收起）。
   **只写 ① 是最常见的漏。**
3. **上界与写失败要一起设计**：localStorage 配额超限时 `setItem` 抛的是**同步异常**；
   `saveSessions` 写失败时**逐条淘汰最旧会话再重试**（宁可丢最旧，也不能让"存不下"静默变成
   "整个功能失效"），并用「配额小到一条都放不下」的假存储钉住**不死循环**（隐私模式即该形态）。
4. **「进行中」状态不可持久化**：`streaming` 原样存下 ⇒ 刷新后那条消息**永远停在"思考中"**
   （没有连接再回来推进它）。落盘一律归一为 `interrupted`，空正文整条丢弃。

**工具层的两条陷阱（同轮实测，都会造成误判）**：

- 本地端口探活**必须 `curl --noproxy '*'`**：本环境带沙箱代理，服务**没在跑**时会被代理兜底成
  **502**，看起来像"在跑但报错"（真值应是 `000` / connection refused）。收尾验收照抄旧口径会误判健康度。
- **指针事件驱动**的 UI（如助手悬浮球：`pointerdown/up` + <4px 判定"点击"）用 `eval` 派发 `PointerEvent`
  是**开→关切换**：连派两次 = 没点；且 **React 提交异步**，同一次 `eval` 里"派发后立刻读 DOM"只会读到旧状态
  ⇒ **派发与读取分成两次 `eval`**，且**每次先读一次当前状态**（toggle 语义会把结论反过来）。

**关联**：[[KB-ENG-65]]（判据必须能变红）· [[KB-ENG-72]]（清单覆盖 ≠ 真实覆盖）· [[KB-ENG-56]]（只在特定条件下变红的断言等于没写）

### KB-ENG-91 「只搬位置」必须可机械证明；`export *` 的重名与 `import type` 的值是两类静默失效

**场景（2026-09-15，`IMP-005` 第一批）**：把 2751 行 / 290 个顶层声明的 `apps/web/lib/api.ts`
按业务域拆成 14 个分片 + 1 个只做转发的门面，判据是「**行为不变**」。拆完 AST 复核：
**289 条声明正文逐字符一致、0 处不一致**、导出面 **284 → 284**（丢失 0 / 新增 0）。

**四条可复算的判据（"行为不变"不靠"看起来对"）**：

1. **逐声明正文比对**：用 TS AST 取每条顶层声明的源码切片，与 **`git show HEAD:<path>`**
   逐字符比（不是与"我印象里的原文"比 —— 基准必须是不可变提交）。同时覆盖
   「搬迁漏了一条声明」（新文件里少一条 = 原文里有而新文件没有，需反向也比）。
2. **导出面集合相等**：原文件 `export` 出的名字集合 == 各分片导出名字集合的并集。
3. **分片之间不得重名**——`export *` 遇到同名会**静默丢名字**（ESM 歧义语义），
   症状是"某名字取不到"，而**任何单文件测试都不会报它**。
4. **跨分片 import 必须分「类型 / 值」**：函数与常量用 `import type` 引入后**不可调用**
   （tsc：`'x' cannot be used as a value because it was imported using 'import type'`）。

**私有助手怎么跨文件（设计要点）**：原文件里**没有 `export`** 的 5 个模块内助手
（`request` / `DEFAULT_TIMEOUT_MS` / `getJson` / `getJsonArray` / `sendJson`）切片后必须可见，
但**就地加 `export` 关键字会改掉声明正文 ⇒ 判据 1 立刻失效**。
⇒ 单列 `internal.ts` 并**追加一行** `export { ... };`，且**门面刻意不转发它**
⇒ 「被搬代码一个字没动」与「跨文件可见」同时成立，对外可见面也一个不多。
**一般化：要让被搬的代码更可见，用「追加导出语句」，不要改原声明。**

**「改回去也没人拦」的形态**：切片的收益只在**门面保持薄**时成立，而有人往门面里塞回实现时
**功能没坏 ⇒ 全部门禁全绿**。⇒ 需要**结构钉**（`lib/api-facade.test.ts`）：门面非注释行只允许
`export * from "./api/<域>";` · **分片 ⇄ 转发双向闭包**（新增分片忘了转发 / 转发指向已删文件，
两种漂移都抓）· `internal` 不得进公开面；并配 4 条**自证**。

⚠️ **自证样本必须"只在一个维度上违规"**：首版假门面漏写了 `market` 分片，于是判据同时报出
「漏转发」，把「到底是哪条判据生效」搞糊了（[[KB-ENG-65]] 同族：**样本不干净时，变红的原因
可能不是你测的那条**）。修法 = 让假样本在其它维度上完全合规，断言写成 `toEqual([唯一那条])`。

**元教训（本轮最值钱的一条）**：三类真缺陷（`import type` 误用 20+ 处、私有名不可见 2 处、
连带 `page.tsx` 推断退化 1 处）**全部由 `tsc` 抓出**，而上述两条最"像判据"的判据
（逐声明比对、导出面相等）**从头到尾全绿**。⇒ **纯文本 / 集合级判据证明不了语义等价**，
必须让**编译器**（类型层）与**运行时冒烟**（行为层）各补一刀：
本轮冒烟 = 四个业务域页面 + `performance.getEntriesByType('resource')` 的 `responseStatus`
直方图；出现 3 处非 200 时**直连后端复现同码**（502「数据源熔断冷却中」/ 400「symbols 非法」）
才能说清"与本次改动无关"—— 否则只能猜，而猜错的方向恰好是"回滚一个没坏的东西"。

**关联**：[[KB-ENG-65]]（判据必须能变红）· [[KB-ENG-72]]（覆盖 ≠ 真实覆盖面）· [[KB-ENG-60]]（扫描面写窄 = 全绿）· [[KB-ENG-87]]（"换个参数再跑"要改产生它的那一层）

### KB-ENG-93 Python 侧「只搬位置」的四条判据与三类静默失效；两个门禁项的判定面是**探针实测**出来的

**场景（2026-09-15，`IMP-005` 第二批）**：单文件 **1934 行 → `app/assistant/tools/` 包 9 个业务域分片 + 186 行门面**
（`core` / `registry` / `dispatch` / `market` / `themes` / `picks` / `agent` / `events` / `account`）。
判据照搬 [[KB-ENG-91]] 四条，落地时又抓到 **Python 特有的三类静默失效**：

1. **`AnnAssign` 漏名 ⇒ 双向同判据的假绿**：`TOOL_SPECS: dict[str, ToolSpec] = {...}` 是 `ast.AnnAssign`
   （目标在 `node.target`，**不是** `node.targets`）⇒ 提取器只读 `targets` 时这两条（`TOOL_SPECS` / `TOOL_LABELS`）
   **整条被丢**，而"门面覆盖"检查用的又是**同一套提取器** ⇒ 两面一致地少，谁都不报（[[KB-ENG-81]] 同族：
   **两侧同判据 ⇒ 必须另有一条独立于它的检查**）。修法两条：① `defined_names()` 覆盖
   `FunctionDef/ClassDef/AnnAssign/Assign`（多目标展开）；② **名字集合从落盘文件重新解析**，
   不复用内存里的中间结果 —— 「表里声明过的名字必须真的落在某个分片里」这条检查立刻抓出了它。
2. **函数内局部 import 被当成顶层需求**：`_t_minute_decisions` 等会在函数体里
   `from app.core.bjtime import beijing_now` `from app.market import minute_decisions as md` ⇒
   生成器按"用到的名字"补了一层顶层 import ⇒ `pyflakes` **两连报**
   （`imported but unused` + `redefinition of unused`）。修法：按语句收集**局部绑定名**并从外部 import 需求里扣除。
3. **`__name__` 会随搬家变值**：`log = logging.getLogger(__name__)` 搬进子模块后 `__name__` 变成
   `app.assistant.tools.core` ⇒ **文本逐字相同、语义却变了**。修法：作为**声明式替换**登记
   （改成硬编码原日志名 + 就地注释说明理由），并让工具**打印替换条数**——
   "允许的偏差"必须**具名登记**，否则"逐字相同"这句话本身就是假的。
   ⚠️ 替换表还要**把注释与语句分开**：首版把注释一起塞进"新语句"，比对时凭空多出一处不一致。

**门面（Python 没有 `export`）**：实测外部引用了 `_valid_date` / `_valid_symbols` / `_latest_trade_day`
这些**私有名**，还有 `T.tool_label` 这种属性访问 ⇒ 门面必须**逐个 re-export 全部顶层名**并用 `__all__` 登记
（`__init__.py` 的"导入但未使用"由 `__all__` 兜住，`pyflakes` 0）。
⚠️ 但**由 import 引入的名字**（如 `TTLCache`）不再在门面上可见 —— 属如实声明的边界（实测无人引用）。

**两个门禁项的真实判定面（用探针实测，不靠名字猜）**：

- `F 代码注释死引用`：输出格式为 `→ docs/{rel}（不存在）` ⇒ **只认 `docs/` 下的路径**。
  往 `app/` 的代码注释里写一个不存在的 `app/xxx.py` **不会**变红（探针实测）。
- `J 文档代码锚点`：往 `docs/` 里写不存在的代码路径**会**变红（探针 → `FAIL 1 处`；还原 → `OK`）✓。
  ⚠️ **本条目首版把机制写错了**（原写「对**同名目录存在**的路径**容忍**，所以文件→目录式重构不被误报」）——
  真机制是判据取 `cand.split("/")[-1] in basenames`：**只比对"这个文件名是否在 git 跟踪清单里"，
  与目录是否存在无关**。当时之所以绿，是**旧文件的删除尚未提交**（判定面 = git 跟踪清单、不是本地文件系统，
  见函数 docstring 与 [[KB-ENG-70]]）⇒ **结论：文件裂成包之后，所有点名旧文件名的行都会变红**；
  正确处置是**改写法**（指向包内实际文件）或登记容忍，**不能指望判据自己容忍**。
  ⇒ **元教训：不要从一次"绿"反推机制**——机制必须读实现，或做**反向探针**。此处我写的探针是
  "文件名与目录都不存在"的路径，**它变红与"目录存在而文件名不存在"变红原因不同**，
  我却用它推出了后者的结论，属**证据与结论错配**（[[KB-ENG-65]] 同族：样本不干净则变红的原因未必是你测的那条）。
- ⇒ **「扫描结果为 0」必须先确认判据的判定面，再用探针换方式复核**（本仓纪律又一次实证；
  [[KB-ENG-72]]：判据**覆盖了什么** ≠ 你以为它覆盖什么）。

**守卫真的响了（正向对照）**：切片后 `tests/test_event_loop_no_block.py` 的 `GUARDED_ROUTES`
按**具体路径**钉着旧的单文件路径 ⇒ 全量跑出 `1 failed`，守卫报错大意
「**<旧路径> 不存在（改路径了？同步更新本清单）**」⇒ 改路径即绿（现路径已同步为 `app/assistant/tools/events.py`）。
⚠️ 此处**刻意不复述路径字面量**：J 项会把这条**记录**判成"文档点名的资产已消失"——它只比对
"文件名是否还在跟踪清单里"，**不区分「在用资产」与「在案引述」**，这是 J 与 changelog 体裁的**结构性张力**：
叙述"某路径曾存在/已被搬走"的句子，天然含一个已消失的锚点。
⇒ **按路径枚举扫描面的守卫，在被扫对象搬家时会响亮报错、不静默**（与"glob 写窄 ⇒ 静默全绿"形成对照，
[[KB-ENG-60]]）；但也提醒：**扫描面写死路径 = 一次无提示的重命名就会让它失效**，二者需权衡。

**关联**：[[KB-ENG-91]]（TS 侧同类切片）· [[KB-ENG-81]]（两侧同判据的假绿）· [[KB-ENG-60]]（扫描面写窄）· [[KB-ENG-72]]（覆盖 ≠ 真实覆盖面）

### KB-ENG-94 阈值型**时间**判据会**既假红又假绿**；偶发失败复现不出来时的正确姿势

**场景（2026-09-15，`BUG-007`）**：`tests/test_provider_budget.py::test_remaining_budget_is_shared_across_sources`
断言「预算是**总量**而非每源配额」。原判据 = `elapsed < 0.3s` + monkeypatch 预算 0.15s，
让 s0 慢失败吃掉 0.1s、s1 挂起 30s。同一条判据**两个方向都失效**：

1. **假红（抖动）**：余量仅 **1.5×**（0.1 / 0.15）⇒ 一次调度抖动让 s0 自身耗时越过预算，
   `_attempt` 在 `left <= 0` 时**直接返回「请求预算已耗尽（未发起）」**、`_call_serial` 也
   `break` ⇒ s1 **根本不被调用**（实测全量跑时 `hang.calls == 0`；单独跑恒绿）。
2. **假绿（漏判）**：注入**真缺陷**（把「每源各发一份完整预算」那种实现注入 `_call_serial`）后，
   缺陷形态总耗时 = `0.1 + 0.15 = 0.25s`，**恰好落在 0.3 阈值之下** ⇒ 旧判据**全绿**。
   ⇒ 它此前**从未真正判过「预算是否共享」**，只在「慢到 0.3s 以上」时偶然响一声。

**现判据（结构关系 + 双分支）**：
- 预算放大到 0.5s（余量 5×），并在 stub 里用 `try/finally` 记下**每次调用实际被给到的时长**
  （被 `wait_for` 取消也记）——比在外层量「总耗时」更接近要判的量；
- 分支 ①：s1 被发起 ⇒ `0 < granted < 0.95 × 预算`（**残值**，不是一份新配额）；
- 分支 ②：s1 被跳过 ⇒ 报错文案**必须含「未发起」**，且**不得**记它的失败
  （没发起过请求不是它的责任，记了会误伤熔断统计）；
- 非法结局（s1 拿到 ≈ 一份完整预算）**在任何分支下都红** ⇒ 注入验证：新判据**变红**、旧判据**漏判**。

**四条可迁移纪律**：

1. **时间判据优先判「两个量的关系」，不要判「绝对阈值 + 小余量」**：抖动能造出假红，
   而缺陷本身可能恰好落在阈值内造出假绿 —— **同一条判据的两个失效方向要分别取证**。
2. **判据自证要做两问**：不只问「注入后能变红吗」，还要问「**它变红之前一直在判什么**」。
   本轮若不是反向注入真缺陷，不会发现旧判据其实**一直是空的**。
3. **让判据对「所有合法结局」都成立、只对非法结局变红**：天然抗抖动的写法是
   枚举合法分支（发起 / 跳过各一条），而不是把某一种合法结局钉成唯一期望。
4. **偶发失败复现不出来时，正确姿势是「读实现 ⇒ 找唯一可行路径 ⇒ 余量分析」，
   并如实标注「未复现」**：本轮人为 **8× 与 24× 忙循环负载共 16 次均未复现**原失败
   （忙循环 ≠ 真实负载：真实场景还叠加 IO / 内存压力与多进程共存）⇒ 不得写成「复现—修复对照」。
   **「没复现」是结论的一部分，不是省略项**（[[KB-ENG-56]] 同族：只在特定条件下变红的断言等于没写）。

**工具层技巧**：`monkeypatch` 同一常量时，autouse fixture 先设、用例内 `setattr` 后设
⇒ **用例内可放心放大预算**而不影响同文件其他用例（本轮即用此把该用例余量从 1.5× 提到 5×）。

**关联**：[[KB-ENG-65]]（判据必须能变红）· [[KB-ENG-56]]（条件性变红 = 没写）· [[KB-ENG-90]]（单读判据照不出缺陷）· [[KB-ENG-72]]（覆盖 ≠ 真实覆盖面）

### KB-ENG-95 门禁的判定面必须等于「CI 检出内容」；新增检查项时必须先问这一句

**事故（2026-09-15，CI 首次真正跑起来就红）**：把 40+ 提交从特性分支合入 `master` 后，CI 的

真因：**`.workbuddy/` 是 gitignored 的工作区目录（`git ls-files .workbuddy` = 0 条）**，

根下的裸名（`AGENTS.md` 等）父目录即根 ⇒ 一律判。无 git 环境（合成树单测）⇒ `None` ⇒ 退回文件系统口径。

**⚠️ 两条「探针本身可能无效」的教训（本轮实测踩到）**：

1. **探针必须先确认落在扫描面内**：我先在 `AGENTS.md` 上打探针测 N，结果「没红」——
   查实现才发现 `INDEX_FILES` **只有 `MEMORY.md` 与 `docs/INDEX.md`**，`AGENTS.md` 根本不在 N 的面内
   ⇒ **「没红」什么都没说明**。同理 `index_pointer_candidates` **刻意排除 `docs/` 开头的 token**
   （那是 B 的面）且不收裸名 ⇒ 用 `docs/...` 探针测 N 也是无效探针。
   ⇒ 通例：**判据自证的第一步是「证明探针进了判定面」**，而不是「看它红没红」。
2. **「修好」必须包含反向验证**：只验「该红的红了」无法排除「把门禁关掉了」。
   本轮特意补了 J 探针（同样形态、应保持绿）——**只证明能红，等于只证明了一半**。

**顺带修掉「诊断信息在最需要时缺席」的缺陷**：N 的**明细打印被嵌在 `for … idx_over` 循环里** ⇒
「体积不超限、只有死指针」时（= 最需要明细的情形）一条明细都不打、CI 日志只剩 FAIL 行 ⇒ 已修。**诊断输出本身也要有判据**：「这条信息在最需要的时候在不在场？」

**Meta：为什么这些红能潜伏 40+ 提交**——CI 原先只写 `on.push.branches: [master, main]`，**开发分支推送不触发任何 CI** ⇒
门禁被推迟到合并那一刻，而那时改动面最大、排查成本最高（本次实证：合入即红）。已把 `develop` 加进触发列表。

**工具化副产品（可复用）**：`git worktree add --detach /tmp/ci-sim HEAD` **就是「模拟 CI 检出」**——
它只含跟踪文件、没有 `.workbuddy/` 等本地目录 ⇒ **任何「本地绿 / CI 红」的怀疑都该先去那里跑一遍**
（本轮全部验证都建在这上面，比反复推 CI 等结果快得多）。

### KB-ENG-97 FastAPI 路由横切切片：函数行号丢装饰器、`include_router` 合并 tags —— 两类静默失效 + 跳过数增量必须归因

**场景（2026-09-15，`IMP-005` 批 3）**：`backend/app/api/routes/market.py`
**1799 行 / 50 端点 / 62 个顶层定义** → 1 个跨域共享辅助模块 + **8 个业务域分片** + **45 行门面**。
与 [[KB-ENG-93]]（助手工具层由**单个模块**切成**包**；其旧单文件路径已消失，
本条目**刻意不复述该字面量** —— 文档锚点守卫不区分「在用资产」与「在案引述」，见该条末段）同族，
但**不是纯文件搬家**：
它是 **FastAPI 路由 + `APIRouter` 装配**，故判据还须覆盖「对外契约」与「路径匹配结果」。

**静默失效 1：`ast.FunctionDef.lineno` 指向 `def` 行、不含装饰器 ⇒ 端点凭空消失。**
用它当搬运的行区间起点，会**静默丢掉整行 `@router.get("/board-fund")`** ——
函数体在、docstring 在、**定义集合比对全绿**，唯独端点没了。
⇒ 修法：`def_start_line(node) = min(node.lineno, *(d.lineno for d in node.decorator_list))`。
⚠️ **本轮判据自证一度对这条缺陷双重盲**：C2「正文逐字」复用了**生成器的同一个行区间函数**
⇒ 生成侧与校验侧同判据 ⇒ 一起少、谁都不报（[[KB-ENG-81]] 同族）。
**补偿判据 = C3（从装饰器解析 `(method, path)` 端点集合）** —— 它取**不同事实来源**；
实测修前 C3 报「原 50 个 / 新 **0** 个」，一击命中。

**静默失效 2：`include_router` 对 `tags` 是「合并」语义，不是覆盖。**
门面写 `APIRouter(tags=["market"])` 且 8 个子 router 也各自声明 `tags=["market"]`
⇒ 最终 OpenAPI 里 tags 变成 **`["market", "market"]`**。
计数（paths 166 / ops 177 / schemas 106）与参数**全对**，**只有 tags 不一致**。
⇒ 判据若写成「路由表条数相同 / 端点集合相同」就**完全抓不到**——必须**逐条比对每个操作的字段**
（本仓工具逐条比 `operationId` / `parameters` / `tags`，见 `.workbuddy/tools/openapi-contract-diff.py`）。
落地选择：**门面刻意不声明 tags**，标签由子 router 独占声明。

**静默失效 3：切片把「同文件内的私有函数调用」变成「跨模块导入私有名」。**
原文件里 `_meta` / `_dated_meta` / `_latest_trade_date` / `_hub_freshness` 被 **39 处**直接调用；
按文件切开后若保留原样，消费方就得 `from app.api.routes.market_envelope import _meta`
⇒ 直接踩既有守卫 `test_routes_do_not_import_each_others_privates`。
⇒ 修法：搬运时**主动去下划线**（4 个跨域共享辅助升为公共名），**不是放宽守卫**。
⚠️ 该守卫**因切片才首次被赋权**：切片前 50 个端点同处一文件，跨模块私有导入**不可能发生**；
切片后才成为真判据。（对照 [[KB-ENG-93]]：按路径枚举的守卫在搬家时报红是**特性、不是噪声**——
本轮同形态复现一次：`LONG_TTL_REGISTRY` 的键含宿主文件路径，位点随域搬进 `market_flow.py` 后
守卫**正确报红**（两侧同时触发：新位点未登记 + 旧登记项已不存在）。修法 = **同步键**，理由文本不动。）

**跳过数增量必须能归因到具体文件（集合恒等式）**：本轮 `collect +9 / passed ±0 / skipped +9`，
其中 8 项来自新分片、1 项来自共享辅助模块，**9 项全部落在 skipped 而非 passed** ——
因为 `test_import_lint.py` 的分层规则把 `app/api/**` 判为**装配层**（`_is_business()` 返回 `False`）⇒ 显式跳过。
机械核验：`app/` 下非业务层模块 = **69** = 31（`api/` 装配层）+ 38（其他非业务层），
与 `skipped 71 − 2 = 69` **逐字相符**。
⇒ **「+8 个文件 ⇒ +8 个测试」不等于「+8 项覆盖」**：增量可能只是**参数化跳过项**（[[KB-ENG-72]]）。
报门禁数字时只说 collect 涨了，等于把「没跑的用例」记成「覆盖增强」。

**⚠️ 本条自身踩的门禁（2026-09-15 实测，已修）**：首版写「与 [[KB-ENG-93]]（<旧单文件路径> 单文件 → 包）同族」，
**当场把 `tests/test_doc_health_anchors.py::test_real_repo_has_no_dead_doc_anchor` 判红**——
①该旧路径已被上一批切走，②**文档锚点守卫不区分「在用资产」与「在案引述」**。
教训：**写"某路径曾存在/已被搬走"的句子必然含一个已消失的锚点** ⇒ 一律用**占位描述**（"旧单文件"），
**不要复述字面量**，也不要靠登记豁免绕过。
⚠️ **第二个红点更隐蔽**：同段写了新分片名 `market_flow.py`，该文件**真实存在**却仍判红 ——
因为判定面 = **git 跟踪清单**，而未提交的新文件不在其中（[[KB-ENG-95]]）。
⇒ **"文件真的在"与"判定面认为它在"是两件事；写新文件名的文档，要等 `git add` 之后才可能绿。**
⇒ **附带纪律**：本轮**只有 `TZ=UTC` 全量跑才暴露它**（首次非 UTC 全量跑在该文档写入**之前**，故为绿）
——**"刚跑过一次全绿"不能替代"改动之后再跑一次"**。
