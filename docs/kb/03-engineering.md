### KB-ENG-16 flex 高度链：中间层块级元素会让 overflow-y-auto 全部失效
- **现象**（两次踩坑，用户明令不再犯）：面板内容超高时页面无法滚动——overflow-auto 容器拿到的
  是「内容高」而非「受限高」，滚动永不触发。
- **根因**：flex 高度链在中间层断掉。FadeSwap 等 tab wrapper 若是**块级元素**（未设
  flex flex-col），其子面板的 flex-1/min-h-0 不产生约束高度 → 内部 overflow-y-auto 失效。
- **正确做法**：高度链每一层都要接力——wrapper `flex min-h-0 flex-1 flex flex-col overflow-hidden`，
  面板根 `h-full min-h-0` + 自管滚动（overflow-y-auto 或内部分栏各自滚）。
  **新建任何「左树右详情/上表下详情」面板时，先把高度链从头到尾写对再写内容。**
- **自查命令**：浏览器 eval `pane.scrollHeight > pane.clientHeight && pane.scrollTop 可设置`。

### KB-ENG-17 lark-cli 发消息：`--content` 必须是 JSON，且别把 validation 误判成身份失败
- **用法**（2026-09-09 实测）：`lark-cli im +messages-send --user-id <open_id> --as bot --msg-type text --content '{"text":"..."}'`，
  或用 `--text '...'`。**直接传纯文本会报 `--content is not valid JSON`**。
- **防误判**：该错误是 `type=validation / subtype=invalid_argument`，**不是身份/权限失败**。
  此时若按"--as bot 失败就重试 --as user"的兜底逻辑去重试，会**多发一条重复推送**（议程类推送红线：一天仅一条）。
  正确做法：先把文本用 `python -c "json.dumps({'text': txt})"` 落文件，再 `--content "$(cat file)"`。
- **通用教训**：「失败后换身份重试」这类兜底，必须先区分**参数校验失败**与**鉴权失败**，否则兜底动作本身会破坏幂等。

### KB-ENG-18 ❌（结论已被取代 → KB-ENG-20）「日志里没有」≠ 没发生：先看 logger 级别
- **原结论作废**：当日归因为「app logger 级别是 WARNING，INFO 不落盘」——实测 root level 是 INFO。
- **真因见 KB-ENG-20**：启动时程序化 alembic 迁移的 `fileConfig(disable_existing_loggers=True)`
  把迁移前创建的 logger（含 evolution、uvicorn 自身）**整体 disabled**，与级别无关。
- **仍然成立的教训**：判断后台任务存活走落库/端点侧证据（本次：agent_agenda 表 + API），
  不要拿"日志里没有"当证据——日志通道本身可能已断。

### KB-ENG-19 测试不得写真实仓库路径：_EVOLUTION_DIR 锚定仓库根，必须注入隔离
- **事故**（2026-09-09）：`tests/test_evolution.py` 的 B 类夹具（"watcher 阈值偏松"/"沉淀今日结论"）
  经 `_execute_b` 写入 `_EVOLUTION_DIR`（= 真实 `docs/evolution/`），**每次 pytest 全量都向真实
  `docs/evolution/当天.md` 追加**——单日累计 84 行垃圾（09-08 也 85 行），进化日报不可读。
- **根因**：`PROJECT_ROOT = Path(__file__).parents[3]` 锚定真实仓库根；测试 patch 了 DB 会话
  却没 patch 文件路径 → "DB 隔离了、文件没隔离"。
- **修复**：sf fixture `monkeypatch.setattr(evo, "_EVOLUTION_DIR", tmp_path/"evolution")` +
  回归测试 `test_b_class_never_touches_real_evolution_dir`。
- **通用教训**：凡是"模块常量指向真实仓库路径"的写入口，测试 fixture 必须一并隔离；
  只隔离 DB 不隔离文件 = 半吊子隔离。清理时保留 evidence 非空的条目（垃圾特征：`依据：{}`）。

### KB-ENG-20 程序化 alembic 迁移的 fileConfig 会 massacre 全部既有 logger（议程静默事故主因之二）
- **事故**（2026-09-09）：15:45 进化议程静默未生成。直接死因是 `_LAST_SHADOW_DATE` NameError
  （每 tick 崩溃，见下）；**但零日志可取证**的原因是 `migrations/env.py:35`
  `fileConfig(config.config_file_name)`——默认 `disable_existing_loggers=True`，每次启动把
  迁移前创建的所有 logger **整体 disabled**：uvicorn 自身（"Application startup complete" 消失）、
  main、以及随 routes 在 import 期加载的 `app.services.evolution`。log.exception 照样被吞。
- **判定特征**：日志里只出现**迁移之后才懒加载**的模块（watcher/fund_flow/review_intraday）
  的告警、且格式是 alembic.ini 的 `%(.5slevelname) [name]`；迁移前创建的 logger 零输出。
- **修复**：①程序化迁移 `cfg.attributes["configure_logger"]=False`（env.py 跳过 fileConfig）；
  ②CLI 直跑保留但 `fileConfig(..., disable_existing_loggers=False)`。
- **通用教训**：库代码里任何 `fileConfig/dictConfig` 都可能 massacre 宿主日志配置；
  程序化调用第三方 CLI 入口时，先查它有没有"顺手重配日志"的副作用。
  另：**"某模块日志消失" ≠ "该模块没跑"**——本次调度器明明在每 tick 崩溃，日志却一片祥和，
  逼着人往"任务没起/守卫没过"的错误方向排查。

### KB-ENG-21 议程调度器三重防护（2026-09-09 事故收口）：缺失全局、可观测、liveness 面
- **直接死因**：`evolution_scheduler` 用 `global _LAST_SHADOW_DATE` 声明并读写，但模块级从未定义
  （4f24462 影子批次引入）→ NameError 每 tick 崩溃且发生在议程块**之前** → 议程永不生成、无任何日志。
- **修复与防护**（evolution.py）：
  ① 模块级补 `_LAST_SHADOW_DATE: str = ""`；
  ② 观测：scheduler started / 窗口触发 / 议程完成全部 `log.warning`（INFO 不可信，见 KB-ENG-20）；
     跳过原因按 (日期, 桶) 节流每日一条（`_log_skip_once`），不刷屏；
  ③ liveness 面：每 tick 刷 `_SCHED_LAST_TICK`，`scheduler_status()` 经 `GET /api/agent/agenda`
     的 `meta.scheduler_status` 暴露（last_tick_at / last_tick_age_sec）——**data=null 时先看调度器死活，
     age > 120s 即停摆**；15:45 推送 automation 与哨兵据此区分"调度死了"与"真没有"。
- **回归测试**：`test_scheduler_fires_when_clock_crosses_window`（受控时钟驱动真实循环跨 15:45 窗口）
  + `_MIN_TICK_INTERVAL_SEC` 可注入（生产恒 60s，行为不变）。
- **教训**：`global X` 声明的名字必须模块级有定义——静态检查抓不到（pyflakes 不报），
  只有"驱动真实循环"的测试能抓；调度类代码必须有可观测的 skip 原因与 liveness 暴露。

### KB-ENG-22 写入侧必须落齐下游过滤所依赖的字段（告警快照漏 `name`，静默丢弃全部条目）
- **现象（2026-09-10）**：`watcher.dispatch_alert` 持久化的事件快照只落了
  `kind/direction/text`，**漏落 `name`**。而消费端悬浮球 `alert_triage.pending_bubbles`
  要求 `symbol` 与 `name` **同时齐备**，缺任一整条过滤（2026-09-09 用户指令）。
  结果：实测 14 条 notify 事件快照**全部 `name=None`** → 悬浮球一条 watcher 个股提醒都收不到，
  且**链路无任何报错**（事件照常入库、判读照常通过）。
- **正确做法**：契约字段（下游过滤/展示所依赖的）必须在**写入侧一次落齐**，
  不能依赖"上游 alert dict 里有"——落库/序列化处是最后一道闸；新增过滤条件时同步回查
  所有写入点（对应 KB-ENG-05 第 3 条）。
- **测试**：`test_dispatch_alert_snapshot_keeps_name`。

### KB-ENG-23 队列消费：先「过滤未处理」再 `limit`，绝不能先 `limit` 再过滤
- **现象（2026-09-10）**：`alert_triage.triage_pending` 原实现取「最近 `limit` 条」再过滤已判读。
  一旦某时段事件量 > limit，**更早的未判读事件被新事件永久挤出窗口**，再也不会被判读。
  实测库内 **75 条从未判读**（含 falsify 18 —即方向证伪这类高价值信号、flow_surge 46、
  break_rate 7、high_board_break 3）。
- **正确做法**：用 `WHERE id NOT IN (SELECT event_id FROM 已判读表)` 让数据库先做差集，
  再 `ORDER BY time DESC LIMIT n`。单轮处理量仍由 `RECENT_LIMIT` 封顶（防 LLM 突发批量）。
- **教训**：「取最新 N 条再筛」是**有状态的队列**里最隐蔽的漏处理模式——它不报错、不堆积，
  只是让一些条目**永远排不到**。任何"按时间取窗口 + 过滤条件"的消费逻辑都要先问：
  积压时新条目会不会把旧条目挤出去。
- **测试**：`test_triage_pending_reaches_old_unjudged`（1 条 12h 前 + 30 条新事件，
  断言最早那条必被判读）+ `test_triage_pending_skips_judged`（幂等）。

### KB-ENG-24 告警/信号阈值先量「噪音比 + 下游预算」，别只看触发量
- **现象（2026-09-10，P1-16）**：`flow_surge` 阈值 0.3 亿，日均产出量看着不大，
  但实测库内 151 条事件的判读中 **102/105 = 97.1% 被 LLM 判读层 ignore**（理由全为
  "冷却窗口内已提醒"）；触发值中位数仅 0.92 亿，0.3 亿档贡献了 51.7% 的事件。
  更严重的是**挤占判读预算**——`triage_pending` 每轮上限 20 条，噪音把窗口占满，
  导致 75 条事件**从未被判读**，其中包含 `falsify`（方向证伪）这类最高价值信号 18 条。
- **正确做法**：①先算**噪音比**（被下游忽略的比例）而不是触发量；②再看**下游预算**
  （LLM 判读是有限资源，噪音排挤的是高价值信号，损失不对称）；③改阈值同时加
  **每拍 Top-N 上限**，未入选的**排队而非丢弃**（`FLOW_ALERT_PER_BEAT=5`）；
  ④阈值配置化 + 非法/非正回退记日志，**不静默改口径**。
- **推广**：所有"触发即产生下游处理成本"的阈值（告警、候选池、采样率）都适用——
  衡量的不是"产出了多少"，而是"下游真正消费了多少、被挤掉了什么"。

### KB-ENG-25 下游「绕道别的列表按 symbol 匹配」= 契约缺失的假解法
- **现象（2026-09-10，盘中跟踪卡片「入选原因」恒空）**：真身 `rec.reason`（同花顺
  官方涨停原因串）**从未导出到 ladder 行**，消费方只能绕道 `leaders.candidates` 建
  `symbol→reason` 映射；而那份列表在源头被过滤为**仅「补涨/反包」两种角色**（语义槽是
  "龙头打出空间后的低位替代"）、值是**硬编码文案** ⇒ 龙头/中军/空间板/首板… 全部
  取不到，卡片恒空。
- **教训**：①字段的真实来源必须在**产生它的那一层就导出**；下游"找不到就绕道另一个
  列表按 symbol 匹配"是契约缺失的信号，不是解法。②按 symbol 在**语义不同**的列表里
  匹配，等于拿错误语义的值冒充正确语义（硬编码角色说明冒充官方原因）——**比取不到更
  危险**，因为它会静默产出看起来合理的内容。③**已有测试会把错误链路固化成断言**
  （原断言注释即写"candidates reason 按 symbol 匹配进 ladder"）：测试全绿 ≠ 行为正确，
  修契约时必须连断言一起改，并加"同 symbol 但文案不同"的对抗性 fixture。
- **修复**：`theme_service` 在 ladder 行导出 `reason`；消费方改 `rung.get("reason")`。
  变异验证：还原旧写法 → 2 项用例失败且报错精确指向旧行为。

### KB-ENG-26 补全逻辑写在某一个路由里 = 同组件被两条数据源喂出两种样子
- **现象（2026-09-10，用户："其他板块打开的字段不一样"）**：`price/stop_ref/exit_plan`
  的补全内联在 `/api/picks/intraday-top` 路由；题材手风琴走 `/api/picks/intraday-
  opportunities`，两条链路**共用同一张选股卡片**（当时叫 `WatchCard`，09-10 与
  `PickCard` 合并为单一组件）⇒ 同一组件渲染出两种字段丰度。
  根因是 09-09 那轮"卡片与每日精选对齐"只改了其中一条路径。
- **教训**：①**"可选字段"最危险**——类型系统不报错，两条路径都能通过 tsc/eslint/
  vitest，只有真机渲染才暴露；②补全属于**数据契约**的一部分，必须放进两端点共用的
  纯函数（此处 `intraday_opportunity.attach_risk_fields(stocks, snap_by)`）；③每拍
  变化的字段（现价）**不进 TTL 缓存**，且**缓存命中分支也要补**（最容易漏的一条路径）；
  ④**不适用 ≠ 缺失**：某来源本就没有的维度，宁可整节不渲染，也不要用「—」占位冒充
  "有数据但没取到"——那会让三态纪律的语义反向失效。
- **推广**：任何"多数据源 → 单一展示组件"的组合，先问：这个字段有几个产生点？
  补全/规整/兜底有几份实现？**多份即漂移**。

### KB-ENG-27 判断「两个组件该不该合并」：先看输入契约能否归一，再看渲染分支数
- **现象（2026-09-10，用户："这两张卡片字段都是不一样的，共用时应该互补，合起来才是完整的"）**：
  `PickCard`（盘前名单）与 `WatchCard`（盘中名单）长期并行。`card-shell.tsx` 里还留着
  一条**写死的错误结论**："只抽壳、不抽内容——两卡分节语义差异大，强行合并会把条件
  渲染做成 5 处分支，可读性反而崩"。该结论把一个**输入契约问题**误判成了**渲染复杂度
  问题**，于是合并一直被劝退。
- **正解**：两卡的字段是**互补**而非重复（盘前有六维评分/估值/买入区间/失效条件，
  盘中有辨识度·确定性判定/涨停原因/T 档/题材强度档）。合并通路不是「在渲染层堆分支」，
  而是**在适配器里归一输入**：`fromDailyPick(DailyPickItem)` / `fromIntradayStock(...)`
  → 中间模型 `TradingCard`，渲染层只认一种形状、每节「有则渲染，无则整节不出现」。
- **两条硬纪律**：
  ①**异名同义字段必须在适配器单点归一**（本例 `role↔echelon_role`、`stage↔theme_stage`、
  `stop_ref↔stop_loss`、`exit_plan↔exit_discipline`）——下游若再写
  `item.role ?? item.echelon_role`，等于把归一逻辑又散回渲染层，等于没合并。
  ②**来源缺的维度不补、也不留白**：整节不渲染 + 卡底一句**口径注记**说明"为什么没有"
  （"盘中实时口径…不含收盘六维评分与买入区间"）。渲染占位「—」是把"该来源本就没有
  这个维度"伪装成"有数据但没取到"。
- **副作用要一并清**：合并后 `exit_plan`（未定型 dict）取值可能一项都没有 ⇒ 归一为
  `null` 而非 `trailing_pct: 0`（渲染出"回落 0%"是臆造数字）；测试要覆盖"整节不渲染
  + 口径注记出现"，而不是覆盖"渲染了占位"。
- **推广**：评估"重复实现要不要合并"时，先问**输入能否归一到单一契约**。能归一 ⇒
  渲染分支数是伪问题（各节只是可选）；不能归一 ⇒ 才轮到讨论拆分。**判定依据要写进代码
  注释，否则下一个人会继续引用那条过时结论。**
- **补充（同日，用户第二轮反馈）**：**合并卡片 ≠ 合并分区**。字段统一后用户仍要求
  "盘中跟踪和盘前选择放两个容器、两条瀑布流、盘中有上面" —— 因为**来源节奏不同**
  （盘中=当日实时动态名单，盘前=收盘定次日持久组合）。教训：组件复用解决的是
  "同一件事别写两遍"，**不解决"两件不同节奏的事别混在一个视图里"**；两者是正交的。

### KB-ENG-28 用户说「没有 X」时，先分清三种成因（数据没产生 / 有数据没标签 / 标签语义漂移）
- **现象（2026-09-10，用户："盘前选择怎么没有入选原因呢"）**：实测 `GET /api/picks/today`
  5/5 只票的 `bases` 七维齐全（情绪/消息/技术/基本/资金/梯队/筹码），依据行一直在渲染
  ——**数据一条没丢**。真正缺的是：盘中卡有一行标签「入选」，盘前卡只有七行维度行、
  **没有标题** ⇒ 用户扫过去判定"这卡没有入选原因"。
- **三分诊断（排查顺序）**：①**数据没产生**（真缺口，改产生层，见 KB-ENG-25）；
  ②**有数据但没标签**（本次；改展示层，最小改动即给分节加标题、两侧口径一致）；
  ③**标签语义漂移**（数据在但挂错名，如 `reason` 曾标成「依据」，见 KB-ENG-26 同轮修复）。
  **不先分清就动手，很容易去改后端补一个本来就在的字段**（浪费 + 引入重复契约）。
- **验证手法**：先 `curl` 原始载荷确认字段在不在（**不要靠看界面猜**），再逐卡枚举
  渲染文本比对。本次靠 `grep`/Python 统计「入选原因」标题数 = 卡片数（3 盘中 + 5 盘前 = 8）
  一次对齐。
- **推广**：UI 上的"缺失"报告一律先落到这三类之一再动手；**"看起来没有"与"真的没有"
  是两种缺陷，修复面完全不同**。

### KB-ENG-29 全局门槛复用前先验量纲：回放分 ≠ 线上分
- **现象（2026-09-10）**：给线上组合加「入选门槛 MIN_PICK_SCORE=50」后，

### KB-ENG-30 名额类常量要区分「上限」与「目标」
- **现象（2026-09-10）**：`MAX_PICKS = 5` 长期被当作"每天输出 5 只"的目标值使用

### KB-ENG-31 多来源拼装的行必须按**唯一键**去重；「撞约束」的兜底不能把两类故障合并
- **事故（2026-09-10）**：快讯事件整条丢失——服务日志刷屏
  `flash news: add_event failed … IntegrityError: UNIQUE constraint failed:
  event_direction.event_id, event_direction.target_type, event_direction.target`。
- **根因**：`extract.build_event` 的方向行来自**四个来源**（文本命中题材名 / 传导链 /
  来源标的 / 东财板块映射），但只有前两者之间做了去重（`_dedupe_chain_rows`），
  **末尾追加的板块行没去重**。当文本命中与板块映射落到**同一个题材**时
  （实测：`南非七月份黄金产量…` 经 name-stem 命中「黄金概念」，东财板块「黄金」
  又映射到同一个「黄金概念」）就产生两行相同 `(target_type, target)`。
- **为什么放大成「整条丢失」**：`EventStore.add_event` 的兜底写着
  `except IntegrityError: 按重复处理`。这是一种**把两类故障合并成一类**的写法：
  ①并发插入同一指纹（应降级为"重复"）②**新事件本身违反约束**（应报错并修产生层）。
  合并之后：fingerprint 查得到 → 静默吞；查不到 → `raise`（日志里只看到一条
  "偶发错误"）。**两种情况都不会被当成 bug 处理**，于是事件每轮轮询重试、每轮都失败。
- **定性证据（排查手法）**：直接查库——`event_card` 里**根本没有**这两条标题。
  「查不到」= 丢了（事务整体回滚），**不是**"没更新"。判断"数据缺失"与"数据没生成"
  必须落到库，不能只看接口返回空。
- **修法（两层）**：①产生层 `extract.dedupe_directions` 按 `(target_type, target)`
  **精确**去重、保留先到者（顺序即优先级：文本证据 > 板块代码推断；板块行在无文本命中时
  仍独自生效，P0-3 的 ~35% 快讯不受影响）；②存储层保留最后一道防线，真去重时
  `log.warning` 留痕——**保住数据、但把问题留在日志里**，绝不静默。
- **推广**：写 `except IntegrityError` 之前先问「这个约束可能被**几种**原因触发」；
  多来源拼装一组行时，**按数据库唯一键的口径去重**（用模糊/语义去重会误丢合法关联）。

### KB-ENG-32 档位标签（level）是**计数产物**，不能当语义判据用
- **现象（2026-09-10）**：空仓闸门的 `level`（strong/mild）由 `len(reasons) >= 2` 决定，
  是个**计数**；而下游「要不要撤买入区间」被写成 `level == "strong"`。于是
  「相位=退潮」单条理由 → level=mild → 不撤区间；「晋级率 29% 差 1 个点擦线」也是
  1 条 → level=mild → 同样不撤。**两种性质迥异的信号被同一个标签压平**。
- **为什么会写错**：`level` 命名自带「严重程度」的含义，读代码的人（和写代码的人）
  都会自然地把它当语义判据。但它的定义里没有任何「信号性质」信息，只有「触发了几条规则」。
- **正解**：判据按**信号性质**另写（`should_strip_buy_range`：相位级 vs 阈值擦线），
  并且**结论算在产生点、下游只读**（落库 `strip_buy_range` 字段），避免前后端各算一遍。
- **推广**：用枚举标签做条件分支前，先回去看**这个标签是怎么算出来的**。凡是
  「按数量/比例分档」得到的标签（low/medium/high、mild/strong），都只携带计数信息，
  拿它表达语义（严重性、可信度、可执行性）迟早错配。

### KB-ENG-33 调度链路的一端传错类型 = 静默数周的数据陈旧（异常被 except 收成日志）
- **事故（2026-09-10）**：情绪指标库（`backend/data/sentiment_metrics.json`）停在
  **2026-09-01**，连续 **6 个交易日**没有更新；而界面照旧写着「按近 241 个交易日的
  历史分位校准」——窗口漂移了 6 天，没有任何告警。
- **根因**：调度侧把 **provider 原始日历（字符串）** 直接喂给 `metric_history.backfill`，
  而 `backfill` 里是 `d < today` 的 `date` 比较 →
  `TypeError: '<' not supported between instances of 'str' and 'datetime.date'`。
  异常被调度器的 `except Exception` 收成**一条 ERROR 日志**，每 6 小时一条、没人看。
  项目里日历有**两条取用路径**：`trade_calendar.trading_days()`（归一化为 `date`，
  带官方→日K回落）与「直取 provider 原始日历」——后者类型未归一。
- **为什么难发现**：①失败是**被动**的（数据没变，而不是报错爆掉）；
  ②界面文案仍然成立（"按近 241 个交易日"是真话，只是这 241 天是几周前的）；
  ③手动跑一次就成功 → 容易归因成"偶发"。**手动复现成功 ≠ 调度正常**，
  必须用「重启后一段时间文件 mtime 是否变化」或心跳日志来验证调度本身。
- **修法**：①调用方改用归一化入口 `tc.trading_days()`（单一真相源）；
  ②被调方对日历元素做 `_as_date()` 归一（传错类型不该是沉默数周的数据缺陷）；
  ③**稳态也打一行心跳**（原来是"只在有新增时打日志"+失败另一条 ERROR，
  两条都不出现时无法区分"跑得很健康"与"根本没跑"）；
  ④纳入数据健康哨兵（`_collect_data_health` 新增 `sentiment_metrics` 检查，
  按**交易日**滞后数判陈旧，>3 报 NG）。
- **推广**：只要"调度 → 数据文件"这条链上任意一段的类型/口径不一致，故障表现就是
  **数据停更**而不是崩溃。这类链路的验收必须包含「观测调度本身」的手段（心跳日志 /
  mtime / 哨兵），不能只看下游数据对不对。

### KB-ENG-34 `describe()` 型接口：确认它描述的是"谁"的位置，再拿来当"今天"

### KB-ENG-35 运行时覆盖：默认值**不能在签名里绑定常量**，`None` 已有语义时要上哨兵

### KB-ENG-37 HTTP 200 不等于契约满足：`.json().catch(() => ({}))` 会把「响应非 Envelope」静默变成 `undefined`
- **事故（2026-09-10 用户报错）**：Safari 显示 `undefined is not an object (evaluating 'reviews.length')`，
  Chrome/错误边界显示 `Cannot read properties of undefined (reading 'length')`。
  **两种措辞，同一个 bug**——报错文本指向页面自身代码，与真实根因隔了好几层。
- **根因（`apps/web/lib/api.ts::request`）**：
  ```ts
  const body = (await res.json().catch(() => ({}))) as {...};
  if (!res.ok) throw new ApiError(...);
  return body as { data: T; meta: Meta };   // ← 200 + 非 JSON 时，body={}，data 是 undefined
  ```
  ① `.json()` 解析失败被 `catch` 吞成 `{}`；② `res.ok` 为真 → 不抛；③ 断言 `as {data:T}` 让 **TS 也看不出**
  这里可能是 undefined。于是调用方 `.catch(() => [])` 看似安全——**它只兜「抛错」，兜不住「返回 undefined」**，
  `setReviews(undefined)` 之后任何 `.length` 访问就崩。
- **为什么"静默"比崩溃更值得警惕**：变异验证时关掉校验，`{"items":[]}` 这类响应会退化成
  `data ?? []` → **空列表**——界面显示「暂无数据」，用户以为正常。**同一种契约破坏有两种伪装：
  崩溃（指向错误的地方）与空数据（看起来正常）**，后者更难发现。
- **修法（单点收口）**：`request()` 在 200 时校验 `"data" in body`，缺失即抛
  `ApiError(code="bad_envelope")` ⇒ 所有调用方的 `.catch` 立刻生效、错误可见、崩溃点回到根因附近；
  另设 `getJsonArray()` 供**列表接口**专用（`data: null` 是后端「无数据」的合法形态 → 归一 `[]`，
  而**缺 data 键仍由 request 层抛**，不在 helper 里吞）。
- **连带修正（诚实提示）**：路由错误边界原文案只有「反复失败请确认后端已启动」——
  本类故障与后端是否启动**无关**，照文案排查会走偏。已改为两步线索：
  ①确认进程 ②进程在跑仍失败则多为**接口响应异常**（HTTP 200 但响应体非预期结构），到 Network 面板看实际返回。
- **验收（可复现的受控证据，非推断）**：`network route` 把 `/api/picks/review` 钉成
  `200 + text/html`——修复前页面落错误边界（正文 166 字符）；修复后同桩下
  **页面正常渲染（正文 12246 字符，闸门横幅与卡片俱在）**，接口失败被降级为该模块无数据。
  单测 6 项（正常 Envelope / HTML → bad_envelope / 缺 data 键 → bad_envelope / data:null → [] /
  非 2xx 沿用 detail / history 同样归一），变异验证关掉校验 → 2 项精确失败。
- **推广**：**`res.ok` 只证明"传输成功"，不证明"契约满足"**。凡是把响应体直接断言成目标类型的地方，
  都要问一句「解析失败 / 结构不对时，我的代码会走到哪里」——**用 `catch` 兜错时，要同时确认
  被兜住的是「异常」还是「undefined 返回值」**（类型断言会掩盖后者）。

### KB-ENG-38 「滚不动」要先查**滚动归属**：`shrink-0` + 祖先 `overflow-hidden` = 内容静默被裁
- **现象（2026-09-10 用户报）**：「参数配置向下滚动不了」。
- **实测几何（agent-browser 读真实 DOM，不是看代码推断）**：
  根容器 `scrollHeight 717 / clientHeight 508`（**差 209px 需要滚**），但根 `overflow-y: visible`、
  父级 `FadeSwap` 为 `overflow: hidden` ⇒ 多出的 209px **被直接裁掉，一像素都滚不动**；
  同时「变更单历史」段被 flex 压成 **26px**（内容 154px）。
- **根因**：`FadeSwap` 的契约是「各 tab 根 `h-full min-h-0` + **自管滚动**」，而本页
  ①根缺 `overflow-y-auto`；②三段全是 `shrink-0`，**没有任何 `flex-1` 子区块吸收剩余高度**。
  ⇒ 高度没人吸收、滚动没人负责，溢出交给父级 `overflow-hidden`。
- **为什么现在才暴露**：内容是逐步变高的（当轮给该页加了「变更存活率」卡片、参数白名单 1→5）。
  **布局类缺陷常在内容长到阈值时才现形**——所以「以前没问题」不能作为「现在也没问题」的证据。
- **诊断口径（可复用）**：判「滚不动」看三个数，**沿祖先链**逐个读——
  `scrollHeight - clientHeight > 0`（确实有内容溢出）**且** `overflowY ∉ {auto, scroll}`（这层不负责滚）
  ⇒ 该层把滚动责任推给了祖先；若祖先为 `hidden` 就是「静默裁掉」。
  **不要用"代码里有没有 overflow-hidden"来判**，也不要靠读指令推断。
- **修法与验收**：根 `overflow-y-auto` + 子段一律 `shrink-0`；**验收标准是 `scrollTop` 能实际改变**
  （实测 0 → 339）且被压扁的子段高度恢复（26 → 156px），而不是"看起来有滚动条"。

- **背景（2026-09-10）**：核验三倍量与五步法时各写了一遍"窗口函数 + 全市场对照 + 分层"

  `split_sample`/`limit_up_share`/`stats`/`baseline`/`render`/`welch_t`/`horizons_of`/`date_lo`。
  每个统计量同时输出**原始均值**与**市场中性均值（扣同日全市场均值）**。
- **四条方法论教训（都会导致"看着对"的错误结论）**：
  1. **t 值 ≠ 效应量**：按 t 值在参数网格里选规则，会挑到「样本量巨大、效应极小」的组
     （实测 n=35 万、t=+11.8，超额仅 +0.12%，扣成本即负）。网格选取必须**并列**
     「max t」与「max 效应量（设样本量下限）」两种准则。
  2. **市场中性必须按日对齐**：只用混合池均值做对照，会把"顺大盘"这类**市场级 beta**
     读成 alpha（好日子天然涨得多）。正确基准 = **同一交易日**的全市场均值。
     且这条**需要逐日波动的市场因子才能测出来** —— 合成数据若每天均值几乎相同，
     连"join 键错位一天"都测不出（本条的测试就踩过：第一版数据太规则，变异逃逸）。
  3. **均值要配中位与胜（跑赢）比例**：实测某规则样本外均值 +1.33%，但**中位 −0.08%、
     跑赢比例 49.3%** ⇒ 收益全靠少数极端样本（右偏）。只报均值 = 只报一半，
     且这种分布对资金曲线极不友好。
  4. **分组静默缺失会被读成"这一档不存在"**：SQL `GROUP BY` 不返回空组。漏斗/单条件
     这类"标签集合已知"的检验必须 LEFT JOIN 补齐、显式输出 `n=0`（三态纪律）。
- **实现坑**：聚合片段拼接用空格 join → `AS s1 count(fwd3)` 语法错误（报错位置误导，
  指向 `count`）；前瞻窗口是**建表期**属性，查询期必须用 `horizons_of()` 探测，
  否则换窗口后查询会引用不存在的列。

### KB-ENG-41 注册表一物二用、待办没有出口：登记层的三个漂移点
- **背景（2026-09-10，P1-36 escalate 接线）**：判读层 docstring 写着「escalate 进任务中心
  待办」，代码却只在 `agent_triage` 落一行 ⇒ **「升级」实际等于丢弃**。接线过程中暴露
  三个通用漂移点（都属"看起来已实现"）。
- **① 一份常量不能同时充当「标签注册表」与「可创建清单」。**
  `TASK_TYPES` 既喂 `GET /agent/task-types`（前端"新建任务"按钮的数据源），又当类型
  白名单；`mutation` 在其中但**没有 handler** ⇒ 按钮可点、点了必在 `_HANDLERS[type_]`
  抛 KeyError，**建出一条必然失败的 L1 任务**。
  **分界**：可创建集合 = **handler 注册表本身**（`CREATABLE_TASK_TYPES = frozenset(_HANDLERS)`，
  单一真相源，新增 handler 自动可创建）；标签元数据可以含不可创建项。
  前端对不可创建项走**本地标签兜底**（先例 `AGENDA_LABEL`），不为省一个 map 扩大接口暴露面。
- **② 待办必须有出口；且初始态语义要精确。**
  只登记不关闭 ⇒ 无限累积 ⇒ 淹没真正要看的条目（与"降噪"初衷相悖）。所以
  `record_escalation` 必须配 `resolve`（`done`→succeeded / `dismissed`→canceled），
  且**终态幂等**（重复处置不改写、不报错）。
  初始态不能图省事用 `queued`：`queued` = **等待执行**，而本类条目**永不执行** ⇒
  永久显示"排队中"并触发前端 3s 轮询（**假承诺**）。正解 `needs_confirm` = 等待人工处置。
- **③ 枚举/标签里存在 ≠ 已实现：状态机会长出「纸面状态」。**
  `needs_confirm` 早已在 `TASK_STATUSES` 与前端 `STATUS_META`（琥珀色"待确认"）里，
  但**没有任何生产者** ⇒ 它永远不可能出现（同族：纸面字段）。接线的真正内容是
  **"给它一个生产者 + 一个消费者（处置入口）"**，只加枚举值是空壳。
- **登记类写入口的两个范式（新增时二选一，勿用 `create_task`）**：
  | 范式 | 幂等性 | 初始态 | 收口 |
  |---|---|---|---|
  | `record_mutation` | 每次一条（可重复登记） | `queued` | `update_mutation_result` 回填结果 |
  | `record_escalation` | **确定性 id `esc-<event_id>`**（重入不刷第二条） | `needs_confirm` | `resolve_task` 人工处置 |
  `create_task` 是"创建并**启动**"（会拉起同类型互斥的执行），语义完全不同。
- **实现坑（三条，都是本次踩到/防到的）**：
  1. 登记发生在 `_save` 内，而 `record_escalation` 要另开 session ⇒ 必须在原 session
     **提交并关闭之后**再调用（SQLite 单写事务，嵌套会锁等待）；且登记失败只留痕不上抛
     （增强层降级纪律，判读落库不能被拖垮）。
  2. `record_escalation` 必须接受**可注入的 `session_factory`**：判读单测跑 tmp 库，
     若内部直接取全局工厂，**测试会往生产库写待办**。
  3. 单测里 `record_audit` 仍走模块级 `get_session_factory` ⇒ 需
     `monkeypatch.setattr(at, "get_session_factory", lambda: sf)` 才能让审计也落 tmp 库。
- **验证方式**：变异验证 2 次——①把 `if verdict == "escalate"` 改成 `notify` → 待办断言
  精确失败；②删掉 `esc-` 幂等守卫 → 两条测试以 `UNIQUE constraint failed: agent_task.id` 失败。

  3. **响应层同款假设**（端点把 `out["signals"]` 当模型列表）——同一错误在两个调用点各犯一次。
- **正解（写进「新模块」的验收清单）**：
  ① 模块测试之外**必须有一条真实调用链**（触发源 → 模块 → 出口），并在测试里覆盖**调用方**

  ② 接线缺陷**不能只靠「手工点一次页面」**发现——本轮 3 个缺陷全部由**新写的接线测试**逼出；

### KB-ENG-43 用「盘后批处理」替代「盘中实时采集」的四个前提
- **背景（2026-09-11，P1-24 接线）**：分钟级信号若盘中逐拍采集，需常驻任务 + 持续消耗行情配额；
  改为**盘后一次性重放全天分时**，可得**同样样本** + 零常驻任务 + 零盘中配额。
  但该替代**不免费**，成立依赖四个前提，缺一即不等价：
  1. **计算前缀稳定**：输出只取决于输入端序列内容、与「何时算」无关
     （全天分时重放 ⇒ 与逐拍实时产出**完全一致**的触发集合）。
     这同时是 `(symbol, trigger_ts)` 去重**可靠的前提**——不稳定就必然重复记账。
  2. **幂等标记落盘**：当日一次（`data/…/scan-YYYYMMDD.json`，原子写 tmp+replace）；
     **失败不写标记**（下次重试）、**无数据也不写标记**（当天晚些补数据仍会被扫到）。
  3. **数据来源唯一且不回落**：跟踪台账是唯一输入源，台账为空即**跳过并具名返回
     `no_tracked_symbols`**——**刻意不回落自选/全市场**。回落会把「今天没跟踪」
     变成「凭空产生信号」，样本口径被污染（**口径干净 > 覆盖率高**）。
  4. **跳过原因具名可见**：`already_scanned` / `no_tracked_symbols` 必须区分返回，
     否则「一直没扫」与「扫了但没数据」在日志上无法分辨（同族 [[KB-ENG-33]]）。
- **附带收益**：读路径**惰性结算**到期记录（与盘后批量结算构成双保险），单用户场景下
  与常驻定时器等价、且少一个常驻任务。
- **三态在接线层的落地**：`signals: []` = 引擎跑过、**确无信号**（真信息）；
  `degraded: [...]` 逐条列出输入缺失。二者都不得用 `None`/空串糊过去，
  **更不得用「无信号」吞掉「算不了」**。

### KB-ENG-45 数据质量门的「主键」必须与数据的**真实语义**同源，否则门会恒定误报
- **背景（2026-09-11，marketdb 补跑撞出）**：`sync_marketdb.py` 的 `adjust_factor.pk_unique`
  检查写成 `GROUP BY (thscode, ex_date_ms) HAVING COUNT(*) > 1`——**想当然地认为
  「代码 + 除权日」是主键**。实际上**同一除权日可以有多个合法事件**：A 股分红与送转
  可以在同一天生效，上游也可能把两笔独立权益分派分成两行。实测全库 3 组同日多事件里
  **2 组是合法**（`000812.SZ 1998-09-22` = 派现 0.2 + 送股 0.1；`603883.SH 2024-06-27`
  = 两笔不同派送），**只有 1 组是真重复**。
- **后果比"少报"更糟——是恒定的假警报**：每次同步都判 `error` 并落 `status:"fail"`。
  一个**每天都红**的质量门等于没有质量门：①告警疲劳，下次真故障淹没在噪声里；
  ②`sync_history` 的 `status` 字段失去信息量；③**盘后自动同步调度器一开启就在"报错"**，
  会让人误以为调度本身坏了。⇒ **假阳性与假阴性同罪，甚至更隐蔽**（假阴性让人以为没事，
  假阳性让人以为一直有事，两者都会摧毁信号的可用性）。
- **正解**：判据取**全字段自然键**（`GROUP BY` 六列全上）——同日**不同**事件放行、
  **完全相同**的行仍然报警。**同时**在入库侧根治（`INSERT … SELECT DISTINCT`）。
- **⚠️ 为什么必须两边都做，不能只改检查**：表是 `DROP TABLE` + 从 parquet 全量重建的
  ⇒ **只改检查 = 把真问题静默掉**；只去重不改检查 = 每次同步仍漏报其它同类形态。
  改完实测 `rows_in=57184 → events=57183`，**恰好剔除 1 条**（数字自证判据精准）。
- **顺带守住的一条**：重复行不是"多一行脏数据"那么轻——复权累计系数是**窗口乘积**，

### KB-ENG-46 被 `except` 吞掉的"守卫"是死代码：必须用测试钉住它**真的在跑**
- **背景（2026-09-11，同上补跑撞出）**：`_calendar_days_ms()` 负责给增量同步算滞后

     > （参见 [[KB-ENG-56]]：错误处方会被后来人一字不差地抄进测试）。

  2. **反漂移断言**：把源码读出来断言不再出现旧的错误调用形态
     （`assert "days = trading_days()" not in src`）+ 断言正确的新写法在

  3. **端到端可见性**：修完后真实跑一次同步，确认日志里**真的打印了**

  ⇒ 口径单点收口，见 [[KB-ENG-44]]），并在日历落后时用**工作日兜底**（宁可多报滞后）。
- **可迁移判据**：凡「守卫 / 校验 / 门槛」类代码，问一句

### KB-ENG-50 时间一律先转 epoch 再比大小——**不同格式/时区的字符串比较是静默错判**
- **背景（2026-09-11，用户实测）**：站内通知「一键已读后计数消失，但新来的一条却是在**之前的累积**上累加」。
- **根因**：同一个「已读水位」有**两个写入方、两种格式、两个时区**——
  `markAllRead()` 写 `new Date().toISOString()` → `2026-09-11T04:31:38.000Z`（UTC + `T` 分隔）；
  打开抽屉时写 `payload.generated_at` → `2026-09-11 11:00:00`（北京 naive + 空格分隔）；
  而条目 `ts` 恒为北京 naive。判定用**字面比较**：
  ```
  "2026-09-11 12:35:00" > "2026-09-11T04:31:38.000Z"   // false —— 第 11 位 ' '(0x20) < 'T'(0x54)
  ```
  ⇒ **当天所有条目恒被判为"已读"**（新条目再也不涨），而一旦水位换成另一格式或跨了日期，
  又**整天条目一起**计入未读 ⇒ 用户看到的就是"累积"。
- **纪律**：
  1. **跨源时间比较前必须先归一**（`Date.parse` / 自定义解析 → epoch 毫秒），严禁 `a > b` 比字符串；
  2. **同一语义只许一个写入格式**——两个写法必然漂移（本例还叠了时区：UTC 与北京差 8 小时，
     靠"格式恰好一致"来自洽纯属侥幸）；
  3. **北京 naive 字符串不能直接 `Date.parse`**（会按运行环境本地时区解释，CI/异地机器结果漂移）⇒
     显式 `Date.UTC(y, m-1, d, H-8, …)`（北京无夏令时，固定 -8 安全）；
  4. **无法解析返回 `null`，不返回 0**——0 会被当成"很久以前"，把未知静默升级成"未读/已读"；
  5. 迁移旧值时**顺带修正历史错值**：旧键（字符串）解析成 epoch 落新键、旧键删除。
- **可复现的验收**：把水位设成 `2026-09-11 12:30`（北京），徽标应显示**恰为水位之后的条数**
  （实测 12:36 那条 → 徽标 **1**），而**不是**全部条数（66）也**不是** 0。
  这条断言同时否证了两种历史故障模式，作为组件测试的固定回归位。
- **顺带的设计修正**：原实现"**打开抽屉即全部已读**"——与"未读条目要能看见红点"直接冲突
  （红点会一闪即逝）。改为**条目级已读**：未读带红点、点开即消失、`全部已读` 才推进水位。
  **红点类需求的隐含前提是"打开 ≠ 已读"**，做之前先确认这一条，否则做得再对也看不到。
- **状态存放**：`useState(读 localStorage)` 会 hydration 不一致，`useEffect` 里补读被
  `react-hooks/set-state-in-effect` 拦下（本项目 eslint 基线 0 warn）⇒ 用
  **`useSyncExternalStore`**（server snapshot 空态 + 模块级缓存保证快照引用稳定），
  顺带白拿多标签页同步。
- **关联**：[[KB-ENG-47]] [[KB-ENG-48]]

### KB-ENG-51 消 N+1 的「批量替换单查」有**三个等价前提**——漏任一即静默改变结果
- **背景（2026-09-11，P0-2）**：`/api/themes/catalog/strength` 在 `cache.get` **之前**先跑
  「1 次 catalog + 每题材 1 次 `get_members`」= 恒 **391 次查询**，默认全量 390 个题材下
  **缓存命中也要照付**（TTL 60s，命中率越高越亏）。改法：缓存判断前移 + 一次 `member_symbols_bulk`。
- **前提一：定序（最易漏，且不会报错）**。单查是 `WHERE theme_code=? ORDER BY symbol`；
  批量只写 `WHERE theme_code IN (...)` 则顺序是 **DB 扫描序（≈rowid 插入序）**。
  调用方有 `members[:200]` ⇒ 取到的是**另外 200 只**——数值全都"看起来很对"，集合却不同、且随插入顺序漂移。
  ⇒ 批量实现必须自带 `order_by`（本项目已补 `order_by(theme_code, symbol)`），**不是调用方排序了事**。
- **前提二：截断语义**。批量把「N 次小查询」换成「1 次全量查询」（实测 70510 行）——
  用**内存与单次耗时**换**查询数**，是否净赚必须实测（本例 541ms→142ms）。
- **前提三：缓存键不许依赖查库结果**。原 key = 排序后的「**有成分的**题材集合」⇒ **必须先查库才能算出 key**
  ⇒ 缓存判断被结构性推后，命中路径白付全部查询。**key 只能依赖请求参数**
  （可接受代价：成分刚同步时最多多返回一个 TTL 的旧值，与既有语义一致）。
- **验收（可复制）**：① 用 SQLAlchemy `before_cursor_execute` 事件计数**真实查询数**，不信"感觉快了"；
  ② 旧/新两口径做**逐元素含顺序**断言（`assert old_map[k] == new_map[k]`，390 题材 70510 条全等）；
  ③ 线上再打冷/热两次，比对响应体是否逐字节一致。
- **实测**：391 次/541ms → **2 次/142ms**；线上热路径 **2.7ms**、与冷结果 `IDENTICAL`。

- **② 测试不许依赖「表恰好还没建」这类副作用**——否则**通过与否取决于执行顺序**。
  实例：新用例把 `_sf` 设成真实可用 sessionmaker，只 patch `core_db.get_session_factory` ⇒
  **只拦到真实持仓那一路**，模拟持仓那路照常成功。单跑（表未建，两路都抛 `no such table`）出 2 条、
  全量跑（前序用例已 `create_all`）只出 1 条。
  ⇒ **「单跑绿、全量红」第一件事是查测试对共享状态的隐式依赖**，而不是怀疑被测代码；
  修法是让每条路径**显式注入失败**，与顺序无关（本项目还为顺序无关性补了混序复跑验证）。
- **③ pyflakes 不认 `# noqa: F401`**（那是 flake8 的语法）⇒ 为"导入即副作用"写的 noqa
  会被直接报 `imported but unused`，门禁红。改法：**顺手断言该名字**，既用掉名字也把
  「导入是刻意的」写进测试（如 `assert RealTrade.__tablename__ == "real_trade"`），
  比 `__all__` 或 `_ = X` 更有信息量。
- **关联**：[[KB-ENG-47]] [[KB-ENG-50]]

### KB-ENG-53 测试与前端环境的六条「静默失败」——都无报错、都只在特定条件下现形
- **① pytest 必须显式 `--basetemp`**：不带时默认目录 `/private/var/.../pytest-of-unknown` 被沙箱 shim 拒绝 ⇒ `PermissionError: EEXIST ... mkdir`，表现为**几十个 E 而不是 F**，极易误判成"刚才的改动把后端弄挂了"。纪律：**E 成簇出现在开头 → 先怀疑环境，不要先怀疑代码**；本项目统一 `pytest --basetemp=/tmp/pytest-basetemp`。
- **② SQLite 的 datetime 过滤必须传 datetime 对象**：库里存的是空格分隔格式（`2026-09-11 09:30:00`），与 ISO 字符串 `2026-09-11T00:00:00` 字面比较**恒 False** ⇒ 过滤条件形同不存在、防线静默失效（预算防线曾因此长期不生效）。统一走 `evolution._utc_cutoff_today()` 这类单点入口，不要各写各的字符串拼接。
- **③ 滚动加载哨兵必须挂在滚动容器内部**：放在容器外时它不随列表滚动，`getBoundingClientRect` 恒定落在视口内 ⇒ **首帧补载一页后再不触发、静默卡在第 2 页**（无报错、无告警，最难查的一类）。`<ul>` 内嵌入时需外包 `<li>` 保持嵌套合法。
- **④ 列表项 memo 化的两个前提缺一即全失效**：回调必须 `useCallback` 固定、数据必须 `useMemo` 稳引用（反例：heatmap 1540 格 hover 全量重渲染，根因就是引用每次都是新的）。
- **⑤ 复用既有抽象前先读它的依赖语义**（不读就复用的代价是静默漏刷新）：`usePollingFetch` 只在 `intervalMs` 变化时重跑 ⇒ **参数会变的取数必须传第三参 key**。
- **⑥ 扫「跨文件未引用导出」默认要排除测试文件** ⇒ 直接照单删会删掉只被测试引用的导出（如 `navUrlForAlias`）；**必须把测试纳入扫描再逐项 grep 复核**，并区分「真死代码」与「只是 export 暴露过宽（本文件内部在用）」。
- **判据**：这六条的共同形态是**「没有错误、没有告警、结果看起来正常」**（甚至"数量对不上"也被解释成"本来就该这么多"）⇒ 凡"改完没变化"或"数量对不上"，先按本表逐条排除环境与复用前提，再去怀疑被测代码。
- **关联**：[[KB-ENG-01]] [[KB-ENG-04]] [[KB-ENG-47]] [[KB-ENG-51]] [[KB-ENG-52]]

### KB-ENG-54 加了一层「守卫 / 上界」之后，真正的风险是**没覆盖到的那些路径**（S1-4 / S2-3）
- **形态**：保护逻辑只挂在**其中一条**执行路径上，其余路径静默绕过——守卫"看起来在跑"。
- **实例①（S1-4 涨跌停守卫，触红线 5）**：`place_order` 与 `match_pending` 是两条独立成交路径，历史上只有前者做了拦截 ⇒ 挂单在股价冲上涨停后**仍按现价成交**（等于在涨停板买入）。修法：判据抽成唯一函数（`limit_block_reason`），两条路径都调。**同族写法**：`if quote.limit_up_price and ...` 在限价 `None`/`0` 时整体短路——**缺值被当成"不需要校验"**；限价来自单源补价、曾真实被中断，所以"缺失"是**会发生的状态**而非异常路径 ⇒ 必须取保守侧（判不了就不放行）并配可见的拒单原因。
- **实例②（S2-3 请求预算）**：给 `_call_serial` / `_call_hedged` 加 `deadline` 参数时**顺手给了默认值 `None`**，4 处调用点漏改 1 处 ⇒ 那条路径整条绕过预算（实时对冲回落的串行段静默跑满 30s，**只有测试抓到**）。**修法不是补这一处，而是把参数改成必填**——让漏传在开发期 `TypeError`，而不是静默降级。
- **实例③（2026-09-11 事件循环阻塞）**：同一个 async 调度循环里**相邻两个 `if` 分支**各调一个同步重 IO 函数，只给其中一个包了 `asyncio.to_thread` ⇒ 另一个把事件循环卡住（连累 QuoteHub 的 1s 行情节奏）；同批另查出 `async def` 里直调同步函数（内部链到 `duckdb.connect` + 多路 SQLite 全表读）。**修法不是"记着下次包"**：新建 `tests/test_event_loop_no_block.py`，把调用点做成**一张表**（新增点只加一行，不再逐个写测试文件），断言分**正向**（`to_thread(<fn>)` 必须存在）+ **反向**（不得另有未包裹的 `<fn>(`，按行前缀判定以排除 `def` 定义行）——**只做正向时，在别处再抄一行裸调用依然全绿**；两道都注入幽灵值实测过（正向只抓"去掉 to_thread"，反向才抓"另加一处裸调用"）。⚠️ **反向还要防自己的实现漏洞**：首版用 `prefix.strip().startswith("def ")`，`strip()` 把 "def " 的尾空格也吃掉 ⇒ 所有函数定义行被误报为裸调用；改用**整行** `line.strip()` 判定。
- **纪律**：任何"加了保护"的改动，收尾必答三问——① `grep` 出**全部**调用点，确认都经过它；② 用测试钉住**最常走的那条**（不是只测新写的那条）；③ 保护被触发时必须有**可见出口**（拒单原因 / 结构化字段 / 哨兵 issue），否则等于没有。
- **判据**：「**判不了**」必须与「**不需要判**」在代码里分开表达——前者取保守侧并报出来，后者才放行。
- **关联**：[[KB-ENG-46]] [[KB-ENG-42]] [[KB-ENG-44]]

### KB-ENG-55 判据的**口径**比判据本身更要命：用了一个在分布里恒真的量，闸门形同虚设（S2-11）

- **形态**：判据名对、阈值对，**唯独口径取错** ⇒ 在真实分布下几乎恒真，什么也没拦住，且**无任何报错**。
- **实例（2026-09-11 `gate_verdict`）**：[[KB-DEC-019]] 写「中位 >0 且跑赢 ≥50%」，代码取的却是**原始收益**口径
  ——候选B 测试段原始中位 **+3.33%**、跑赢 **68.1%**（判 pass），**市场中性**口径实为 **−0.08% / 49.3%**（应为 observe）。
  **上涨市里原始胜率天然 >50%**，用它当判据等于没设门槛。同族既往：`PROMO_FLOOR=30%` 落在 241 日分布之外。
  两次同一个病：**判据没用它本该区分的基准来归一化**——收益类的基准恒为**同日市场均值**。
- **修法**：只接受 `excess_median` / `excess_win_rate`；拿不到就记 `unchecked` **跳过**，绝不换口径顶替（没验 ≠ 验过）。
- **连带**：登记册里「−0.08%/49.3%」与「+3.33%/68.1%」长期并存未标口径 ⇒ 重跑对不上。
  **只写数字不写口径 = 重跑必然对不上**（已订正，见 `docs/strategy-registry.md §3`）。
- **纪律三问**：① 归一化到什么基准？② 在历史分布里是否恒真（扫一遍分布，别只看当前值）？
  ③ 拿不到所需口径怎么办（显式跳过 + 报出）？
- **判据**：一条**从未被触发过**的判据，先怀疑它恒真，再怀疑数据太干净。

### KB-ENG-56 断言若由**真实运行日**驱动，就只在特定日历日变红——「一周 5/7 是绿的」等于没写守卫

- **背景（2026-09-12 00:15 全量 2 failed，根因同源）**：①`assert out[-1] >= 今天`（实测 09-11 vs 09-12）；
  ②`assert real_days[-1] >= 今天`。**当天是周六**——交易日历只装交易日，末元素必为周五
  ⇒ 两条断言在**每个周末与每个长假**都挂，一周里 5 天是绿的。
- **归属判定**：**产品口径正确，断言写宽**。`_calendar_days_ms` 与 `marketdb_freshness.trading_day_lag`
  同源约定「非交易日不追加、周内工作日兜底、宁可多报滞后」；调度器拒绝在周六生成议程**也是对的**。
- **两类错误前提（可迁移）**：
  - **①把"日历覆盖交易日"写成"日历覆盖今天"**：日历的语义是交易日集合，"覆盖"只能按**交易日**判。
  - **②把"运行日"当成"测试夹具"**：`test_scheduler_*` 的主题是「时钟跨过 15:45 是否触发」，
    与"今天是否交易日"**正交**；用真实今天当时钟起点，就把两件正交的事绑死了。
- **修法（均不碰产品逻辑）**：
  1. **基准日做成可注入参数**：`_calendar_days_ms(limit=400, *, today=None)`，`None` 才取 `now()`。
     **范式照抄既有的 `trading_day_lag(latest, asof)` / `freshness(asof=)`，别另发明**。
     附带修掉跨零点竞态：此前**测试与实现各取一次 `now()`**，跨零点会落在不同日期。
  2. **夹具锚到「日历里真实存在的交易日」**：`probe_day = real_days[-1]`，并断言
     `last_trade_date(real_days, asof=probe_day) == probe_day`（把选它的理由写进断言）⇒ 与运行日解耦且不丢真实口径。
- **必配定点回归**（否则修完仍是"只有周末才有效"）：周六→周五；**周日→同样周五**；
  **工作日节假日（如 2026-10-01 周四）会被刻意补上**（该取舍若改，必须连 `freshness` 一起改，不能只改一处）；
  **补负向用例**——原有覆盖只测"交易日必须触发"，**"非交易日必须不触发"无人守**，本次暴露的恰是这一侧。
- **注入验证（四道，全实测变红）**：①去掉 `weekday()<5` → 4 红；②去掉 `today` 注入缝 → 1 红
  （**证明注入缝承重，不是装饰**）；③删 `_LAST_SHADOW_DATE` 定义复现 09-09 根因 → 调度测试红
  （**证明它仍抓得住原事故**）；④去掉调度器交易日守卫改恒真 → 新增负向用例红。
- **可迁移判据**：写完一条断言先问**「它在哪些日期/时区/环境下会变红？」**——若答案是"只有周末"或
  "只有某个时刻"，它**大部分时间在制造"绿"的假象**，必须把驱动量显式注入并补定点用例。
  同族：[[KB-ENG-55]]（判据恒真）、[[KB-ENG-47]]（门禁工具假阴性）。
- **反哺**：[[KB-ENG-46]] 第 1 条防线的处方「断言末元素等于今天」**本身就是缺陷来源**，已就地订正
  ——**错误处方会被后来人一字不差地抄进测试**，KB 与代码一样要接受订正。
- **关联**：[[KB-ENG-46]] [[KB-ENG-55]] [[KB-ENG-47]] [[KB-ENG-44]]
