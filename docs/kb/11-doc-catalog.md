## 1 「一份好文档」的定义（七条判据）

用户 2026-09-13 的定义：*「它不只是文档，而是开发、研发、研究、遵守规则、错题本、知识翻阅、
迭代总结与知识库的核心与关键。」* 落到可判的判据上，**七条缺一不可**：

| # | 判据 | 不满足时的症状 | 怎么判（可机检的尽量机检） |
|---|---|---|---|
| 1 | **可定位** | 找不到 ⇒ 等于不存在 | 有编号 + 分类 + 领域，且在编目表里能查到 |
| 2 | **单一真相源** | 两份都"像真的"，读者不知信谁 | 同一事实只写一处，其余**指针**；发现第二份即登记待合并（KB-ENG-26） |
| 3 | **状态显式** | 把示例当规范、把设想当已实现 | ✅ 已落地 / 🔶 试验中 / ⏳ 待落地 / ❌ 被取代 / **📎 示例**（KB-DEC-019） |
| 4 | **主张带失效条件** | 被当"规律"无限引用 | 主张类条目必须有「什么条件下不再成立」（`doc-health` **H 项**已机检） |
| 5 | **结论可验证** | 数字/结论无法复核 | 带**实测数字 + 命令 + 出处**；引用外部材料标 `📎` 且注明"零实测" |
| 6 | **待办有出口** | 写进文档就等于做完 | 有价值的未做项须经方案准入，进入 `retro-and-gaps.md` §6.0 索引的所属阶段（KB-DEC-020） |
| 7 | **可维护** | 文档只加不改，逐渐变成伪证 | 有明确**维护触发**：何时更新 / 何时归档 / 何时删（见 §4 生命周期） |

> **反例即错题本**：本仓 §七 已累计 **34 处「文档 × 实际状态」偏差**（16 处低估完成度、
> 9 处高估、1 处需求口径不成立…）。这七条判据正是从那 34 处反推出来的——**每一条都对应一类
> 真实踩过的坑**，不是抽象原则。

## 2 卡帕西三层模型 ↔ 本仓映射

卡帕西 LLM-Wiki 模式的核心主张：**不是 RAG**——知识**编译一次、保持最新**，
交叉引用与矛盾都已就位，而不是每次查询重新从原始材料推导。

| 层 | 卡帕西 | 本仓 | 谁写 | 可变性 |
|---|---|---|---|---|
| **L1 原始源** | `sources/` | `artifacts/logs/`（逐轮日志）· `artifacts/reports/`（审查/复盘报告）· `artifacts/research/`（调研快照）· `docs/archive/` · `docs/daily-review/` · `docs/evolution/` | 过程自然产生 | 保留期内不原位改写；到期可整件退休 |
| **L2 编译层** | `wiki/` | `docs/kb/`（KB 条目，ID 引用制）· `docs/summary/`（主题汇总）· `CONTEXT.md`（领域词汇表） | agent 全权维护 | **保持最新**，可重写 |
| **L3 约定层** | `SKILL.md` | `docs/kb/07-doc-curation.md`（流程）· **本文件**（判据）· `AGENTS.md`（作业手册）· `scripts/doc-health.py`（机检） | 与用户共同演化 | 低频、显式改版 |

⚠️ **与本仓的一处诚实差异**：卡帕西的 L2 是「从 L1 编译出来」；本仓的 L2 是「从**实践**里提炼」，
L1 是**过程记录**（不是 L2 的素材来源）。目标一致（不重复推导），路径不同——不要照搬"从 sources 重建 wiki"。

**入口分工（避免"文档迷宫"）**——**会话第一读永远是 `AGENTS.md` 的短入口块**：

| 想查什么 | 去 |
|---|---|
| **会话从哪开始**（总入口） | **`AGENTS.md` 的短入口块**（纯指针，不存内容） |
| **我要做 X，按什么顺序读哪些** | **`docs/INDEX.md` §0 主题路由**（按主题列「先读→再读→红线」；含**任务动线** / **症状反查** / **已拍板清单**） |
| **知识 / 规则 / 教训**（某条是什么） | `docs/kb/00-INDEX.md`（唯一登记处） |
| **某主题的收敛结论** | `docs/summary/` |
| **还有什么事没做** | `docs/retro-and-gaps.md` §6.0 → 所属阶段任务（唯一状态） |
| **某份文档是什么 / 在哪** | `docs/INDEX.md`（编目表） |
| **某个词在本项目什么意思** | `CONTEXT.md`（领域词汇表，唯一权威） |

> **三者不得互相承载内容**：`AGENTS` 短入口管「从哪开始」· `INDEX` 管「有什么 ＋ 怎么走」·
> `kb/00` 管「写了什么」。读写协议见 `kb/07` §4.4；索引自身的体积与指针由 `doc-health` **N 项**兜底。
> ⚠️ **「主题路由」不单独成册**——它与 `INDEX.md` §0 回答的是同一个问题（「我要查 X → 去 Y」），
> 2026-09-14 已**否决并合并**（初版 `kb/12-topic-router.md` 随即撤销，教训见 `kb/07` §4.1）。

## 3 KB「收敛」标准（定义 + 四动作 + 三底线）

### 3.1 「收敛」的定义

> **收敛 = 在不损失知识的前提下，减少「需要人读的条数」。**

注意三件**不是**收敛的事：**删条目**（本仓纪律：永不删，被取代改 ❌ 并写明取代者）、
**删判据**、**删证据链**。收敛的产物是**更少的条目 + 更强的判据**，不是更少的文件。

**为什么必须收敛**：条目只增不减时，**信噪比**会持续下降——`00-INDEX` 从"可通读"变成"只能 grep"，
新人（含未来的自己）不再读它，于是**沉淀失效**。这与「一上线就红满天的门禁会被整体无视」
（KB-ENG-58）是**同一种失效机制**：**过载 = 被忽略**。

### 3.2 四类收敛动作（按"动到什么程度"排序）

| 动作 | 何时用 | 怎么做 | 保留什么 |
|---|---|---|---|
| **合并 merge** | 同主题 + **同判据**的 ≥2 条 | 写一条更完整的，原 ID 改为 `❌ 已被 KB-X-NN 合并` | 原 ID 可检索 + 全部判据/阈值 |
| **蒸馏 distill** | 多条**同源**教训 → 一条**更高阶**判据 | 提一条上位判据，原条目降为其"实例" | 原 ID 指针 + 证据链 |
| **降层 demote** | 不再有复用价值（零外部引用 ≥2 季度，`doc-health` **G 项**） | 移出 KB 到 `docs/archive/`，或标 ❌ | 条目本体（挪位不删） |
| **拆册 split** | 单册超阈值且**主题可分离**（`kb/07` §5.2 条件①） | 按"缺陷发生在哪一层"拆 | 全序列唯一登记处（`00-INDEX`）不变 |

### 3.3 三条底线（**违反即不是收敛，是丢失**）

1. **可检索性不降**：合并/蒸馏后，**原 ID 必须仍能命中**（留 `❌ 已被 X 取代` 或别名索引）。
   *判据*：拿旧 ID 去 `00-INDEX` 搜，必须能跳到新条目。
2. **判据不丢**：只删**叙述**，不删**判据 / 阈值 / 失效条件 / 边界**。
   *判据*：收敛前后逐条比对「阈值数字」与「失效条件」集合，必须**超集**（新 ⊇ 旧）。
3. **证据链不断**：指向 commit / 文件 / 实测的指针必须保留。
   *判据*：收敛后每个条目至少保留一条可复核的证据指针。

### 3.4 触发条件（何时该动手，不靠"感觉条目多"）

| 触发 | 动作 |
|---|---|
| 单册 > 500 行（框架）/ > 800 行（KB 文件） | 评估**拆册** |
| 同一主题 ≥ 3 条，且判据高度重叠 | 评估**合并** |
| 某条连续 **2 个季度零外部引用**（G 项孤儿） | 评估**降层** |
| **新增条目时发现与既有条目同判据** | **就地合并**，不新增（最常见、最该拦住的一类） |
| `00-INDEX` 某册条目数 > 30 且通读成本 > 15 分钟 | 评估**按子类拆册**或**蒸馏** |

## 4 非 `docs/` 面的治理（用户 2026-09-13 要求：**除 docs 外也要遵循**）

`kb/07` 的规则此前只覆盖 `docs/`。实际文档面还有四处，**此前无治理**：

| 位置 | 内容 | 归属层 | 处置 |
|---|---|---|---|
| **根目录** | `AGENTS.md`（作业手册）· `README.md`（对外）· `CONTEXT.md`（领域词汇表） | L3 / L2 / **L2** | `CONTEXT.md` 是**术语唯一权威**，纳入编目；三者均受 `doc-health` B/B2/F 扫描 |
| `artifacts/logs/` | 新逐日日志（原始证据） | **L1** | append-only；旧日志按 `GOV-018` 清单提炼/归档；入口固定在 AGENTS 短块 |
| `artifacts/reports/` | 本地审查/性能报告 | **L1** | 时点快照，结论提炼进 L2 后归档，禁止充当最新状态 |
| `artifacts/` | 调研快照、恢复副本与补丁 | **L1** | 忽略且保留恢复元信息；旧资产逐项映射，不整包改名 |
| `skills/`（项目内） | 已提炼并入库的项目技能 | L3 能力 | 技能自述即入口；旧平台资产按迁移清单审阅，未审内容不入库 |

**统一原则**（与 `docs/` 一致）：**L1 在有效保留期内不原位改写，L2 保持最新、L3 显式改版**；L1 并不等于永久占用磁盘，满足生命周期退出条件后可整件退休并从 Git/PR/紧凑证据恢复。
**物理分类规则（2026-09-20）**：`docs/` 根只保留 6 个跨域控制面；系统/数据/产品/策略/AI/复盘/研究正文分别进入 `system/`、`data/`、`product/`、`strategy/`、`ai/`、`review/`、`research/`。`archive/` 只能承载只读历史，不得重新充当当前权威。具体白名单与 O2 门禁见 `docs/INDEX.md` §0.0.1 和 `scripts/doc-health.py`。
**唯一例外**：仍在保留期内的 L1 逐日日志是 **append-only**（改历史 = 伪造记录），
故其内部引用指向"当时存在的文件"属**正确语义**——`doc-health` 的 B/F 项对它们**默认跳过**即为此。

### 4.1 产物落点纪律（**第一规则**，2026-09-13 用户确立）

> 用户原话要点：*产物一律进项目目录，**不散落 `~/`***。

| 判据 | 内容 |
|---|---|
| **禁令** | agent 生成的项目产物（报告 / 快照 / 脚本 / 草稿 / 图表）**不得散落到 `~/Desktop`、`~/Downloads` 或任何应用私有目录**；必须进入项目中性目录 |
| **唯一落点** | 技能进 `skills/`、复用工具进 `scripts/`、稳定知识进 `docs/`；原始报告/日志/补丁/恢复副本进忽略的 `artifacts/` |
| **自检** | 写完 `ls` 确认落点正确（**不靠记忆，靠观察**） |
| **删除** | tracked/独有资产走 `artifacts/trash/`（`scripts/safe-trash.sh`）；GOV-026 批准白名单中的项目自有、可再生临时/缓存项在核无活动进程/脏工作树/唯一证据后可直接清理以真正释放空间——完整护栏见 `kb/07` §6.2 |

**两处例外**（显式、穷举，不得类推）：
1. **既有独立运行环境**：按已审核的项目技能说明运行；外部工具资产不默认搬运、复制或成为项目依赖；
2. **用户级跨项目文件/插件/偏好**：它们属于用户环境，不属于本仓，也不得为方便而复制成项目内应用目录。

⚠️ **为什么这条要写在 L3 而不是逐日日志里**：它是**跨切面纪律**（每次产出都适用），
而逐日日志是 L1 append-only、按日期消费，**换一天就翻不到**。纪律类内容进 L3，证据类内容进 L1——
这正是 §5「生命周期」表里"新建先答三问"的判据来源。

## 5 维护触发与生命周期（判据 7 的落地）

| 阶段 | 触发 | 动作 |
|---|---|---|
| **新建** | 要写一份新文档前 | **先答三问**：能否并入既有文档？能否写成 KB 条目？能否只进逐日日志？（`kb/07` §3.1 归属三问） |
| **保持** | 每次功能点收尾 | 跑 `python3 scripts/doc-health.py`；改了代码就同步改引用它的文档 |
| **更新** | 文档里的数字/状态被改动追过 | **当轮**回填（数字类改**指针式**，KB-ENG-36） |
| **收敛** | 命中 §3.4 任一触发 | 按 §3.2 四动作之一处理 |
| **归档** | 时点性文档（结论已进 L2，但仍有追溯/恢复价值） | 移入 `docs/archive/` 或忽略 artifacts；标明保留理由/退出条件，不把归档当永久存储 |
| **删除** | 已完成方案原件或过期 L1（精华/待办已提炼、活引用清零、无活动依赖、可恢复） | tracked/独有内容走 `scripts/safe-trash.sh`；同步索引写“已删除 + 精华去向/恢复入口” |
| **卫生收尾** | 每轮任务结束 | 按 GOV-026 将本项目资产分成 EPHEMERAL / REGENERABLE_CACHE / COMPACT_EVIDENCE / RECOVERY / LIVE_OR_EXTERNAL；前两类满足白名单条件即清，后两类按退出条件收口，最后一类默认不自动删 |
