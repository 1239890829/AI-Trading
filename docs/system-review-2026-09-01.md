# 系统功能与性能评审报告（2026-09-01）

> 评审方式：全量代码排查（前端 5 页面 + 详情终端 8 页签 + 96 REST 端点 + 后端调度链），
> 逐项实测轮询频率与请求链路，不凭印象。结论按「应删除 / 应合并 / 需补充 / 需优化」四类分条，
> 每条含涉及模块、问题说明、建议方案、优先级。技术栈：FastAPI(SQLite/Parquet) + Next.js 16/React 19 + WS。
> 本报告只评审不动代码；确认后按优先级逐条落地。

## 一、应删除

### D1. 盘面页「板块排行」tab（用户点名 #1）
- **涉及模块**：`/tape?tab=boards`（`components/tape/boards-tab.tsx`）；重复方：工作台详情右列「板块」页签（`components/detail/board-rank-panel.tsx`）
- **问题说明**：板块数据只有一条链路（新浪闪电排行 → `GET /api/boards`），工作台详情右列已有「板块」页签（60s 轮询、行业/概念同源）；盘面页再放一个 tab 属同一数据两个入口。板块排行是"行业横截面"，与盘面页"题材梯队/涨停生态"的短线生态定位也不契合。
- **建议方案**：删除盘面页 boards tab（连 `boards-tab.tsx` 一起删），盘面页收敛为三 tab（题材梯队/涨停生态/龙虎榜）；`next.config.ts` 的 `/boards → /tape?tab=boards` 重定向改为 `/workbench`。数据能力不受损（工作台详情仍可看）。
- **优先级**：高

### D2. screener 冻结残留（页面 + 4 端点 + service）
- **涉及模块**：`app/screener/page.tsx`、`/api/screener*`（4 端点）、`screener_service.py` + `tech_score.py`
- **问题说明**：2026-08-31 已拍板"冻结"（导航移除、代码保留），但页面与端点仍在运行：`/screener` 直链仍可访问，每次启动仍加载 service。与每日精选定位冲突的问题没有真正消除，只是藏起来了。
- **建议方案**：删除前端页面与 4 个 REST 端点（git 历史可随时找回）；`tech_score.py` 被每日精选技术维复用，**保留**。若你希望保守，可维持现状（冻结不删），但需接受"半成品可被直链访问"。
- **优先级**：低（已冻结，无活跃危害；删除是一劳永逸的收尾）

### D3. 逐笔成交（trades）轮询常驻 + 页签降级保留
- **涉及模块**：详情右列「逐笔」页签（`stock-detail.tsx` trades 10s 轮询）
- **问题说明**：逐笔数据只有腾讯单源（东财 WAF），且对"每日精选"的持仓周期（平均持有 2.46 天）几乎无决策价值——它是做 T 工具，而已删除的分钟信号端点同因被判"与持仓周期不匹配"。
- **建议方案**：轮询仅在页签激活时开启（见 O2）；页签本身保留（数据已有，删除收益小），但不再默认常驻拉取。
- **优先级**：中（轮询部分与 O2 合并执行）

## 二、应合并

### M1. 「全部」归位自选股面板内部（用户点名 #3）
- **涉及模块**：工作台左栏（`app/workbench/page.tsx` 243-289 行）
- **问题说明**：分组 chips（全部/持仓/自定义组）当前渲染在自选股 Panel **外部的独立一行**，视觉上像页面级筛选而非自选股的内部结构；「全部」是默认视图却没有"默认分组"的身份。
- **建议方案**：chips 行移入自选股 Panel 内部（Panel 头部 `extra` 区或面板内首行 sticky）；「全部」保持默认选中，语义改为"自选股的默认分组视图"；「持仓」chip 保留独立（它不是自选分组，是真实持仓视图，建议在视觉上与自选分组用分隔线区隔）。
- **优先级**：高（用户点名，纯 UI 移动，半小时工作量）

### M2. 市场页「涨停速览」与盘面涨停生态双入口
- **涉及模块**：市场页总览「涨停速览（今日连板前列）」Panel vs 盘面页「涨停生态」tab
- **问题说明**：同一份涨停池数据（`/api/limit-up`）两个页面各渲染一份；市场页是 top10 截断，盘面是全量+日期查询。
- **建议方案**：市场页保留速览但降级为"摘要 + 入口"——行数减到 5，Panel 标题带「完整涨停池 ↗」链接跳 `/tape?tab=limitup`，行点击同样跳转（当前行不可点）。不删：总览页需要"今天市场在炒什么"的一眼答案。
- **优先级**：低

### M3. 两处真实持仓订阅逻辑重复
- **涉及模块**：`app/workbench/page.tsx`（15s 轮询 realPositions）与 `components/detail/real-position-panel.tsx`（15s 轮询 + real-changed 事件）
- **问题说明**：同一条数据链（`/api/real/positions`）两处各自轮询、各自监听 `real-changed` 事件，刷新节奏不一致会造成左栏持仓分类与详情持仓 tab 短暂不同步。
- **建议方案**：抽 `useRealPositions()` hook（15s 轮询 + real-changed 监听去重），两处共用；顺手把工作台 realSymbols 与持仓面板的符号列表统一为单一来源。
- **优先级**：中

## 三、需补充

### A1. 分组管理：新建 / 重命名 / 删除（用户点名 #2）
- **涉及模块**：自选股模块（前端 `app/workbench/page.tsx` 管理模式；后端 `app/api/routes/` watchlist 路由）
- **问题说明**：分组当前只能给单只股票"改派"到已有分组（管理模式下拉），**没有**新建分组、重命名分组、删除分组的入口；分组列表完全由成员的 `group_name` 派生——空分组会直接消失，"先建组再放股"的操作路径不存在。
- **建议方案**：
  1. 后端补三个端点：`POST /api/watchlist/groups`（新建）、`PUT /api/watchlist/groups/{name}`（重命名，级联更新该组成员的 group_name）、`DELETE /api/watchlist/groups/{name}`（删除，成员回落「默认」）。因组列表是派生的，需新增一张 `watchlist_group` 表持久化空组（alembic 迁移一份）。
  2. 前端管理模式下，chips 行尾部加「＋ 新建分组」；对自定义组（非"全部/持仓/默认"）提供重命名/删除按钮（删除带 confirm）。下拉选项与 chips 同源。
- **优先级**：高（用户点名；后端 + 迁移 + 前端约一次迭代）

### A2. 复盘完整报告没有查看入口
- **涉及模块**：后端 `app/review/`（6 个 REST 端点已就绪：报告列表/详情/检索对比） vs 前端只有每日精选页的"复盘归因"片段
- **问题说明**：复盘 Agent 每日 15:30 自动产报告并落库，但前端没有任何页面展示完整报告（阶段判定依据、逐只归因全表、元结论自迭代记录）。产出没有消费口，等于白做。
- **建议方案**：研究页（`/research`）新增第三个 tab「复盘」：报告日期列表 + 当日报告全文（阶段/温度/依据链）+ 与前日对比。不新增一级导航，符合减负原则。
- **优先级**：中

### A3. 预警真实推送通道
- **涉及模块**：`app/market/alert_engine.py`（in_app/log 已有）+ 研究页预警 tab
- **问题说明**：预警触发只写库与页面红点，人不在页面前就收不到。价值在"触发时通知"，当前只有"打开页面看"。
- **建议方案**：等你选定通道（企微/飞书/Telegram/email/webhook 均已抽象可插）后接入一个；评审建议企微群机器人（成本最低，一条 webhook 即可）。
- **优先级**：中（阻塞于你的通道选择，非技术）

### A4. 自选分组维度的批量操作
- **涉及模块**：自选股面板
- **问题说明**：分组建起来后缺少"按组操作"的能力：整组隐藏/显示（现在要逐个点 chip）、导出某组清单。
- **建议方案**：与 A1 合并做——管理模式下按组批量移除；导出 CSV 放研究页或右键菜单（低频）。
- **优先级**：低

### A5. 移动端/窄屏可用性
- **涉及模块**：全站（workbench 左列 340px、盘面表格 min-w-[560px]、详情右列 300px）
- **问题说明**：桌面优先设计，`lg:` 断点以下详情会堆到自选下方，表格横向滚动——能用但体验粗糙。若你只在桌面用可忽略。
- **建议方案**：暂不动（等真实使用场景出现再做针对性适配）；记录在案。
- **优先级**：低

## 四、需优化（性能与卡顿）

### O1. 切股卡顿主因：详情面板全量重挂载 + 8 请求并发【收益最大】
- **涉及模块**：`app/workbench/page.tsx`（`<StockDetailPanel key={activeSymbol}>`）+ `components/stock-detail.tsx`（切股 `Promise.all` 8 个请求：K线120根/盘口/逐笔/分时+量比基线/资金流/财务/公司资料/新闻摘要）
- **问题说明**：现在切股是**双重全量重建**——key 变化导致整面板卸载重挂（所有子组件 state 归零、图表销毁重建），面板内 `useEffect[symbol]` 又把 8 个请求一次性并发拉齐。用户点一只新股 → 图表白屏等待最慢的那个请求（财务/新闻走东财，慢时 2-4s），期间 K 线区显示空。这是"系统操作卡顿"的第一主因。
- **建议方案**（两步）：
  1. **首屏分级**：切股先只拉 K线 + 分时 + 实时 quote（首屏可见三件套），盘口/逐笔/财务/资料/新闻改为**延迟拉取**（`requestIdleCallback` 或各 tab 首次激活时拉）。`skipStockOnly` 的指数分支已证明"按需跳过"模式可行。
  2. **去重重挂**：key 重挂载与 `useEffect[symbol]` 清空二选一即可——建议保留 key（防行情残留语义清晰），内部 effect 里的全量清空简化为首屏三项。
- **优先级**：高

### O2. 轮询风暴：6 个定时器不管页面在不在看都在跑
- **涉及模块**：`stock-detail.tsx`（盘口 5s / 逐笔 10s / 竞价 30s / 模拟账户 10s 常驻）+ `workbench`（loadBase 10s 内含 riskState、paperPositions）+ `market`（10s 内含 breadth/sentiment/sentHist）
- **问题说明**：实测盘点（页面挂载期间常驻请求）：workbench 每 10s 发 4 个请求；详情面板每 5s 盘口 + 每 10s 逐笔 + 每 10s paper + 每 30s 竞价——其中竞价只有 9:15-9:30 有数据意义，模拟账户只有交易 tab 在用时才需要。后端压力叠加：QuoteHub 5s（ths 批量）+ AlertEngine 5s + 新浪全市场 56 页/60s。
- **建议方案**：
  1. 盘口/逐笔轮询绑定 `rightTab` 激活（条件 useEffect）；
  2. 竞价改为"交易时段 9:15-9:31 内 10s，其余时间不拉"；
  3. paper 轮询 10s→30s（已有 `paper-changed` 全局事件即时刷新兜底）；
  4. market 页 sentiment/breadth/sentHist 降 30s/60s（日频属性），仅指数卡保留 10s；workbench 的 riskState 同理降 30s。
  预计常态请求量降 ~60%，后端上游（腾讯/东财）配额压力同步下降。
- **优先级**：高

### O3. 行情 WS 全量重连与无差别重渲染
- **涉及模块**：`hooks/use-quote-stream.ts` + `app/workbench/page.tsx`（左栏列表）
- **问题说明**：① 自选集合每次变化（加/删自选、持仓变动）→ `key` 变化 → WS **整体断开重连**（重连期行情空窗，降级 3 次失败还会进 5s 轮询）；② 每条 WS 推送 `setQuotes` 全量替换 → 左栏所有行 + 详情面板整体重渲染，`Sparkline`/`PriceFlash` 无 memo，自选 30 只时每 5s 一轮全列表 reconcile。
- **建议方案**：① 后端 `/ws/quotes` 支持 `action:"subscribe"` 动态增删订阅（现在只读 URL 参数），前端 symbols 变化时发消息而非重连；② 左栏行组件 `React.memo`（quote 按引用比较），Sparkline 数据 5 分钟才变一次、天然适合 memo；③ `setQuotes` 增量 merge（仅更新变化的 symbol key）。
- **优先级**：中

### O4. 云图 5546 个 SVG 节点全量渲染
- **涉及模块**：`components/market/heatmap-tab.tsx`
- **问题说明**：全市场模式渲染 ~5546 个 `<rect>` + 文本，30s 轮询到新数据后 squarify 全量重算 + React 全量 diff；hover 一只股票 setState 在顶层 → 整棵 SVG 重渲染。低端机上拖动/缩放窗口可感卡顿。
- **建议方案**：改为 Canvas 绘制（一次 draw，hover 用坐标命中检测查 stock 列表），或折中：SVG 保留但组内只画 Top12（现已有"组内 Top12、其余聚合"口径——确认全市场聚合节点是单个 rect，若已是则节点数其实 ~40 组 × 12 ≈ 500，问题减轻，先实测再决定是否上 Canvas）。
- **优先级**：中（先实测帧率，若聚合口径已生效则降为低）

### O5. 题材梯队页三请求串行感知
- **涉及模块**：`components/tape/themes-tab.tsx`（themes 60s 后端缓存 + hot + strength 三请求）
- **问题说明**：三请求并行但卡片要等 `getThemes`（后端需聚合涨停池，实测 1-3s）才有内容，hot/strength 后到各自补渲染，首屏有两次跳变；60 张卡片上限在极端日全部渲染。
- **建议方案**：hot/strength 等主数据到齐后再渲染（消除跳变）；卡片超过 30 张时默认折叠尾部（「展开其余 N 张」）。小改进。
- **优先级**：低

### O6. 后端：休市时段全市场快照照跑
- **涉及模块**：`app/services/snapshot_service.py`（新浪 56 页/60s 轮询 + 300s 落库）
- **问题说明**：QuoteHub 有休市 stale 机制，但快照服务未确认是否跳过休市时段——若照跑，每 60s 白打 56 页新浪请求（日志显示 00:43 仍在跑 56 页分页）。既是流量浪费也有被新浪限流风险（东财 WAF 前车之鉴）。
- **建议方案**：快照轮询循环加交易日历判断，休市时段跳过（保留 15:05 收盘后一轮兜底落库）；同规则应用于 speed_sampler。
- **优先级**：中

### O7. `tsconfig.tsbuildinfo` 与门禁脚本
- **涉及模块**：`apps/web/package.json` scripts
- **问题说明**：`npx tsc --noEmit` 会改写被 git 跟踪的 `tsconfig.tsbuildinfo`，每次提交前都要手工还原（已两次差点带进 commit）。
- **建议方案**：`tsconfig.tsbuildinfo` 加入 `.gitignore` 并 `git rm --cached`；或 scripts 里加 `incremental: false`。
- **优先级**：低（一劳永逸的工程卫生）
