### 5.9 阶段门、优先级与跨阶段治理

> **唯一目的**：防止“看到一个高优先级任务就跳过去做”，导致后续结论缺少前期事实、契约或样本支撑。W00–W09 继续回答“任务归谁管”；**G0–G5 回答“最早什么时候能做”**；P0/P1/P2 只回答同一可执行范围内的重要性。三者不得混用。

#### 5.9.1 有序阶段门

| 门 | 含义 | 允许的典型产物 | 默认不得越过 |
|---|---|---|---|
| **G0 事实与安全底座** | 时间/身份/分母/未来数据/证券规则/权限等真实性 | 失败反例、点时修复、样本身份、硬安全 | 未解决的可行动“阻断”任务 |
| **G1 核心事实契约** | 数据、通知、执行、事件、候选的可追溯对象与来源契约 | outbox、snapshot、source lineage、真实UI事实 | G0 阻断项 |
| **G2 产品闭环接线** | 已可信对象进入用户路径、通知、模拟、猎场与前后台分层 | 消费链、状态/失败语义、用户动作 | G0/G1 阻断项及本任务硬依赖 |
| **G3 研究验证与准入** | 标签、全分母、walk-forward/消融、gold、策略/因子研究 | OOS/前向证据、负结果、晋级/否决 | 相关 G0–G2 真实性/消费契约 |
| **G4 智能体、性能与结构优化** | AI/Agent、性能、隔离、去重、迁移与维护优化 | challenger、性能证据、简化/迁移 | 被优化对象尚未证明正确/稳定 |
| **G5 验收与发布** | 工程、运行、研究、用户价值与恢复的最终核验 | 准确候选 SHA、CI、运行/效果结论 | 对应切片前置门未闭环 |
| **GX 持续治理** | 文档、Jev治理、创新雷达、CI成本等控制面 | 规则/审计/监测 | 不构成绕过 G0–G5 的通行证 |

#### 5.9.2 每个任务必须有的调度字段

阶段任务除原状态/优先级/依赖外，必须维护：

- **阶段门**：G0–G5 或 GX；表示该任务最早可进入的执行门。
- **门内序**：同一门内的稳定顺位，使用 10/20/30… 留插入空间；不是历史工时排名。
- **门禁角色**：`阻断 / 非阻断 / 持续治理 / 验收`。
- **依赖**：只允许写**硬开工依赖**；依赖未完成就不能开工。长期治理任务不得伪装成永远完成不了的硬依赖。
- **效果前置**：允许任务先做采样/工程，但在这些 ID 完成前不得宣称效果、晋级生产或改变生产权重。

新增任务必须先完成“领域归属 W → 阶段门 G → 门禁角色 → 硬依赖/效果前置 → P0/P1/P2 → 门内序”，再进入账本；不能先开工后补治理字段。

#### 5.9.3 动态选刀算法

1. 排除 `已完成 / 已退出 / 已合并`；`待条件` 的条件未满足时不算可行动任务。
2. 找到**最低的 G0–G4，且仍有可行动 `阻断` 任务**；该门就是当前主门。只要任一 G0–G4 仍有可行动阻断项，就不以更低门的非阻断项绕开它。**若 G0–G4 已没有任何可行动阻断项，则回落到最低仍有可行动 `非阻断` 任务的 G0–G4 作为当前主门；只有普通门连非阻断项也为空时，普通主门才允许为 `None`。**
3. 当前门内先 `阻断` 后 `非阻断`；同角色按 **P0 → P1 → P2 → 门内序升序**。选择器返回该门全部可行动候选并按本序排序，首项为唯一首选；G5/GX 不参与普通主门 fallback。
4. 已 `进行中` 的同一切片优先收口；`部分完成` 不自动压过更高优先的真实阻断项，仍按上述比较。
5. GX 只能作为一个不冲突的伴随治理切片；不能让“文档/雷达/CI优化”绕过业务前置。
6. G5 只针对已经完成实现/研究的准确候选执行，不作为普通功能开发的提前入口。
7. 每轮最多**一个主切片 + 一个低风险 GX 伴随切片**；完成/阻塞/证据变化后重新从最新 `master` 计算。

#### 5.9.4 跨阶段例外不是自由通行

只有同时满足以下条件，网页规划侧才能在 handoff 记录一次性 `CROSS_GATE_EXCEPTION`：

- 更低门剩余阻断项处于真实外部等待/不可行动，或与候选切片可证明无共享输入/消费者；
- 候选不依赖未完成前置，且只读、采样、影子、文档或可完全隔离/恢复；
- 明确写出范围、为什么不污染下游、停止条件、恢复点和不得产生的效果主张；
- 不得用于生产权重、真实外发、权限扩大、策略晋级或“先做后补证据”。

Codex 不得自己发明例外；没有 handoff 明示就按正常阶段门执行。例外结束后必须回到最低未闭环主门。

#### 5.9.5 依赖与效果闭环

`依赖` 是“能不能开工”，`效果前置` 是“能不能声称有效/上线”。例如 RSH-031 的历史语料整理可以按其阶段门开始，但在 RSH-026/IMP-020/RSH-030 满足前，只能产研究资产，不能把“龙头规律”写成已验证优势。任何任务完成后，网页审核都要重算被它解锁的任务；没有消费者/下游的“完成”不算闭环价值。

## 日常使用

默认采用固定仓库记录＋人工短提示，不传递任务卡、不建设自动接续链。handoff只索引唯一当前任务；派工、执行事实、审核结论和下一动作仍在该阶段条目。用户的完成提示仅触发重读，未推送记录/缺证据/过时批准均不能继续。网页每轮审完须复评功能衔接与净收益，有依据再修改方案和优先级。

权责按 [协作审核规范](collaboration-workflow.md)：网页ChatGPT负责规划和任务增删重排，Codex回填执行事实并提交审核。状态“待交付”可表达待网页审核/待CI，具体阻塞写任务页；不得未审核自标最终完成或直接跨轮。

1. 默认由网页或 `ashare-ledger-continue` 严格按 §5.9 计算当前主门和唯一切片：阶段门 → 门禁角色 → P0/P1/P2 → 门内序 → 硬依赖/效果前置。用户说“继续任务/继续”只授权这一刀，不授权跨门或连续扫账本。每轮最多一个主切片和一个不冲突的 GX 伴随切片。
2. 任务只有一份：阶段页的 `## BUG/IMP/RSH/GOV/OPS-NNN` 条目。新增先去重、取域内未用序号；迁移/合并保留原 ID 的去向。不要把工作包数量或任务数量当作工时/完成率。每个领取切片补文件/消费者、反例、低成本替代、实施步骤及恢复；业务任务由 Codex 实现，方案文字不是完成证据。
3. 状态使用 `待执行 / 进行中 / 部分完成 / 待条件 / 待交付 / 已完成 / 已退出 / 已合并`。阶段门、门内序、门禁角色、依赖、效果前置同样是任务真相的一部分；改变它们必须有证据与理由，不能为了方便开工临时降门。退出/合并须增加“处置依据”；合并还须填“合并至”另一个有效任务 ID。退出不算完成，活动任务不得继续依赖退出/合并项。待条件须在“下一步”明确条件；未验收不是完成。P0 正确性/安全优先，P1 核心能力，P2 仅证据支持的简化。
4. 更新时只改任务本页。完成后保留一句结论、验收证据、PR/commit 与必要限制；长日志进忽略的 artifacts，稳定知识回原专题/KB。不再为每轮复制全仓门禁、F 档、H 索引和 handoff 条目。
5. 完成项不再影响施工顺序。被依赖/引用的 ID 保留简短条目，迁出时须同步可解析去向，不能留下幽灵依赖。仍支撑依赖/恢复的成果留阶段“已交付基线”；后续新任务完成/退出/合并后在所属阶段尾部保留简短 ID 条目与证据，不参与活队列；[旧编号处置记录](archive/ledger-transition-20260917.md) 冻结本次 123 个源 ID，不追加新任务或成为第二份状态表。不再维护已关闭任务的长篇日记。
6. 每批跑 doc-health：阶段全部可达、任务唯一、阶段门/门内序/角色合法、硬依赖不逆序且无环、效果前置可解析、状态合法、完成有证据、旧编号可解析。门禁验证这些不变量，不强制旧多表格式。
