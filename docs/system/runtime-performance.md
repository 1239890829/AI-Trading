# 运行性能：测量入口与 2026-09-30 有界调查

> 用途：定位真实请求浪费，保留可复现测量和反例。任务状态仅归 [W06/IMP-019](../stages/w06-performance.md#imp-019)。本页不是生产 SLO、部署验收或策略效果证明。

## 1. 本轮能确认什么

板块排行 `/api/market/boards` 原先是 `get → await 回源 → set`，冷缓存同时到达的请求各自回源。现在复用既有 `TTLCache.get_or_set`；缓存仍为 60 秒、容量 4，返回全量、排序规则及源字段保留。每次响应只复制要标记的元数据，`cached` 不写回共享对象。响应 JSON 序列化不修改缓存数据。

`/api/system/metrics` 的 API 行新增 `error_count`、`error_rate`、`status_counts` 和 `status_unknown_count`。4xx/5xx 是错误；未捕获异常记 500，取消等没有响应的尝试记 unknown。全部观测进入延迟分布；错误率分母为有状态的观测，unknown 单列。原有核心端点预算保持 2000ms，但现在必须全部返回 200 才能通过，不能用快速报错获得绿色。

测量边界：中间件量到 `call_next` 返回响应头；不声称包括流式响应完成、网络传输或最终画面。进程环形缓冲最多保留 20000 条、默认聚合最近一小时；`count` 是保留窗口中的观测，不是进程生命周期总请求数。DuckDB 原有慢查询环只包含超过阈值的查询，不能拿它计算全查询错误率/分位。

### 6.3 全系统尚需区分的原因

工作台、盘面、市场各视图、选股、复盘/助手和详情读链已按当前调用入口检视；不能靠单一资金页面推导全部完成。工作台依赖报价/宽度快照、盘面依赖榜单与题材、选股依赖事件/联动与真实全市场快照。上游限流、串行分页/备源退避、全市场快照覆盖和后台竞争都可能带来慢读与陈旧，需与前端重复请求分别定位。

本批不改变供应商优先级、时间/质量阈值、总重试预算或研究隔离。真实开盘同版本/同负载的源龄与错误率、浏览器关键画面完成、长期内存/SQL锁及重研究竞争仍需IMP-019现场测量。正常盘后最近行情、真实陈旧、缺源和加载中继续分开标注；没有证据不能宣称全系统流畅度问题已经消失。
