# 行情实时性与数据源答疑（2026-09-01）

> 回答四个问题：①同花顺 skill 收费与实时级别；②各模块数据源与刷新频率总表；③实现同花顺级"每秒跳动"的技术方案；④券商 API 实盘交易可行性。
> 项目内事实均来自代码与 `docs/data/data-source-comparison.md`（2026-08-29 实测）；外部事实（收费、券商门槛）来自 2026-09-01 网络检索。

---

## 1. 同花顺行情 skill：是否收费、是否实时、刷新频率

### 1.1 收费：免费

项目所用 skill 为 `hithink-finance`——同花顺官方「金融数据服务」（fuyao.aicubes.cn），**免费**：

- API Key 免费申请（fuyao.aicubes.cn/admin），项目 MIT 开源（GitHub HiThink-Tech/Financial-API）；
- 官方声明（README §调用频率与限流）：**不设累计调用次数上限**，仅要求合理控制请求节奏，可能动态限流（错误码 `4001`，指数退避最多重试 3 次）；
- 注意区分：它**不是**同花顺 iFinD / quantapi 那类付费数据终端（商用年费约 2–5 万/年，Level-2 逐笔 8–15 万/年）。fuyao 是官方免费开放的数据出口，代价是能力边界更窄。

### 1.2 实时性：REST 拉取式"最新行情"，非 tick 级，不适合秒级轮询

- 官方能力边界明确：**不覆盖分钟 K、tick、Level-2、五档盘口**（`capability-map.md`）。
- 行情快照端点（`/api/a-share/prices/snapshot`）返回"最新行情"并带毫秒时间戳，但**无延迟 SLA、无推送/WebSocket 通道**，只能轮询。
- 本项目实测（2026-08-29/09-01）：涨停池、龙虎榜等特色数据端点延迟 40–130ms，很快；但**行情快照批量端点响应不稳定（曾实测最长 8s）**。这正是秒级化改造时把 `realtime_rank` 定为"腾讯优先、ths 移出秒级链"的原因——ths 配额宝贵且响应慢，不能挡在 1Hz 链路上。

### 1.3 结论

| 问题 | 答案 |
|---|---|
| 是否收费 | 免费（Key 免费、无累计次数上限、动态限流） |
| 数据级别 | 最新行情快照（L1 级），非 tick/L2；无分钟 K、五档、逐笔 |
| 能否秒级回传 | 单次请求最快几十 ms，但响应不稳定（可达秒级~8s），**不建议 1Hz 轮询** |
| 刷新频率 | 无推送，只能 REST 轮询；官方按限流约束请求节奏 |
| 项目内定位 | 低频/特色数据主源（涨停池、龙虎榜、日历、板块、竞价、估值）；秒级行情不用它 |

## 3. 实现与同花顺产品一致的"每秒跳动"

### 3.1 先澄清事实：同花顺 App 也不是 tick 级

同花顺 App/网页的"每秒刷新"，本质是**交易所 L1 快照行情**（约 3–6 秒一个价格变化）+ 客户端**秒级轮询/推送** + **涨跌闪动动画**。它不是逐笔 tick——tick/L2/十档在同花顺是单独付费的 Level-2 产品。所以"做到无延迟观感"用免费 L1 源就能对齐；真正的差距在数据级别，不在刷新频率。

### 3.2 方案对比

| 方案 | 做法 | 端到端延迟 | 成本 | 限制 |
|---|---|---|---|---|
| **A. 现状（已达成）** | 腾讯 L1 快照 1Hz 轮询 + WS 推送 + 闪动动画 + K线/分时实时合成 | 实测 0.6–1.3s（数据本身 L1 3–6s 一变，1Hz 轮询理论上零漏拍） | 0 | 非 tick、无逐笔/十档；爬虫性质，腾讯改版需跟进 |
| B. 双源并发对齐 | 新浪 + 腾讯并行请求取先到者 | 与 A 相当，可靠性提升 | 0 | 两源同属 L1，收益主要是抗单源抖动 |
| C. 推送型免费源 | 东财 push2 WebSocket / 雪球 ws | 理论 <1s | 0 | 反爬强（push2 主域本机已被 WAF）、随时失效，**不建议做主链** |
| D. 付费行情源 | ① miniQMT 自带实时行情（开通量化权限即免费，tick 推送）；② 东财 Choice 约 3k–1万/年；③ 同花顺 iFinD/quantapi 商用 2–5万/年、L2 8–15万/年 | tick 级 <1s 推送，含逐笔/十档 | 免费（①）到数万/年 | ① 需先开通券商量化权限（见 §4）；②③ 预算门槛高 |

### 3.3 结论

- **观感层面方案 A 已达标**：上一轮秒级化改造（QuoteHub 1s 固定节奏、订阅原地更新、前端稳定 key 订阅、闪烁动画、K线/分时合成）实测列表 999ms/1125ms、头部 1300ms、K 线 757ms、分时 575ms，与同花顺 App 的 L1 观感一致。
- 若要"真·无延迟"（逐笔驱动、盘口十档、委托队列），唯一路径是方案 D——其中 **miniQMT 行情是免费 tick 源的最优解**，可与 §4 的实盘对接一并开通。
- 可选的小幅增强（方案 B）：把新浪并入 1Hz 并发组，腾讯失败时零感知切换，成本约 20 行代码。

## 4. 对接券商 API 实现真正的实盘交易

### 4.1 结论：可行，但必须走券商量化终端，个人没有"裸 REST 下单接口"

券商不对个人投资者提供官方 REST/WebSocket 下单 API；同花顺、东财等三方平台的交易接口也仅对机构/券商合作开放。个人实盘程序化的正规通道只有两条：

1. **miniQMT / QMT（迅投）**——提供 Python API（`xtquant` 库），可独立进程下单、查持仓、收回报。**对本项目最现实**。
2. **PTrade（恒生）**——策略跑在券商服务器端（云端托管），不适合本项目"本地策略引擎 + 外部执行"的架构，仅作备选。

### 4.2 开通前提（2026 年主流券商口径）

| 条件 | 要求 |
|---|---|
| 基础 | 券商开户、沪深股东户正常、三方存管 |
| 风险测评 | **C4（积极型）及以上**，C3 以下驳回 |
| 交易经验 | 首笔 A 股交易满 **6 个月** |
| 资产门槛 | 客户经理白名单渠道：miniQMT/PTrade 约 **10 万日均资产**（国金/银河等）；纯自助渠道普遍 30–50 万甚至不给入口 |
| 合规 | 签署程序化交易协议并**向券商报备**（账户、策略类型、交易系统信息）——《证券市场程序化交易管理规定》已施行，高频标准（如每秒申报≥300 笔）另有更严格要求；本项目"人工确认 + 低频下单"属普通报备即可 |
| 费用 | miniQMT/PTrade 权限本身免费；注意撤单流量费与佣金条款 |

### 4.3 实现路径（对本项目）

1. **开权限**：联系券商客户经理开通 miniQMT（建议国金/银河等 10 万门槛渠道），先跑模拟账号。
2. **加适配层**：backend 新增 `BrokerAdapter` 接口（`place_order / cancel / query_positions / query_trades`），第一个实现基于 `xtquant.xttrader`（miniQMT 需在本机登录 miniQMT 客户端作行情/交易网关）。
3. **复用现有风控链**：下单前过 `RiskEngine` 预检（仓位上限、回撤保护、拒单校验）——这条链已在模拟盘引擎里验证过，实盘只是把撮合换成真通道。
4. **保留人工确认**：订单意图先落库，人工点确认后才会发出（与现有"不真实下单"红线兼容，红线解除需用户显式授权）。
5. **灰度顺序**：paper trading（已具备）→ miniQMT 模拟盘 1–3 个月 → 实盘小资金。

### 4.4 不可行/不推荐的路径

- **easytrader 等客户端 UI 自动化**（模拟点击券商 App/同花顺客户端下单）：灰色地带、违反券商协议、客户端一改版即失效、存在误下单风险，不推荐。
- **直接调用同花顺/东财"交易 API"**：对个人不存在此通道。
- **替代方案**（不开权限也能获得 80% 的价值）：现有模拟盘引擎（撮合/风控/回撤保护已全）+ 券商 App 自带条件单承接简单触发单。
