## §0 结论摘要

### 0.1 三句话结论

1. **助手最大的缺口不是"不够聪明"，而是"没有手"** —— 它没有工具调用能力，只能读注入提示词的 6 只标的快照，其余全靠模型背书。竞品（问财/妙想/涨乐）的核心分水岭就在"能不能按问题取数"。这是 P0。
2. **跳转要从"2 个落点"扩到"全功能点"** —— 现在只能跳工作台个股和盘面题材，市场/研究/精选/盘中的具体 tab 与条目都跳不了。方案是「受限枚举 + 入口注册表 + 三类定位方式」，见 §1。
3. **归属上有个真 bug 要先修** —— 后端 `review-scheduler` 15:30 自动跑复盘，WorkBuddy automation「A股每日盘后复盘」也在 15:30 跑，两者抢同一份报告。助手不该"再生成一份复盘"，而该"解读已产出的复盘"。详见 §3.2。

### 0.2 现状盘点（实测）

**助手侧**

| 项 | 现状 | 位置 |
|---|---|---|
| 对话链路 | SSE 流式，`meta/delta/error/done`，可中断/重生成 | `api/routes/assistant.py:102` |

### 1.2 一键跳转：定位方式与参数约定（**本方案核心交付物**）

#### 1.2.1 三类定位方式

功能入口不是单一 URL 能覆盖的，因为项目里存在三种状态归属：

| 定位方式 | 适用 | 机制 | 可靠性 |
|---|---|---|---|
| **A. URL 深链** | 状态已在 URL query 里的（tape/market/research/picks/intraday） | `router.push(url)`，目标页 `useSearchParams` 初始化 | 高（无时序依赖，可书签） |
| **B. 命令总线** | 状态纯组件 state 的（**工作台右栏 8 tab、市场子视图、研究复盘日期**） | URL 带参 + 目标页挂载后派发自定义事件；或 `sessionStorage` 存 pending 命令，目标页消费后清除 | 中（依赖目标页已挂载） |
| **C. 锚点滚动 + 高亮** | 长页分区（`/intraday` 七个 section） | `?sec=<id>` → 目标页 `scrollIntoView` + 2s 高亮描边 | 中（纯视觉定位） |

**推荐顺序**：能用 A 就别用 B；B 的目标页改造应按 A 收敛（把 state 提升为 query），一次性成本换长期可深链。

#### 1.2.2 参数命名约定（统一，禁止各页自造）

| 参数 | 含义 | 取值 | 现状 |
|---|---|---|---|
| `tab` | 页级主视图标识 | 见下方路由表 | 已用于 tape/market/research，统一沿用 |
| `rt` | 工作台右栏 tab | `book/trades/trade/real/profile/info/speed/boards` | **待新增** |
| `ct` | 工作台图表 tab | `kline/minute/flow` | **待新增** |
| `date` | 交易日 | `YYYY-MM-DD` | tape 已有，统一全站 |
| `focus` | 聚焦具名实体（题材名） | 题材名原文 | tape themes 已有 |
| `symbol` | 单个个股代码 | 6 位数字 | workbench 已有 |
| `symbols` | 多个个股代码 | 逗号分隔 | tape limitup 已有 |
| `theme` | 题材过滤 | 题材名 | tape limitup / intraday 已有 |
| `from` | 来源页完整 URL（返回按钮） | encodeURIComponent(path+search) | 已有 |
| `sec` | 长页分区锚点 | `quotes/opportunity/brief/watcher/reminders/compare/winrate` | **待新增**（intraday） |

#### 1.2.5 「提及的功能点」如何变成链接（识别机制）

现有实体识别只认**实体**（个股/题材）。功能点是**意图**，需另开一路。三方案对比：

| 方案 | 做法 | 判断 |
|---|---|---|
| A 词典别名表 | `"涨停池"→NAV_TARGETS.limitup_pool`，前端最长匹配 | ✅ 确定、可测、零 token，但需维护别名表 |
| B 模型输出完整 URL | `[[/tape?tab=limitup\|涨停池]]` | ❌ 模型会编 URL（项目既有教训："模型记代码不可靠"），且有越权/注入风险 |
| C 受限枚举 | 模型输出 `{{nav:limitup}}`，前端查注册表 | ✅ 模型选枚举比拼 URL 可靠，且可白名单校验 |

**推荐 A + C 混合**：
- 高频功能名走 **A**（前端词典，零成本，覆盖"涨停池/龙虎榜/题材梯队/每日精选/复盘报告"等固定说法）；
- 模型回答里主动引导走 **C**（提示词给枚举清单，模型输出 `{{nav:xxx}}`，前端渲染成按钮）；
- **硬守卫**：C 路径产出必须命中 `NAV_TARGETS` 白名单，未命中即当纯文本，绝不渲染成链接；所有生成 URL 必须以 `/` 开头且 pathname 在 `{/workbench,/tape,/market,/picks,/research,/intraday}` 内。

**验收标准**（可测）：给定 20 条含功能点的话术，跳转命中率 ≥ 90%，且无一条链接指向白名单外。

## §2 竞品差距分析

对比对象：同花顺问财、东方财富妙想、华泰 AI 涨乐、第三方多智能体（财搭子类）、Wind Alice。

### 2.1 我们缺失或明显落后的能力

| # | 能力 | 竞品水位 | 我们 | 差距影响 | 说明 |
|---|---|---|---|---|---|
| 1 | **工具调用 / 按需取数** | 问财、妙想、涨乐均能按问题调数据 | **无**，仅 6 只注入快照 | **极高** | 决定助手是"能查"还是"只能聊"，是最大分水岭 |
| 2 | **输出溯源**（标注数据来源与口径） | 财搭子标注可溯源来源、妙想带信息溯源 | **无标注** | **高** | 金融场景可信度核心；且与本项目"口径必须标注"的既有纪律冲突 |
| 3 | **主动提醒 / 盯盘** | 九方 AI 盯盘（6 只×35 因子，推送+弹窗+语音，盘后盯盘日报）、涨乐"特别提醒" | 有告警引擎但**助手不参与**，且无 WS 事件通道 | **高** | 检测能力其实我们更全（涨停/炸板/情绪/方向证伪），缺的是"送达 + 归因" |
| 4 | **自然语言→结构化操作**（建条件、加自选、建盯盘任务） | 涨乐任务助手、问财条件单 | **无** | 中高 | 我们能做"用自然语言建告警规则"，见 §4.1 |
| 5 | **个股一键诊断报告** | 妙想财报拆解、九方六维体检卡 | **无** | 中 | 我们已有六维评分与事件卡，只差聚合 |
| 6 | **会话历史 / 结论沉淀** | 主流均有多轮会话 | 无持久化 | 中 | 改进后可将助手结论沉淀为 action_items |
| 7 | **反馈闭环**（点赞点踩反哺） | 部分有 | 无 | 中 | 可复用复盘 action_items 机制 |
| 8 | **多 Agent 分工** | 涨乐主 Agent + 多专家 Agent | 单提示词 | 中 | 单人项目性价比低，暂不建议 |
| 9 | **语音交互** | 涨乐/九方语音下单 | 无 | 低 | 桌面工作台场景收益小；Web Speech API 可做但优先级低 |
| 10 | **持仓诊断** | 财搭子跨券商持仓复盘 | 有模拟盘 + 真实持仓接口，未接入助手 | 中 | 数据我们其实有（`/real`、`/paper`） |

### 2.2 我们的结构性优势（不应妄自菲薄，方案要放大）

1. **数据与呈现同源**：助手跳过去的涨停池/题材梯队，就是你自己算的，口径与页面完全一致。问财/妙想给你的是黑箱结果，你无法验证。
2. **有方法论闭环**：本地回测、复盘报告、改进项处置、方法论版本体系——竞品没有"上次错了→改了什么→改得对不对"的闭环。
3. **零边际成本、数据不出本机**：不依赖第三方 API 配额（除 LLM 网关），不上传持仓。
4. **可解释性底子好**：`picks` 的 `basis`、`review` 的 `evidence/gaps` 本来就是结构化的，天然适合做溯源标注——竞品要从零补，我们是"把已有的展示出来"。

### 2.3 差距排序结论

**先补 1（工具调用）和 2（溯源）** —— 这两项决定了"能不能信"；再补 3（提醒）和 4（自然语言操作）——决定"用不用得起来"；8/9 明确不做。

## §3 板块联动与能力边界

### 3.1 归属判据（先定规矩，再分活）

| 判据 | 归属 | 理由 |
|---|---|---|
| 需要 LLM 判断 + 跨系统编排（读文档、改代码、处置改进项、发飞书） | **WorkBuddy automation** | 只有它能读仓库、执行 skill、跨进程操作 |
| 确定性、可重放、服务内闭环（拉数→算→存→推） | **后端常驻调度** | 可重放、可测试、不依赖 LLM 可用性 |
| 结果因人而异、需要追问、需要解释 | **助手被动响应** | 主动生成会与调度产物分叉 |
| 需要秒级反应的检测 | **后端规则引擎**（绝不交给 LLM） | LLM 轮询成本爆炸、延迟高、不可重放 |

### 3.2 每日复盘：谁生成？

**现状（有问题）**

```
后端 review-scheduler      15:30  →  POST /api/review/run  → 生成报告
WorkBuddy「A股每日盘后复盘」 15:30  →  加载 skill + 清单逐项核验 + PATCH 改进项 + T+3 回访
WorkBuddy「盘后对照推送」    15:40  →  build_push_cards.py → 飞书卡片
```

⚠️ **同一分钟撞车**：后端在 15:30 生成报告的同时，WorkBuddy 也在触发复盘流程，两者抢同一份 `review_reports` 记录，存在重复生成/覆盖风险。

**建议归属**

| 环节 | 归属 | 触发条件 | 数据流向 |
|---|---|---|---|
| **报告生成** | 后端 `review-scheduler` | 交易日 15:30 后 + 当日无报告 | 内部数据源 → `ReviewService.run()` → SQLite `review_reports` + JSON 落盘 |
| **深度复盘与改进项处置** | WorkBuddy automation（**改到 15:45**） | 交易日 + 报告已存在（先 GET 校验，无则等待/跳过） | 读 `docs/daily-review-*.md` → 调 `/api/review/*` → PATCH action_items → 回读校验 |
| **推送** | WorkBuddy 15:40（保持不变） | 报告存在 | `/api/review/reports/{date}` → `build_push_cards.py` → lark-cli |
| **助手** | **不生成**，只**解读** | 用户问"今天复盘怎么样" | 读 `/api/review/reports/{date}` → 讲成人话 + 跳 `/research?tab=review&date=` |

**助手不生成复盘的三条理由**：
1. 已有两处产出，助手再生成一份 = 第三份事实来源，必然分叉；
2. 复盘需要全市场数据聚合（breadth/themes/picks/trading），远超助手当前 6 只快照能力，硬做只能靠模型编；
3. 复盘的价值在**改进项闭环**，不是那篇文字——闭环在 WorkBuddy 侧已有完整实现。

**助手该做的（差异化价值）**：把结构化报告翻译成人话、回答"今天错在哪一类"、把 `action_items` 变成"我可以帮你建一条告警规则"这类可操作动作。

### 3.3 盘中个股机会 / 异动：怎么实时通知？

**现状能力盘点（比想象中全）**

| 层 | 已有 | 位置 |
|---|---|---|
| 个股级异动端点 | 涨停池、跌停池、炸板池、涨速榜、龙虎榜、资金流 | `market.py:617/634/931/796/652/892` |
| 规则层 | 方向确认（板块涨幅/涨停家数/龙头/量比）、证伪（回撤/转负/龙头炸板） | `picks/intraday_rules.py:142,240` |
| 市场级 | 高度板炸板、炸板率≥40%、指数 15min 急杀 | `sentiment/intraday_monitor.py` |
| 机会视图 | 独特性/确定性评分、`top_watch_stocks` | `picks/intraday_opportunity.py:61,109,255` |
| 告警引擎 | 规则表 + 5s 轮询 + 冷却 + log/in_app/feishu 三通道 | `market/alert_engine.py:16` |

**缺口**：① 全是"系统自己定的规则"，没有用户/助手订阅的个性化提醒；② 无 WS 事件通道，前端只能轮询 REST；③ 助手浮窗完全没消费告警。

**分工设计**

```
[检测层 100% 后端，不碰 LLM]
  行情/快照 1s~60s
      ↓
  AlertEngine(5s) + picks-watcher(60s) + sentiment-monitor(60s)
      ↓ 命中
  AlertEvent 落库 + 冷却判定
      ↓
  ┌───────────────┬────────────────┬─────────────────┐
  ↓               ↓                ↓
飞书(强打断)   in_app + 浮窗角标   用户主动问
  ↓               ↓                ↓
外部通道      [新增] 助手浮窗     助手读 /api/alerts/events
              角标 + 一键展开      + intraday-opportunities
                                   ↓
                              LLM 只做「归因与措辞」
                              （事件后一次性调用，非轮询）
```

| 环节 | 归属 | 触发条件 | 理由 |
|---|---|---|---|
| **异动检测** | 后端规则引擎 | 5s~60s 轮询命中阈值 | LLM 实时检测成本/延迟都不可接受，且不可重放 |
| **是否推送 / 推哪** | 后端引擎（冷却 + 通道配置） | 规则 `cooldown_seconds` | 确定性决策 |
| **归因与措辞** | **LLM（助手）** | 事件发生后**一次性**调用 | 这是 LLM 唯一不可替代的环节：把"炸板率 42%"说成"高位分歧加剧，注意情绪退潮" |
| **规则创建/修改** | **助手（自然语言）** | 用户说"茅台跌破 1600 提醒我" | 助手独占能力，竞品卖点，见 §4.1 |
| **页面内呈现** | 浮窗角标（**新增**） | 有未 ack 的 in_app 告警 | 助手目前与告警系统完全脱节 |

**为什么不让助手"自己盯盘"**：助手是请求-响应式的，没有常驻状态；真要它盯，就得每秒拉全市场数据喂给 LLM——按当前网关成本（单次约 $0.0006~0.085）算，一天下来是灾难，且 15:00 收盘后不可重放。检测必须留在后端。

### 3.4 助手可打通的板块总表

| 板块 | 打通方式 | 归属 | 触发 | 现状 |
|---|---|---|---|---|

## §4 拓展功能挖掘

每项给出：场景 / 数据来源 / 落地合理性 / 预期价值 / 依赖档位。

### 4.1 【推荐】自然语言建告警 ⭐

- **场景**："茅台跌破 1600 提醒我"、"储能板块有 3 家涨停就通知我"
- **数据来源**：实体词典（个股识别）+ `AlertRule` 模型（已支持 `price_below/change_pct_above` 等）
- **合理性**：后端规则表字段完备，只差"自然语言 → 规则 JSON"这一层。助手解析出 `{symbol, condition_type, threshold}` → `POST /api/alerts/rules`，**落地前给用户确认卡片**（防误建）
- **价值**：**高**。这是竞品的收费卖点，我们有现成引擎，成本极低；且把助手从"只能说"变成"能办事"
- **依赖**：A（立即可做，纯本项目内）

### 4.2 【推荐】口径解释器 ⭐（项目特有）

- **场景**："涨停家数为什么两个数字？"、"为什么日 K 显示 5 连板但涨停池说不是涨停？"
- **数据来源**：`docs/data/data-source-comparison.md` + 记忆里的口径分歧表（涨停家数两口径、连板高度两口径、题材归因投票）
- **合理性**：这些是**本项目踩过的坑**，写进提示词即可，零开发量；外部竞品根本答不了"你这个系统的口径"
- **价值**：**高**。直接降低使用者的误解成本，是差异化能力
- **依赖**：A（写提示词 + 少量文档抽取）

### 4.3 【推荐】数据健康播报

- **场景**："今天题材归因怎么全是未分类？"、"为什么没有涨停原因"
- **数据来源**：`/api/system/providers`（已有）、`ths-reason-sentinel`、`llm-probe`（刚做完）
- **合理性**：端点全在，缺的只是"翻译成人话"。2026-09-04 的教训正是"降级无感知"
- **价值**：**中高**。把"静默降级"变成"可解释的状态"
- **依赖**：A

### 4.4 个股速诊卡

- **场景**："帮我看看 600519"
- **数据来源**：技术评分（tech_score v3 八维）+ `/themes/stock/{sym}` + `/events/symbol/{sym}` + `/financials` + `/capital-flow`
- **合理性**：数据全在，需新增一个**聚合端点**（`GET /api/assistant/briefing/{symbol}`），避免助手串行调 6 个接口
- **价值**：**中高**。竞品标配（妙想财报拆解、九方体检卡）
- **依赖**：B（需后端新增聚合接口）

### 4.5 复盘解读器

- **场景**："今天哪里做错了"、"这周改进项有哪些没处置"
- **数据来源**：`/api/review/reports/{date}`、`/api/review/action-items`、`/review/effectiveness`
- **合理性**：报告已结构化（`dimensions/action_items/meta_insights`），助手只需翻译 + 提供跳转
- **价值**：**中高**
- **依赖**：A（端点已有，只需助手能取）

### 4.6 助手输出溯源标注

- **场景**：助手给出的每个数字都标出来自哪个端点、什么时点、什么口径
- **数据来源**：改造 `assistant/context.py` 的快照块，给每行加 `[来源: /api/quotes · 14:32 · 快照]`
- **合理性**：金融可信度刚需；且本项目 `picks.basis`、`review.evidence` 本就结构化
- **价值**：**高**（§2 差距 #2）
- **依赖**：B（需改快照注入格式 + 提示词）

### 4.7 助手结论沉淀为改进项

- **场景**：助手给出建议 → 一键"存为改进项"
- **数据来源**：`POST /api/review/action-items`（表已存在）
- **合理性**：复用已有闭环，不新建存储
- **价值**：**中**
- **依赖**：B

### 4.8 自然语言多条件选股

- **场景**："PCB 板块净利润连续三年增长、市值 100 亿以上"
- **数据来源**：**缺口**——`/api/financials` 是单股接口，没有全市场财务筛选维度
- **合理性**：这是问财的核心能力，但要建全市场财务快照仓（marketdb 目前只有日 K）
- **价值**：**高**，但成本高
- **依赖**：C（**依赖外部财务数据源 + 建仓**，不建议近期做）

### 4.9 历史追问（"上周三涨停池怎么样"）

- **数据来源**：`/api/limit-up?date=`（已支持）、`/limit-down`、`/longhu`
- **依赖**：B（需要助手具备工具调用能力，即 §2 差距 #1）

### 4.10 多标的对比表

- **场景**："对比茅台和五粮液的估值与资金"
- **数据来源**：`/financials`、`/capital-flow`、`/quotes`
- **依赖**：B

### 4.11 推送卡片文案润色

- **场景**：`build_push_cards.py` 产出的卡片用 LLM 润色成更可读的结论
- **依赖**：C（**依赖网关配额**，且增加故障面；收益不明确，**建议暂缓**）

### 4.12 语音播报盘中提醒

- **依赖**：A（Web Speech API，零成本），但**价值低**（桌面场景），排在最后

## §6 风险与验收

### 6.1 实施风险

| 风险 | 缓解 |
|---|---|
| 工具调用让模型伪造参数（编代码、编日期） | 参数 schema 强校验；标的代码必须命中实体词典；日期必须落在交易日历内；失败显式报错不静默 |
| 工具调用放大网关成本 | 每轮上限 N 次调用；结果进 TTLCache；超限显式提示 |
| 跳转白名单被绕过 | 所有目标必须命中 `NAV_TARGETS`；pathname 白名单；新增守卫测试（这是**必须有的反向断言**） |
| 命令总线（B 类定位）时序问题 | 目标页未挂载时降级为 `sessionStorage` pending 命令；优先把 state 收敛为 query（A 类） |
| 助手生成"第三份复盘"造成分叉 | 提示词硬约束：复盘只在既有报告上解读，禁止自行生成；回答附跳转而非复述全文 |

### 6.1.1 P0 落地实测（2026-09-06）

**跳转（P0-1）**——浏览器文本通道逐条验，不是读代码推断：

| 验证项 | 结果 |
|---|---|
| `/workbench?symbol=600519&rt=profile` | 右栏「资料」tab 为激活态（其余 5 个非激活） |
| `/workbench?symbol=600519&ct=minute` | 图表区「分时」激活、「K 线」非激活 |
| `/research?tab=review&date=2026-09-04` | 复盘 tab 直接展开 2026-09-04 报告 |
| `/intraday?sec=opportunity` | 容器 scrollTop=90，目标分区 relTop=8（滚动到位） |
| 助手回答点「涨停池」 | URL → `/tape?tab=limitup`，盘面页「涨停生态」tab 激活 |
| 渲染形态 | `涨停池↗`/`龙虎榜↗`/`复盘报告↗` 绿色、`存储芯片` 紫色（个股/题材/功能三类可区分） |

**工具调用（P0-3）**——真实网关 + 真实数据源跑通：

```
POST /api/assistant/chat {"content":"今天涨停池有几家？用工具查一下"}
→ meta → tools["limit_up"] → delta（正文）
→ "**2026-09-04 涨停池共 38 家**（来源：涨停池数据快照，数据时间 2026-09-04，
   口径：当日涨停个股统计；工具默认返回最近一个交易日，9月6日为周日，故为 9月4日数据）。"
```

两个实测踩到并修掉的坑：
1. **流式会把半个标记漏给用户**（`{{` 单独一块 → 界面上出现 `{{`）：判据从"出现 `{{tool:` 完整前缀"放宽为"出现 `{{` 且未闭合"，见 `has_partial_tool_call`。
2. **日期非法时静默回退最近交易日**：模型查 9/5（非交易日）会拿到 9/4 的数据还照说不误。改为显式报错；默认日也从 `date.today()` 改为周末回退（周日查池子只会空，模型会照着"没有数据"回答）。

变异验证（确认断言能见红）：清空 quota markers → 7 项失败；`fail_ttl` 走 `ok_ttl` → 1 项失败；白名单守卫 `return true` → 失败；meta 去掉 `sources` → 失败；工具标白名单关闭 → 2 项失败。

### 6.2 验收口径（沿用项目纪律：以实际渲染为准，不靠推理）

- 跳转：20 条话术命中率 ≥ 90%，0 条越权链接（浏览器文本快照逐条验）
- 工具调用：参数非法时返回显式错误，绝不静默降级为"无数据"
- 溯源：助手回答中每个数字可追溯到具体端点与时间戳
- 门禁：pytest + pyflakes + tsc + eslint + vitest 全绿；新增改动补变异验证（断言要能见红）
