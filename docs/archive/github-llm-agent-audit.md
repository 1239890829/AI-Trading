# GitHub star 分组 trading 审计（第 3 组）：LLM 交易 Agent 三仓对比

> 审计日期：2026-09-03。审计对象：TradingAgents（LangGraph 多智能体）、ai-hedge-fund（线性 pipeline）、Vibe-Trading。
> 方法：clone 到 `/tmp/gh-audit/`，无 API key 环境下用 mock LLM 客户端降级验证编排流程 + 逐文件精读 prompt/编排代码。
> 证据等级标注：**A = 实际运行验证**；**B = 读了代码未运行**；**C = 只看元数据/README**。
> 说明：本稿为审计结论整理落盘。

---

## 一、基线：本项目 LLM 使用现状（审计前先摸底，证据 A）

- 本项目 LLM 已接入 WorkBuddy 通道（2026-08 任务 #187），用于盘后复盘等场景。
- 现状短板：LLM 输出缺乏**系统性可解释性契约**——置信度怎么给的、数据缺失时怎么表现、幻觉怎么拦，都没有成文规则。

---

## 二、TradingAgents（LangGraph 多智能体）

**一句话定位**：多角色（分析师/研究员/交易员/风控）圆桌讨论式交易决策框架。

### 2.1 实测（证据 A/B）

- 编排流程用 mock 客户端跑通：每产生**一张票**需要约 **12 次 LLM 调用**（多分析师 × 多轮辩论 × 汇总）。
- 成本结构判断：这是「研究报告生产管线」的架构，不是「盘中实时系统」的架构。打板系统分钟级响应 + 每日数百标的扫描，12 调用/票的编排在本项目场景下**过度设计**。

### 2.2 真金：置信度必须附带规则解释

其 prompt 契约里要求每个置信度数值必须附带**生成该置信度的规则引用**（哪条证据、哪个权重）。这是可解释性的正确姿势，值得直接采纳。

**判定：编排不引入；prompt 契约中的置信度规则采纳。**

---

## 三、ai-hedge-fund（线性 pipeline）

**一句话定位**：模仿知名投资人风格的线性分析 pipeline（各分析师模块串行产出，最后汇总）。

### 3.1 真金：弃权语义（证据 B）

- 其 prompt 明确定义**「数据不足以支持判断时，分析师必须输出弃权（no-opinion）而不是硬给方向」**——弃权是合法输出，不是失败。
- 这对治的是 LLM 交易系统最隐蔽的病：**数据缺失时模型硬编一个结论**，表面完整实则幻觉。

**判定：弃权语义直接采纳进本项目 LLM prompt 契约。**

---

## 四、Vibe-Trading

**一句话定位**：轻量 LLM 交易助手，亮点在**输出校验与反幻觉闸门**。

### 4.1 真金：反幻觉闸门三类拒绝码（证据 B）

- 其输出校验层定义三类拒绝码，LLM 输出触及即整体拒绝重试：
  1. **引用不存在数据**（编造指标值/不存在的新闻）
  2. **超出输入范围推断**（结论依赖输入里没有的信息）
  3. **格式越权**（输出未经 schema 许可的字段/动作）
- 拒绝码语义明确，比「输出不合法就重试」的泛化重试可观测得多（能统计幻觉类型分布）。

**判定：三类拒绝码采纳，落点 `backend/app/core/grounding.py`（新建）。**

---

## 五、三仓横向对比与采纳汇总

| 维度 | TradingAgents | ai-hedge-fund | Vibe-Trading |
|---|---|---|---|
| 架构 | LangGraph 多智能体圆桌 | 线性 pipeline | 轻量单 Agent |
| LLM 成本 | 12 次/票（过高） | 每分析师 1 次 | 1-2 次/票 |
| 可解释性 | **置信度规则引用** ✔ | 一般 | 拒绝码可观测 ✔ |
| 数据缺失处理 | 未显式处理 | **弃权语义** ✔ | 拒绝码覆盖 ✔ |
| 引入编排？ | 否 | 否 | 否 |

### 采纳清单（只采纳契约，不采纳编排）

| # | 采纳项 | 来源 | 落点 |
|---|---|---|---|
| 1 | 置信度必须附规则解释 | TradingAgents | LLM prompt 契约 |
| 2 | 弃权（no-opinion）为合法输出 | ai-hedge-fund | 同上 |
| 3 | 反幻觉三类拒绝码 | Vibe-Trading | `backend/app/core/grounding.py`（新建） |

### 共同判定：多 Agent 编排不引入

三个仓库的编排复杂度与其决策质量**无实证正相关**（未见任何一家公开可复现的胜率对比），而成本与延迟显著上升。本项目已有的「规则引擎为主 + LLM 点缀（复盘/归因）」结构更适合打板场景，维持不动。
