一、问题排查结论

1.1 先澄清项目内现状

grep 全仓核实：ashare-ai-trader 项目并未安装也未引用 easytrader——它不在 requirements.txt / requirements.lock，backend/.venv 里也没有。唯一提及是 docs/realtime-broker-feasibility-2026-09-01.md §4.4，当时的评估就是「客户端 UI 自动化：灰色地带、违反券商协议、客户端一改版即失效，不推荐」。因此「无法使用」发生在独立环境，本次在 /tmp 隔离 venv 中完整复现。

1.3 「无法使用」的根因分层

层级根因能否修复
L1 平台限制（决定性）核心卖点的「券商客户端自动交易」= pywinauto 驱动 Windows 窗口控件，macOS/Linux 上从第一行代码就不可用，报错还是晦涩的 AssertionError: 16不可修复（架构性）
L2 反自动化对抗（Windows 上的决定性问题）同花顺/券商客户端持续加验证码、改版界面。issue #448/#452/#461 从 2021 年挂到今天未解；2026 年还在新增：#524（同花顺新版下单界面去掉市场选择→跟随策略报错）、#527/#528（验证码修复 PR 积压半年未合并）、#529（miniqmt 模式 balance 可用金额经常为 0）慢性病，永远在追赶
L3 依赖/版本兼容① requires_python 从未声明——任何 Python 版本都"装得上"，跑不跑得起来不负责；② easyutils 与 pandas 3.x 不兼容；③ 官方报错文本里的 extra 名写错（xtquant ≠ miniqmt）可绕过（钉 pandas<3、用对 extra 名），但没解决 L1/L2
L4 维护节奏2021-03 → 2025-03 停更 4 年；2025 年复活后 PyPI 只发了 0.23.7（2025-04-16），仓库里 2025-09 之后的修复（#511 setup.py 语法错误、#520 follower 参数等）没有发新版，pip 装到的是带已知 bug 的版本需从源码安装才拿到修复
一句话结论：easytrader "无法使用" 不是某个依赖坏了，而是三重结构性问题叠加——平台锁死（Windows only）+ 客户端反自动化军备竞赛（验证码/改版）+ 半停滞的维护。在你当前 macOS 环境下，它四个模式里三个（ths/universal/gj/yh 客户端、miniqmt）从原理上就不可用，剩下的雪球模式也需要有效 cookie 且功能有限（组合跟随，非券商实盘）。

二、降级到旧版本：影响分析

2.1 降级能否解决「无法使用」——逐场景判定

你遇到的场景降级有效？理由
在 macOS 上跑客户端模式无效0.16（2018）到 0.23.7 全系基于 pywinauto，平台限制从未变过
Windows 上同花顺客户端弹验证码无效验证码是客户端侧反自动化行为（2021 年起新客户端引入），与 easytrader 版本无关；老版本反而更不认识新界面
新 Python（3.12/3.13）安装或运行失败无效且更糟easytrader 未声明 Python 版本约束，旧版（0.18/0.19，2019-2020 代码）对新 Python 兼容性只会更差；0.23.x 已是兼容性最好的一代
easyutils 在 pandas 3 下报 pandas._config 错降级 easytrader 无效easyutils 上游只有 0.1.7 一个版本可装，没有"旧版好 easyutils"；有效做法是钉 pandas<3
0.23.7 的已知 bug（setup.py 语法错误等）无效bug 在 PyPI 发布物里，旧版 bug 更多；正确做法是 pip install git+https://github.com/shidenggui/easytrader 装仓库最新（含 #511/#520 修复）

2.2 降级对本项目其他依赖的影响

关注点实测结论
与项目现有依赖的版本冲突零冲突。easytrader 0.23.7 对 pandas / requests 均不钉版本（实测 3.9 隔离环境与项目同款 pandas 2.3.3、requests 2.32.5 共存无冲突）；唯一钉死的是 pywinauto==0.6.6，但它是孤立包，不反向影响其他库
是否动了项目 venv没有。easytrader 本就不在 requirements 中，项目零引用；本次全部测试在 /tmp 隔离环境完成并已清理
若强行引入会新增什么7 个新依赖：flask、pillow、pywinauto、easyutils、six、cssselect/pyquery 等（为雪球模式服务）；不会升级任何现有包
降级的连带风险若为了 easytrader 把项目 pandas 钉回 1.x/2.0，会真实伤害项目：本项目 pandas 2.3.3 是 Parquet 快照、marketdb、复盘链路的运行基线，回退属得不偿失
结论：降级 easytrader 解决不了任何一类「无法使用」，也不需要对项目依赖做任何让步——它是"无效且无副作用"，但正因为无效，没有执行的必要。

3.4 推荐结论（按场景）

场景推荐理由
A. 给 ashare-ai-trader 接 A 股实盘（维持"本地策略引擎 + 外部执行"架构）miniQMT + xtquant（Windows 网关机），项目内自写 BrokerAdapter券商正规报备通道（10 万日均资产门槛，09-01 可行性文档 §4.2 已调研）；easytrader 0.23 的 miniqmt 模式本质也是封装 xtquant——不如直连；与现有 RiskEngine/人工确认链路可无缝衔接。vnpy 整套引入属重复建设
B. 需要开箱即用的完整量化平台（回测+实盘+风控+多市场，可接受重框架）vnpy（VeighNa）唯一同时满足 star≥4000（45k）/活跃（9 月仍在 push）/A股实盘 gateway（XTP、华鑫、东财 EMT）/口碑（社区公认事实标准）的开源项目；本机 macOS 核心实测通过
C. 只想"跟单/雪球组合自动化"（不碰券商客户端）easytrader 雪球模式（仓库最新源码）勉强可用需自备有效 cookie，接受风控不确定性；若继续走这条路，务必 pip install git+... 装 0.23.7 之后的修复，并钉 pandas<3
不推荐backtrader / QUANTAXIS / qlib 作为实盘替代分别因：停止维护 / 实盘能力弱 / 无执行层（纯研究平台）

3.5 如果最终走 miniQMT 线路（建议路径）

① 券商开通 miniQMT 权限（国金/银河等 10 万门槛渠道，C4 测评 + 6 个月交易经验 + 程序化报备）→ ② Windows 机常驻 miniQMT 客户端作网关（交易时段在线）→ ③ 项目新增 BrokerAdapter 接口的 xtquant 实现（place_order / cancel / query_positions / query_trades）→ ④ 下单前过现有 RiskEngine 预检，保留人工确认红线 → ⑤ 灰度：模拟账号 1–3 个月 → 小资金实盘。macOS 本机负责策略引擎，通过局域网调用 Windows 网关（xtquant 支持跨机连接）。
